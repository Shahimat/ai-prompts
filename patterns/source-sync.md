# source-sync

Механизм синхронизации промпта с его источником. Позволяет
проекту-потребителю одной командой сверить свою локальную версию (или
проектную документацию, построенную по промпту) с актуальной версией
промпта в источнике, получить план изменений и внести их с явного «да».

## Назначение

- Промпт эволюционирует. Проекты, которые его применили, должны иметь
  дешёвый способ узнать об обновлениях и мигрировать.
- Ссылка на raw-версию может быть подменена или указывать на другой
  промпт — сверка по стабильному ключу защищает от этого.

## Требования к целевому промпту

В frontmatter обязательны:

- `key` — стабильный kebab-case идентификатор промпта. Один раз выбран
  — не переименовываем без явного согласования.
- `patterns: [..., source-sync, ...]` — декларация применённого
  паттерна.

В теле промпта — inline-блок из этого паттерна (см. ниже).

## Требования к проекту-потребителю

Проект, применяющий промпт, хранит в своём конфиге два поля (типовое
место — `context/project.yml`, но паттерн не требует именно этого пути;
важно, что поля есть):

- `contract_source` — raw-URL источника промпта (обычно
  `raw.githubusercontent.com/...`).
- `contract_key` — ожидаемое значение поля `key` из frontmatter
  источника.

Первый раз оба поля сохраняются при первичной поставке промпта
(агент берёт `key` из frontmatter, либо пользователь задаёт явно). Далее
пользоваться без переспрашивания.

## Протокол команды синхронизации

Ключи команды: «сверь спецификацию с источником», «синхронизируй
контракт», «обнови из источника», «проверь источник».

По такой команде агент выполняет:

1. Читает `contract_source` и `contract_key` из конфига проекта.
2. Если `contract_source` отсутствует или пуст — отвечает «источник не
   сохранён, пришли ссылку». Не идёт дальше. При первом получении
   ссылки — сохраняет оба поля.
3. Если поля есть — идёт по ссылке (WebFetch).
4. Сверяет поле `key` из frontmatter источника с сохранённым
   `contract_key`. Совпадают — читаем нужный промпт, идём дальше. Не
   совпадают — ссылка ведёт на другой промпт (или он подменён). Стоп,
   сообщает пользователю, не применяет.
5. Если ключ сошёлся — сравнивает содержимое источника с текущим
   состоянием проекта (проектной документации, локальной копии
   промпта — что применимо).
6. Если расхождений нет — отвечает «без изменений».
7. Если расхождения есть — выдаёт план миграции: перечень конкретных
   правок с указанием файлов/разделов. Дожидается явного «да» до
   внесения.

### Синхронизация с источником

Применение паттерна `source-sync` (см. `patterns/source-sync.md` в
репозитории `ai-prompts`). Inline-копия обновляется вместе с паттерном.

Когда пользователь в первый раз даёт ссылку на raw-версию этого промпта
(обычно `raw.githubusercontent.com/...`) — сохрани её в конфиге проекта
(типовое место — `context/project.yml`) в поле `contract_source`,
одновременно сохрани поле `contract_key` (значение берётся из frontmatter
источника либо задаётся пользователем явно). Не переспрашивай повторно:
раз сохранили, пользуемся.

По команде **«сверь спецификацию с источником»** (варианты:
«синхронизируй», «обнови из источника», «проверь источник») выполняешь
цепочку:

1. Прочитай `contract_source` и `contract_key`.
2. Если `contract_source` нет или он пуст — явно ответь: «источник не
   сохранён, пришли ссылку». Дальше не идёшь.
3. Если поля есть — сходи по ссылке.
4. Сверь поле `key` из frontmatter источника с сохранённым
   `contract_key`. Совпадают — читаем нужный промпт, идём дальше. Не
   совпадают — ссылка указывает на другой промпт (или он сменился под
   этим URL). Стоп, сообщи пользователю, не применяй.
5. Если ключ сошёлся — сравни содержимое источника с текущим состоянием
   проектной документации по слоям: что нового появилось, что
   изменилось, что удалилось.
6. Если расхождений нет — коротко ответь «без изменений».
7. Если расхождения есть — выдай план миграции: перечень конкретных
   правок по слоям и файлам. Дождись явного «да» до внесения.

# source-sync

Механизм синхронизации промпта с его источником. Позволяет
проекту-потребителю одной командой сверить свою локальную версию (или
проектную документацию, построенную по промпту) с актуальной версией
промпта в источнике, получить план изменений и внести их с явного «да».

Поддерживает **множественные источники** (базовый контракт + подключённые
модули) через общий индекс `prompts/index.yml` с SHA-256 checkpoint по
каждому источнику: анализируются только те, у которых SHA разошёлся.

## Назначение

- Промпт эволюционирует. Проекты, которые его применили, должны иметь
  дешёвый способ узнать об обновлениях и мигрировать.
- Ссылка на raw-версию может быть подменена или указывать на другой
  промпт — сверка по стабильному ключу защищает от этого.
- Fetch по каждому источнику затратен по токенам. Единый индекс +
  SHA-checkpoint позволяет одной операцией понять, что вообще менялось,
  и точечно тянуть только разошедшееся.

## Требования к целевому промпту

В frontmatter обязательны:

- `key` — стабильный kebab-case идентификатор. Один раз выбран — не
  переименовываем без явного согласования.
- `kind` — тип промпта (`contract` / `module` / `pattern` / `prompt`).
- `patterns: [..., source-sync, ...]` — декларация применённого
  паттерна.

Для модулей (`kind: module`) дополнительно обязателен:

- `applicable_to: [<base-key>, ...]` — список ключей базовых промптов, к
  которым модуль применим.

В теле промпта — inline-блок из этого паттерна (см. ниже) либо указатель
на поставляемый skill `source-sync`. Его версия протокола может жить
в reference skill: выбирается по действующему или явно целевому контракту,
не загружается вместе с протоколом другой версии.

## Требования к источнику (репозитория промптов)

Источник промптов (например, `ai-prompts`) содержит единый индекс:

- **`prompts/index.yml`** — машиногенерируемый каталог всех промптов.
  Для каждого промпта — `key`, `path`, `raw` (URL), `sha256`
  (SHA-256 от файла), `applicable_to` (для модулей).
- Skills (`skills/<name>/`) и субагенты (`agents/<name>.md`) — тоже
  записи индекса (группы `skills`, `agents`). У skill нет общего `raw`:
  это каталог, в записи — список `files` с `raw` и `sha256` каждого
  файла, а `sha256` самой записи меняется при правке любого файла.
- Индекс генерируется скриптом, не пишется руками. Правда — в самих
  файлах промптов; индекс — навигация и SHA-справка.
- Расхождение индекса с фактическим содержимым файлов должно ловиться
  на CI и валить билд.

## Требования к проекту-потребителю

Пути задаёт базовый контракт. Ниже и в inline-шаблоне показан вариант v3:
`.oc3/project.yml` и `.oc3/modules/<key>.yml`. Для v2 используй
`context/project.yml` и `context/modules/<key>.yml` во всём протоколе,
включая чтение `sync`, поиск manifest'ов и сохранение SHA. Это подстановка
путей, не миграция структуры: не создавай `.oc3/` в v2 ради source-sync.
Копия v2 в `skills/source-sync/references/v2.md` уже содержит эти пути;
прежние inline-копии производных контрактов также используют `context/`.
Совместимые модули должны явно описывать применимые раскладки. Остальные
правила и проверки одинаковы.

Проект, применяющий промпты, хранит в `.oc3/project.yml` блок
`sync`:

```yaml
sync:
  index_source: <raw-URL prompts/index.yml источника>
  index_sha: <hex — SHA-256 индекса на момент последней синхронизации>
  contract:
    key: <key базового контракта>
    synced_sha: <hex — SHA-256 контракта на момент последней синхронизации>
```

Для каждого подключённого модуля — отдельный manifest
`.oc3/modules/<key>.yml` со своими `source`, `synced_sha`,
`synced_at`, `provides`.

Если источник поставляет **части** — skills и субагентов — их SHA
хранятся рядом с SHA самого источника (в `sync.contract` или в
manifest'е модуля):

```yaml
parts:
  skills:
    <name>: <hex — sha256 записи skill из индекса>
  agents:
    <name>: <hex>
```

Состав обязательных частей задаёт сам источник: `provides.skills` /
`provides.agents` либо его явный раздел поставки. `parts` хранит checkpoints,
а не разрешение исключить недостающую часть. Весь каталог устанавливать не нужно.
Декларация должна соответствовать актуальному SHA источника из индекса.
Если она неизвестна или относится к другой версии, получи исходник по `raw`,
сверь его SHA и прочитай декларацию; совпадение checkpoints этого не отменяет.
Нет обязательной части в индексе или не подтверждён её SHA — сообщи о проблеме,
не объявляй sync завершённым и не обновляй его checkpoints.

Skill `skills/<name>/…` источника ставится в `.agents/skills/<name>/…` проекта:
префикс источника заменяется, относительные пути внутри каталога сохраняются.
На каждой сверке проверяй наличие и SHA **всех** `files` по каталогу, независимо
от SHA самого контракта, индекса или checkpoint записи skill. Части субагентов
ставятся по раскладке их контракта; наличие parts не вводит обязательные роли.

Недостающий, повреждённый или изменившийся файл — расхождение для общего плана.
Конфликт с одноимённым project-skill не решается молчаливой перезаписью;
удаляются только подтверждённые части поставки, не неизвестные локальные файлы.
Полный текст skills при этом не загружай в рабочий контекст: доставка и проверка
байтов не являются вызовом skill. Их инструкции читаются по триггеру задачи.

Первое сохранение полей — при первичной поставке промпта (агент берёт
`key` из frontmatter, `synced_sha` — из fetch'а). Далее пользоваться
без переспрашивания.

## Единый fetch-канал: только `curl`

Fetch источников для синхронизации выполняется **только `curl`** через
Bash с фиксированными флагами и заголовками:

```bash
curl -fsSL -H "Cache-Control: no-cache" -H "Pragma: no-cache" "<url>"
```

WebFetch и аналоги **запрещены** для source-sync:

- локальный кэш инструмента может подставить старый ответ;
- pre-processing (HTML → markdown, обрезка) искажает контент;
- SHA-checkpoint от такого ответа не сойдётся с SHA-256 raw-контента
  источника, и вся механика развалится.

SHA-256 считается от того же байт-потока:

```bash
curl -fsSL -H "Cache-Control: no-cache" -H "Pragma: no-cache" "<url>" | shasum -a 256 | awk '{print $1}'
```

На практике удобнее сохранить ответ во временный файл, посчитать SHA,
если не совпал с сохранённым — работать с этим же файлом, не делая
повторный fetch.

## Протокол команды синхронизации

Ключи команды: «сверь всё», «сверь спецификацию с источниками»,
«синхронизируй», «обнови из источника», «проверь источник».

По такой команде агент выполняет:

1. Читает `sync.index_source` из `.oc3/project.yml`. Если пусто —
   отвечает «источник не сохранён, пришли ссылку», дальше не идёт. При
   первом получении — сохраняет.
2. `curl` тянет `index.yml`, считает SHA-256 полученного контента.
3. Сравнивает SHA с `sync.index_sha`, но не выходит до проверки полноты частей.
   Неизменный индекс не доказывает наличие и целостность локальных файлов.
4. Читает нужные записи индекса. Для каждого подключённого источника
   (контракт из `sync.contract.key`, модули из `.oc3/modules/*.yml`)
   находит актуальный `sha256` в индексе, а декларацию обязательных частей —
   в проверенной версии источника с этим SHA.
5. Сравнивает `sha256` из индекса с `synced_sha` в проекте:
   - совпал — не перечитывает источник целиком, но проверяет его части;
   - разошёлся — `curl` тянет конкретный файл по `raw` из индекса,
      сверяет SHA, делает полный diff, готовит план миграции.

   Части проверяет независимо: сравнивает `parts` и каждый локальный файл
   с `files` записи skill. Недостающие и несовпавшие файлы получает по их
   `raw`, сверяет SHA; новый обязательный skill входит в тот же план.
   Неизменные инструкции целиком в контекст не загружает.
6. Дополнительные проверки по индексу:
   - подключённый модуль пропал из индекса → предупреждает пользователя;
   - контракт или модуль помечен в индексе `deprecated` → предупреждает
     и называет замену (ключ или путь из поля), миграция — по запросу;
   - `applicable_to` подключённого модуля больше не содержит `key`
     подключённой базы → предупреждает;
   - в индексе появились новые модули с подходящим `applicable_to` →
     упоминает как справку («опционально можно подключить»), не
     подключает сам.
7. Только если источники, обязательные части и локальные файлы полны и
   совпадают — «без изменений» одной строкой.
8. Если расхождения есть — единый план миграции: перечень конкретных
   правок по слоям и файлам. Дожидается явного «да» до внесения.
9. После согласования применяет весь план и повторно сверяет файлы поставки.
   Только после этого обновляет все SHA: `sync.index_sha`,
   `sync.contract.synced_sha`, `synced_sha` в manifest'ах затронутых
   модулей, SHA частей в `parts`, `synced_at` — на текущую ISO-дату.
   Неполная поставка не объявляется завершённым sync; чужие настройки и
   project-skills не меняются вне согласованного плана.

## Проверка `key` в источнике

При тяге отдельного промпта (контракта или модуля) не через индекс, а
напрямую по ссылке — обязательная сверка: поле `key` из frontmatter
источника == сохранённый ключ (в `sync.contract.key` или в manifest'е
модуля). Не совпало — стоп, сообщи пользователю, не применяй. Защита от
подмены URL.

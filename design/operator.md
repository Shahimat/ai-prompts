# Оператор: одна сессия раздаёт работу ролям и jobs

Статус: принят (2026-10-29). Решения ниже приняты в обсуждении с
пользователем; закрытые открытые вопросы — в разделе «Решения». Документ проектирования: в
`prompts/index.yml` не попадает.

## Зачем

Проект на v3 может вести много параллельных работ: 8–10 тикетов,
слежение за PR и merge checks, сводки пользователю. Если всё это делает
одна интерактивная сессия, её контекст забивают тела skills, сырые
ответы систем и код. Замер на первом потребителе: контекст вырос с
26,5k до 247k токенов за 150 запросов, ~60k из них — сырые ответы
трекера через `Bash`. Каждый ход перечитывает весь хвост.

Цель — основная сессия становится оператором: держит намерение
пользователя, раздаёт работу и пересказывает итоги. Читают, правят и
проверяют роли с чистым контекстом.

Это обобщение правила 4 ядра: запись в документацию уже делает роль, а
не основная сессия. Оператор переносит тот же принцип на всю тяжёлую
работу.

## Место в v3

- **Универсальная спека.** Всё ниже — модули, роли и срез harness в
  источнике `ai-prompts`. Проект получает их через `contract-setup`, как
  любую возможность. В источнике нет ни одной конкретной системы
  компании: они — провайдеры проекта или машины.
- **Ядро не меняется.** Модули только добавляют: роли, skill, блок
  `AGENTS.md`, convention автономии, команды `ai ops`.
- **Постепенно.** Ступени с `requires`: проекту, которому достаточно
  ролей, рантайм не ставится.
- **Рантайм — только Claude Code.** `roles` и `operator` нейтральны к
  агенту (субагенты есть и у Codex). `ops`, `watchers`, `dashboard`
  запускают роли через `claude -p`, как harness сейчас; модуль говорит
  это явно.

## Ступени: модули v3

1. **`roles`** — роли `researcher`, `oracle`, `reviewer` в `agents/`
   источника. В сессии — субагенты; в harness — роли с `output`.
   Подходит любому проекту.
2. **`operator`** — skill-протокол оператора, convention автономии,
   сводка на `SessionStart`. `requires: [roles]`.
3. **`ops`** — jobs поверх сессий harness, карточка задачи, журнал,
   `ai ops brief | status | watch`, провайдеры `tasks` и `vcs`.
   `requires: [operator, harness]`.
4. **`watchers`** — наблюдатели, общий для машины планировщик,
   провайдеры `review`, `checks`, `schedule`. `requires: [ops]`.
5. **`dashboard`** — `ai ops serve`: HTML-доска и ответы на вопросы из
   браузера. `requires: [ops]`.

Пресет `operator` — `external` плюс все пять ступеней. Остальные виды
проектов берут ступени по вкусу, чаще всего только `roles`.

Паттерны: `source-sync` — у всех пяти модулей; `guardrail-dual-level` —
у `operator` (автономия).

## Главное решение: работа живёт вне сессии оператора

Субагенты сессии (`Agent`) не подходят для параллельных долгих работ:
умирают вместе с процессом, их итоги копятся в контексте оператора,
журнала хода нет. Поэтому:

- работа по тикету — **job**: сессия автомата harness на диске, роли —
  отдельные процессы `claude -p` (механика `design/roles.md`:
  состояния, счётчики, `open`, `result` и `verdict` по схеме);
- оператор не хранит состояние в контексте: доска jobs — файлы,
  рестарт и чистка контекста ничего не теряют;
- в контекст оператора попадают только короткие итоги и события.

Цена одного делегирования для оператора — бриф (300–800 токенов) и итог
(100–500). Та же операция в сессии — 5–20k, которые остаются до конца
сессии. Общий расход по всем агентам сопоставим: каждый работник платит
12–25k за старт, зато не копит длинный хвост. Мелочь (один короткий
вызов) выгоднее делать на месте.

## Провайдеры

Провайдер — реализация интерфейса внешней точки. Через провайдеры
спека остаётся универсальной: роли и автоматы знают интерфейс, а не
систему.

Интерфейсы:

- **`tasks`** — источник задач: `fetch(ref) → карточка`, `update(ref,
  поля)`, `list(query)`;
- **`vcs`** — изолированная копия на job: `create(job) → путь`,
  `diff(путь)`, `remove(путь)`;
- **`review`** — PR: `list(query)`, `status(id)`, `comment(id, текст)`,
  `approve(id)`;
- **`checks`** — проверки PR или ветки: `status(id) → список проверок`;
- **`schedule`** — системный планировщик машины: `install(unit)`,
  `remove(unit)`, `status()`.

Где живут, по возрастанию охвата:

- **встроенные в harness** — нейтральные: `tasks/local` (markdown-файл
  или цель `goals`), `vcs/git` (`git worktree`), `schedule/launchd`,
  `schedule/systemd` (user-таймер);
- **машина** — `~/.config/harness/providers/<interface>/<name>.ts`:
  общие для всех проектов пользователя (например, провайдеры компании,
  которые нужны в десяти репозиториях);
- **проект** — `.agents/providers/<interface>/<name>.ts`: только для
  этого проекта.

Проект выбирает провайдер по имени в `context/ai-core.yml` → `ops`:

```yaml
ops:
  providers:
    tasks: local
    vcs: git
    review: none
    checks: none
```

Имя ищется в проекте, затем на машине, затем во встроенных. Одно имя на
двух уровнях — ошибка, а не тихая подмена (как у расширений `.agents/`).
Провайдер — модуль `export default { interface, name, … }`; проверка
формы — при загрузке, ошибка с путём к полю.

Провайдер действует наружу — значит, подчиняется автономии: методы,
которые пишут (`update`, `comment`, `approve`, `install`, `remove`),
harness вызывает только если convention разрешает действие.

## Оператор

- Skill `operator` — без `context: fork`: меняет поведение основной
  сессии. Короткий: кому отдать задачу, формат брифа, что делать с
  итогом, формат сводки. Код и сырые ответы систем оператор не читает;
  проверка — работа `reviewer`, а не перечитывание за работником.
- Сводка на старте: `ai ops brief` — до 20 строк (активные jobs,
  блокирующие вопросы, свежие события). Его же подставляет hook
  `SessionStart` (`startup`, `resume`, `compact`): после чистки контекста
  оператор восстанавливается сам. Hook ставит `ai adapters sync` из
  `hooks` в `context/ai-core.yml`, как `docs-guard`.
- Пробуждение: оператор держит фоновый `ai ops watch` — команда
  выходит на первом важном событии проекта (вопрос, провал, готово),
  инструмент будит сессию. Опроса по таймеру в сессии нет.
- Сводка пользователю — до 10 строк на все jobs; подробности — журнал и
  дашборд.

## Job по задаче

### Карточка

Роли источник задач не читают. В `intake` провайдер `tasks` превращает
задачу в карточку `.ops/jobs/<id>/task.md`: заголовок, контекст, DoD,
ссылки, ссылка на источник. `researcher`, `implementer`, `reviewer`
работают только с карточкой и артефактами job.

Канон текста задачи — источник: его правят люди. Поэтому:

- текст карточки обратно не пишется; на `ready` и `done` через
  `tasks.update` уходят только статус и ссылка на результат (PR или
  diff) — по политике автономии, по умолчанию после «да»;
- на каждом `open` job и перед `review` карточка заново читается из
  источника; изменился DoD — событие «DoD изменился» и вопрос:
  продолжить по новому или по старому. Иначе `reviewer` проверит
  устаревший DoD.

### Автомат `ticket-work`

1. `intake` — провайдер `tasks`: карточка `task.md`.
2. `research` — `researcher`: `research.md`.
3. `plan` — план и пауза с вопросом «план ок?»; «да» — дальше.
   Упрощённо, без `plan-review`.
4. `implement` — `implementer` в копии от провайдера `vcs`.
5. `verify` — механика цели: команды сборки, тестов и линта из конфига
   job.
6. `review` — `reviewer` против DoD; провал — в `implement` с
   находками, общий лимит кругов.
7. `ready` — diff и сообщение коммита; git-запись делает пользователь.
8. `docs` — намерения в `docs-delta`.
9. `done` — копия `vcs` удаляется, наблюдатели job гаснут.

Из любого состояния — `question`: пауза, вопрос в событиях и на доске,
ответ продолжает job. Событие `feedback` от наблюдателя возвращает job
из `ready` в `implement` с запросом.

### Журнал

`.ops/jobs/<id>/` (в `.gitignore`), чтобы пользователь мог проследить
ход сам:

- `events.jsonl` — переходы, вызовы ролей, токены, время;
- `log.md` — то же человеческим языком (`tail -f`);
- `runs/<state>-<n>.jsonl` — полный stream-json каждого прогона роли;
- артефакты: `task.md`, `research.md`, `plan.md`, `diff`, `review.json`.

### Граница: рантайм не знание

`.ops/` — состояние работ, не документация и не memory. Устойчивое
(факт о системе, решение, правило) попадает в документацию только через
`docs-delta`, в состоянии `docs` job или по намерению оператора. Роли и
оператор не опираются на старые журналы как на источник правды: правда
— документация и источник реальности. Без этой границы запрет memory
обходится через `.ops/`.

## Роли

Каждая — `agents/<name>.md` источника с `tools`, `model`, `output`.

- **`researcher`** (opus; чтение и каналы на чтение) — глубокий разбор.
  Отчёт по схеме: вопрос, «коротко», карта «что где», находки с
  доказательствами (ссылка, `file:line`), выводы, открытые вопросы,
  уверенность. Полный отчёт — файл, в итог — до 8 строк и путь.
- **`oracle`** (sonnet; только документация проекта) — быстрый ответ.
  Не нашёл — `miss`, найденное и черновик вопроса для `researcher`. Сам
  не пишет. На промах оператор спрашивает одной строкой («в доке нет;
  найдено: …; исследовать / в очередь / не надо»); вопрос уже в очереди
  исследований (`goals`) — не спрашивает, а говорит «уже в очереди,
  позиция N». Политика автономии может разрешить «в очередь сам»;
  запуск `researcher` — только после «да»: это дорогая работа.
- **`implementer`** (opus) — правки в копии по карточке, исследованию и
  плану.
- **`reviewer`** (sonnet) — DoD и результат, рассуждений исполнителя не
  видит; вердикт по каждому пункту DoD (`ok` / `fail` / `unknown`) с
  доказательством, цитаты harness сверяет дословно, как в `docs-delta`.
- `docs-keeper`, `judge` — ядро, без изменений.

Роль, которая работает с источником задач, не нужна: это провайдер
`tasks`, а не модель.

## Наблюдатели

Трекеры, PR и checks сами не сообщают об изменениях: локального
вебхука нет, таймер нужен. Постоянный демон — нет.

### Наблюдатель

`.ops/watches/<id>.yml` проекта: провайдер и запрос (`review`,
`checks`), интервал (по умолчанию 5 минут, минимум 1), `until`
(`merged`, `closed`, `job-done`), job, к которому привязан. Гасится сам по `until` или оператором:
`ai ops watch list | stop <id>`.

Лестница моделей:

- **L0 — код, без модели**: провайдер отдаёт статусы, сравнение с
  прошлым тиком; не изменилось — ноль токенов;
- **L1 — haiku**: изменилось — важно ли (новый комментарий, упал
  check);
- **L2 — sonnet**: нужна работа — формирует запрос и шлёт событие
  `feedback` в job, не оператору; оператор видит строку в сводке.

### Один планировщик на машину

Одни и те же провайдеры могут работать в десяти репозиториях. Поэтому
планировщик — общий для машины, а не на каждый проект:

- **Реестр** — `~/.config/harness/ops/projects.yml`: корни проектов с
  включёнными наблюдателями. `ai ops schedule on` в проекте добавляет
  его в реестр, `off` — убирает.
- **Unit один** — провайдер `schedule` ставит его при первом проекте в
  реестре и снимает, когда реестр пуст. Установка и снятие — действия
  наружу: только после «да».
- **Тик** — unit раз в минуту (launchd `StartInterval 60`, systemd
  `OnUnitActiveSec=1min`) запускает диспетчер `ai ops tick --all`. Он
  читает реестр и время следующей проверки каждого наблюдателя и
  вызывает `npx ai ops tick` только в корнях, где что-то подошло, —
  проект работает своей версией пакетов. Пустой тик — миллисекунды, без
  запуска Node в проектах. Интервалы — у наблюдателей: merge checks
  можно смотреть каждую минуту, PR на ревью — раз в 15, без отдельных
  units. Недоступный корень — предупреждение в событиях, не падение.
- **Общий кэш опроса** — `~/.config/harness/ops/cache/`: ключ —
  провайдер и запрос, срок — интервал. Десять проектов, которые следят
  за одними PR, опрашивают систему один раз за тик.
- **Общий поток событий** — `~/.config/harness/ops/events.jsonl`: у
  каждого события поле `project`. `ai ops watch` проекта по умолчанию
  видит свои события, `--all` — события всех проектов машины.
- **Общий лимит моделей** — подписка одна на пользователя: лимит
  одновременных прогонов `claude -p` и очередь — на машину, а не на
  проект. Конфиг — `~/.config/harness/ops/limits.yml`:
  - полоса jobs — до 4 прогонов, из них opus не больше 2;
  - полоса наблюдателей — 1 отдельный слот под L1 и L2: очередь jobs
    не душит наблюдателей, наблюдатели не съедают слоты jobs;
  - порядок в очереди jobs — продолжение после ответа пользователя →
    `review` → `implement` → `research`: ближе к готовому — раньше;
  - rate limit от `claude -p` — очередь встаёт на экспоненциальную
    паузу, оператору одно событие; job ждёт, не падает.

  Числа — стартовая догадка: лимиты подписки неизвестны. Токены каждого
  прогона пишутся в `events.jsonl`, по ним лимиты калибруются.

Формат реестра, кэша и событий — версионированный: проекты с разными
версиями пакетов делят их без конфликтов.

## Политика автономии

Действия наружу — по `context/conventions/autonomy.yml` проекта: «сам»,
«после „да“», «никогда». Паттерн `guardrail-dual-level`:

- **агент** — правило в блоке `AGENTS.md` модуля `operator`;
- **рантайм** — harness не вызывает пишущие методы провайдеров и не
  выдаёт роли инструменты записи, если политика не разрешает действие.

Модуль ставит стартовую политику: всё наружу — «после „да“», git-запись
— «никогда» (её делает пользователь, правило ядра). Проект расширяет
«сам» явными записями: например, ревью чужого PR — анализ, не больше
одного issue и только при реальной нужде, approve.

## Где живёт код

Нового пакета нет. Job — сессия автомата, наблюдатель — маленький
автомат (L0 — код, L1 и L2 — роли), сводка и дашборд читают сессии: всё
это зона `@shahimat/harness`.

- `@shahimat/harness` — срез `harnesses/ops/`: команды `ai ops …`,
  автоматы `ticket-work` и `watch`, загрузчик провайдеров, встроенные
  провайдеры, реестр, кэш и поток событий машины, `serve`.
- Модули `roles`, `operator`, `ops`, `watchers`, `dashboard` — в
  `prompts/modules/`; роли — в `agents/`; skill `operator` — в
  `skills/`; пресет `operator` — в `presets/`.
- Проект или машина — свои провайдеры и, при нужде, свои автоматы.

Ожидания, которые нужно расширить (правка заголовков — с согласия
пользователя): состав команд и автоматов harness в
`expectations/harness.expect.ts`. Состав пакетов не меняется.

## Этапы

1. Этот документ.
2. Источник: роли `researcher`, `oracle`, `reviewer`; модуль `roles`.
3. Источник: skill `operator`, convention автономии, hook
   `SessionStart`; модуль `operator`.
4. harness: срез `ops` — jobs, карточка, журнал, провайдеры `tasks` и
   `vcs` (`local`, `git`), `brief | status | watch`; модуль `ops`.
5. harness: наблюдатели, планировщик машины, провайдеры `schedule`
   (`launchd`, `systemd`), интерфейсы `review` и `checks`; модуль
   `watchers`.
6. harness: `ai ops serve`, ответы из браузера (канал `ask_user` из
   `design/roles.md`); модуль `dashboard`. Пресет `operator`.
7. Потребитель: проект подключает ступени через `contract-setup`, свои
   провайдеры — в `.agents/providers/` или на машине.

Каждый модуль — отдельный план с паттернами и «да» пользователя.

## Решения

Открытые вопросы черновика закрыты пользователем 2026-10-29:

1. **Промах `oracle`** — оператор спрашивает одной строкой, повторный
   вопрос из очереди не задаёт; «в очередь сам» — по политике, запуск
   `researcher` — после «да». Раздел «Роли».
2. **Карточка `task.md`** — текст обратно не пишется, только статус и
   ссылка; карточка перечитывается на `open` и перед `review`, смена
   DoD — вопрос. Раздел «Карточка».
3. **Лимит моделей машины** — полоса jobs (4, opus ≤ 2) и полоса
   наблюдателей (1), приоритет по близости к готовому, пауза при rate
   limit. Раздел «Один планировщик на машину».
4. **Интервал тика** — unit раз в минуту, интервалы — у наблюдателей
   (по умолчанию 5 минут, минимум 1). Разделы «Наблюдатель» и «Один
   планировщик на машину».

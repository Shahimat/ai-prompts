# Роли и протокол harness

Дата: 2026-10-28. Документ проектирования: в `prompts/index.yml` не
попадает. Проверяемые правила — в `expectations/roles.expect.ts`, здесь —
решения и их причины.

> Текущая модель ролей — `design/operator-centric-v3.md`; этот документ
> остаётся историей.

## Зачем

До ролей одна и та же работа жила в трёх формах: docs-keeper —
субагент и handoff-текст в docs-delta, судья — промпт plan-review и
задания `.judge/` для ручного субагента, обновление источника — строка
в source-sync. Роль сводит их в одно описание, которое работает и в
сессии агента, и в harness.

## Роль

Роль — файл `agents/<name>.md` источника (в проекте —
`.agents/agents/<name>.md`), отдельной сущности `roles/` нет: ключи
субагентов уже используют проекты.

- Frontmatter: `name`, `description`, `output` и необязательные
  `skills`, `tools`, `model`. Схема —
  `expectations/schemas/agent-frontmatter.schema.json`.
- `output` — сообщение протокола, которым роль возвращает итог.
  Без `output` файл — просто субагент, harness его не запускает.
- `model` — короткое имя модели из настроек раннера; адаптер переносит
  его в файл субагента.
- Тело — инструкции, нейтральные к инструменту. Ветка «есть инструмент
  `submit_result` — ответ им, иначе — текстом» делает одну роль
  пригодной для обоих режимов.

Режимы одной роли:

1. **Субагент в сессии агента** — адаптеры генерируют файл субагента
   под инструмент (`.codex/agents/<name>.toml`,
   `.opencode/agents/<name>.md`), основная
   сессия передаёт вход текстом. Работает в любом агенте.
2. **Исполнитель в harness** — `ai role run <name>` или действие
   состояния автомата (`roleOrHandoff`). Описание ролей нейтрально, а
   `ModelRunner` оставляет дорогу runner'у
   под другой агент.

Роли сейчас: `docs-keeper` (`result`), `judge` (`verdict`, только
чтение). Модели — ради скорости каждой правки: `docs-keeper` на `haiku`
(пишет по правилам skill, ошибки ловят `verify` и `review`), `judge` на
`sonnet` (смысловую проверку некому перепроверить: пропущенное
противоречие ничто не поймает). Качество держит и механика harness —
схема ответа, дословные цитаты, бюджет файла. Обе — в ядре контракта v3: судья проверяет документацию на
противоречия в docs-delta. Проверка правок проекта по `*.expect.ts` в
проектах-потребителях — за будущим модулем `expectations`; до него
судья работает только с документацией.

## Протокол

Сообщения — JSON Schema 2020-12, лишние поля запрещены, константа
`PROTOCOL` пакета:

- `result` — итог работы: `status` (`done` / `failed`), `changed`,
  `failed`, `questions`, `report`;
- `verdict` — ответ судьи: `answers` пакета вопросов,
  `contradictions` и `unmeasurable` проверки заголовков или `conflicts`
  — противоречия в документации (`file_a`, `quote_a`, `file_b`,
  `quote_b`, `reason`);
- `question` — блокирующий вопрос по формату skill `workflow`:
  `question`, `options` (от двух), `default`, `reason`.

Вход роли docs-keeper — схема `intents` (`INTENTS_SCHEMA`): список
намерений `kind` / `summary` / `evidence`. Это вход, а не сообщение
ответа, поэтому в `output` ролей не встречается.

Канал для `question` (инструмент `ask_user`) не сделан: ни judge, ни
docs-keeper человека не спрашивают, вопросы docs-keeper уходят в
`result.questions`. Спайк показал, что механика есть (см. ниже).

## Runner: CLI плюс канал результата

Роль запускается CLI-раннером инструмента-хоста (`opencode run`)
под входом пользователя, а не через SDK хоста.

- **Почему не SDK.** Документация SDK прошлого хоста (2026-10-28):
  вход — API-ключ или облачные
  провайдеры; сторонним продуктам на SDK запрещено предлагать вход
  сервиса хоста без согласования с поставщиком. `@shahimat/harness` —
  публичный пакет, поэтому SDK — только с API-ключом. Документация
  называет headless-прогон с JSON-выводом штатным путём из
  программы; harness вызывает инструмент пользователя под его входом.
  Прямой формулировки об этом случае в документации нет — это
  прочтение, а не подтверждённый факт.
- **Канал.** `ai role channel <message> --out <файл>` — MCP-сервер
  stdio без зависимостей с одним инструментом `submit_result`. Ответ
  проверяет ajv по схеме сообщения: невалидный — `isError` с путём к
  полю, модель исправляет и вызывает снова; валидный пишется в файл.
  Ответ текстом harness не читает.
- **Запуск.** `opencode run --format json --auto --agent <роль>
  --model <модель>`: конфиг — из `OPENCODE_CONFIG_CONTENT` (одна
  инструкция — системный промпт роли), `tools` роли — в файле агента,
  итог — инструментом `submit_result` плагина контракта, задание —
  на stdin.
- **Схема инструмента** объявляется без `oneOf` / `anyOf` / `allOf`
  верхнего уровня (их не принимает API инструментов); полную схему
  проверяет канал.

## Проверенные факты (спайк 2026-10-28, CLI прошлого хоста)

- Headless-прогон с MCP-каналом работает под входом по подписке, без
  API-ключа.
- Пустые sources настроек и строгий MCP-конфиг: глобальные инструкции
  пользователя в прогон не попадают.
- MCP-сервер на голом JSON-RPC по строкам: `server/discover` (ответ —
  ошибка «нет метода», клиент продолжает), `initialize`,
  `notifications/initialized`, `tools/list`, `tools/call`.
- Клиент не проверяет аргументы по `inputSchema`: значение вне `enum`
  доходит до сервера — проверка на стороне harness обязательна.
- Ответ `isError` возвращается модели, она исправляет и повторяет вызов.
- Вызов инструмента может ждать ответа долго: 190 с ожидания ответа
  человека прошли без таймаута.
- Stream-режим: несколько
  ходов в одном процессе с одним `session_id`; control-запрос
  `interrupt` прерывает ход.
- В режиме без вопросов MCP-инструмент вне allowlist отклоняется;
  пустой список tools ограничивает только встроенные инструменты.
- Allowlist инструментов принимает несколько значений: позиционный
  промпт сразу после него съедается — поэтому задание идёт на stdin.

## Где используется

- Основная сессия с harness передаёт намерения процессу docs-delta
  напрямую — `ai docs-delta start --name <имя> --file -`, JSON на
  stdin (правило 4 шаблона `AGENTS.md`). Субагент docs-keeper в сессии
  не нужен: правила записи читает только роль, отчёт до 10 строк
  печатает harness. Без harness — субагент docs-keeper, как раньше.
  Команда — в `AGENTS.md`, а не в skill `workflow`: у него уже
  `runs: check`, а skill запускает не больше одного.
- `expect judge --run` — задания `.judge/` отвечает роль `judge`
  параллельно, затем `--apply`. Без `--run` — прежний путь через
  субагента.
- `docs-delta start --file <намерения | ->` — намерения проверяются
  схемой `intents` и хранятся в сессии (`request`), в проект файл не
  пишется; `-` — stdin, так основная сессия передаёт их без файла.
  `apply` выполняет роль `docs-keeper`; без `--file` или при провале
  роли — пауза с заданием агенту (с намерениями). Роли сказано, что
  процесс уже идёт: сама она docs-delta не запускает.
- `review` в docs-delta — после `verify`: роль `judge` получает дельту
  и список изменённых файлов (`git diff HEAD` и неотслеживаемые, без
  `.delta/`) и ищет противоречия с документами по ссылкам и маршрутам.
  Цитаты каждой находки harness сверяет с файлами дословно (с точностью
  до пробелов): без цитаты находка отклоняется — защита от выдуманных
  противоречий. Найденное — `fail`: возврат в `apply`, находки — в
  задании docs-keeper (из `review.json` сессии), общий лимит `verify`.
  Решение противоречия — за docs-keeper: неочевидное он выносит
  вопросом в отчёт. Причину провала `verify` роль по-прежнему не
  получает.
- `plan-review` заморожен и на роли не переведён.

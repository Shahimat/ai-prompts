# Составная документация: субпроекты

Статус: черновик (2026-10-28). Решения ниже — предложения; открытые
вопросы в конце решает пользователь. Документ проектирования: в
`prompts/index.yml` не попадает.

## Зачем

Одна проектная дока описывает несколько частей: сервисы монорепозитория,
несколько целевых систем оверлея, крупные независимые области. Сейчас
экономию чтения дают только namespaces и маршрут «вопрос → где ответ»:
вся дока — одно пространство, и интерактивная сессия, работая с одной
частью, видит маршруты, правила и индексы всех частей. Субпроект
ограничивает, что сессия читает: корень — общее, субпроект — своё.

## Что уже есть и на что опираемся

- Иерархия `AGENTS.md`: Codex читает файлы от корня git до текущего
  каталога (суммарно ≤ 32 KiB); Claude Code подгружает вложенные
  `CLAUDE.md` по мере работы с файлами каталога. Вложенный `AGENTS.md`
  (и прослойка `CLAUDE.md` рядом) — штатный способ дать сессии правила
  части, только когда она там работает.
- `reality` в `context/project.yml` — где правда о «как сейчас»;
  у оверлея — ключи `external`.
- namespaces — области внутри одного проекта; остаются и внутри
  субпроекта.

## Предложение

### Модуль `subprojects`

Субпроекты — модуль-возможность (`prompts/modules/subprojects.md`), а
не часть ядра: большинству проектов они не нужны.

```yaml
key: subprojects
kind: module
applicable_to: [agent-operational-contract-v3]
feature:
  summary: составная документация — субпроекты со своими слоями и вложенным AGENTS.md
  default: false
  requires: []
  conflicts: []
  asks:
    - key: initial
      question: Какие субпроекты завести сразу (ключ — путь)?
```

Модуль ставит: skill `subprojects` (правила частей: наследование,
`scope`, маршруты), блок в корневом `AGENTS.md` (маршрут «вопрос про
субпроект → его `AGENTS.md`»), шаблон вложенного `AGENTS.md`. Ядро
ничего не знает о субпроектах: всё, что модуль добавляет в чужое, —
явно, через `provides`:

- `extends: {project: [subprojects]}` — поле `subprojects` в
  `context/project.yml` корня;
- `extends: {intents: [scope]}` — поле `scope` в намерениях;
- `harness_checks: [subprojects]` — сверка: у каждого объявленного
  субпроекта есть каталог, `context/project.yml` и `AGENTS.md`.

Механика harness (индекс, `review`, `context for` по субпроектам)
включается, только если модуль подключён (`context/modules/subprojects.yml`).

### Субпроект

Субпроект — каталог с собственным `context/project.yml` и вложенным
`AGENTS.md`. Корень объявляет субпроекты:

```yaml
# context/project.yml корня
subprojects:
  billing:
    path: services/billing
    summary: биллинг — тарифы, счета, платежи
```

Субпроект — **слои, а не отдельная установка контракта** (вариант A):
контракт, skills, роли, адаптеры, `context/ai-core.yml` и manifest'ы
модулей — одни на корень. В субпроекте — только слои документации
подключённых модулей (`docs/`, `context/conventions/`, `context/views/`)
и его `context/project.yml` (`summary`, `reality`, `namespaces`,
`external`).

Почему не вложенная установка (вариант B): каждый субпроект со своими
skills и модулями — дубли, свой source-sync на каждый, расхождение версий
контракта внутри одной доки. B оставить на случай, когда часть живёт в
отдельном репозитории (тогда это просто отдельный проект).

### Чтение

- Корневой `AGENTS.md` — маршрут «вопрос про субпроект → его
  `AGENTS.md`» одной строкой на субпроект (ключ и `summary`). Правила
  частей в корне не пишутся.
- Вложенный `AGENTS.md` субпроекта — до 40 строк: одна строка о части,
  маршруты по её слоям, правила, которые действуют только в ней. Жёсткие
  правила ядра не повторяются — они в корне и действуют везде.
- Правило маршрута: работаешь с субпроектом — читаешь корень (общее) и
  этот субпроект; соседние субпроекты — только по явной ссылке.
- `ai context for <path>` (когда появится) определяет субпроект по
  пути и выдаёт документы только корня и его.

### Правила и наследование

- Договорённости корня действуют во всех субпроектах. Субпроект
  добавляет свои, но не переопределяет корневые (как модуль — ядро):
  конфликт — противоречие, его ловит судья в docs-delta.
- `reality` — у каждого субпроекта своя; нет своей — корневая.

### Запись

- Намерение получает необязательное поле `scope: <ключ субпроекта>`
  (схема `intents`); без него — корень.
- docs-keeper пишет в слои своего `scope`; правило полноты и ссылки —
  в пределах субпроекта и корня.
- Судья в `review` сверяет правку с документами того же субпроекта и
  корня; соседние субпроекты — только если правка на них ссылается.
- `ai context index` генерирует `context/index.yml` в каждом
  субпроекте и корневой — со списком субпроектов.

### Журнал решений

Предложение — один `CHANGELOG.md` в корне, ключ субпроекта в начале
сути: `- 2026-10-28 · [arch] billing: … · …`. Решения по составу частей
видны в одном месте; строка ≤ 120 символов остаётся.

## Открытые вопросы

1. **Субпроект внутри модуля — слои (A) или вложенная установка
   контракта (B)?**
   Рекомендация — A.
2. **Журнал: один в корне с ключом субпроекта или свой в каждом?**
   Рекомендация — один в корне.
3. **Может ли субпроект переопределять договорённость корня?**
   Рекомендация — нет, только добавлять.
4. **Глубина: только один уровень субпроектов?** Рекомендация — да;
   глубже — namespaces внутри субпроекта.
5. **Оверлей поверх нескольких целевых систем**: субпроект = целевая
   система (`reality` субпроекта — её ключ из `external`)? Рекомендация
   — да.
6. **Модули на часть**: может ли модуль быть подключён только в одном
   субпроекте (например, `manuals` только у `billing`)? Рекомендация —
   да, через список субпроектов в manifest'е модуля; по умолчанию — во
   всех.

## Что меняется при реализации

- Новый модуль `subprojects` и skill `subprojects`; ядро контракта v3 не
  меняется, кроме того, что `provides.extends` получает цели `project`
  (корневой `context/project.yml`) и `intents`.
- Добавить / убрать субпроект — протокол skill `subprojects`;
  подключение и отключение модуля — `contract-setup`, как у всех.
- Схемы: `project.yml`, manifest (список субпроектов), `intents`
  (`scope`).
- harness: `context index` по субпроектам, `review` и роль docs-keeper
  с `scope`, `context for`.
- skills `docs-keeper`, `workflow`: `scope` в намерениях.

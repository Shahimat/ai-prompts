# Как добавить промпт

## Главный принцип

Промпт пишется так, будто ты ставишь задачу умному коллеге, а не настраиваешь
скрипт. Никаких плейсхолдеров `{{...}}`, никаких пошаговых инструкций для
очевидных вещей. Если агенту чего-то не хватит — он сам спросит.

## Формат файла

Один промпт — один `.md` файл в подходящей категории `prompts/<категория>/`.
Имя файла — короткое, на латинице, kebab-case: `code-review.md`,
`refactor-legacy.md`.

В начале файла — YAML-frontmatter:

```markdown
---
key: code-review-changes
kind: prompt
title: Код-ревью текущих изменений
tags: [code-review, git]
use_case: Когда нужно получить вдумчивый разбор изменений в ветке перед PR.
---

Текст промпта...
```

Поля:

- `key` — стабильный kebab-case идентификатор. Один раз выбран — не
  переименовываем без согласования: на него ссылаются manifest'ы
  подключённых проектов и `prompts/index.yml`.
- `kind` — тип промпта, обязательное поле. Значения:
  - `prompt` — обычный самостоятельный промпт;
  - `contract` — базовый контракт для развёртывания проектной
    документации (например, `agent-operational-contract-v2`);
  - `pattern` — переиспользуемый блок правил в `patterns/` (обычно
    заполняется в самих паттернах, не в промптах);
  - `module` — расширение над базой, живёт в `prompts/modules/` (см.
    ниже).
- `title` — человекочитаемое название.
- `tags` — массив тегов для поиска.
- `use_case` — одна строка: в какой ситуации этот промпт полезен.

## Что писать в теле промпта

- **Цель** — чего хотим в итоге.
- **Рамки** — что важно учесть, что нельзя делать.
- **Поведение при нехватке контекста** — явно скажи агенту задавать вопросы,
  а не выдумывать.

Чего **не** надо:

- Жёстких шагов «сначала сделай X, потом Y» — пусть агент сам решает.
- Плейсхолдеров и шаблонных переменных.
- Дублирования того, что любой нормальный агент и так знает.

## Паттерны промптов

В `patterns/` живут переиспользуемые блоки правил (например,
`source-sync` — механизм синхронизации промпта с источником через
индекс и SHA-256 checkpoint). Промпт может декларировать применённые
паттерны в frontmatter:

```yaml
patterns: [source-sync]
```

Содержимое соответствующего паттерна инлайнится в тело промпта как
отдельный раздел (гибрид «декларация + inline-копия»).

При добавлении или правке промпта — посмотри `patterns/README.md` и
список файлов в `patterns/`, оцени применимость. Правила процесса для
агента — в `CLAUDE.md`.

## Модули расширения

В `prompts/modules/` живут модули — надстройки над конкретной базой
(обычно над контрактом), опционально подключаемые проектом-потребителем.
В отличие от паттернов, модули не инлайнятся в базу, а применяются
самостоятельно.

Обязательный frontmatter модуля:

```yaml
---
key: <kebab-case>
kind: module
applicable_to: [<base-key>, ...]
patterns: [source-sync]
title: ...
use_case: ...
tags: [...]
---
```

Правило WRITE > UPDATE: модуль только добавляет новые слои, файлы,
правила; редактировать базу нельзя. Полная спецификация — в
`prompts/modules/README.md`.

## Индекс промптов

`prompts/index.yml` — сгенерированный каталог всех промптов репозитория
(ключ, путь, raw-URL, SHA-256, `applicable_to`). Проекты-потребители
пользуются им для быстрой синхронизации через `source-sync`.

**После правки любого промпта, паттерна или модуля обязательно запусти:**

```bash
./scripts/build-index.sh
```

Скрипт пересобирает `prompts/index.yml`. Обновлённый индекс включай в
тот же коммит, что и правку. CI (`scripts/check-index.sh`) сверяет
консистентность и валит билд при рассинхроне.

## Pull request

1. Форкни репо.
2. Добавь файл в нужную категорию (`prompts/<category>/` для обычных
   промптов, `prompts/modules/` для модулей).
3. Запусти `./scripts/build-index.sh`, добавь `prompts/index.yml` в
   коммит.
4. Открой PR с коротким описанием: что за промпт/модуль и зачем.

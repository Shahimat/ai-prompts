# Как добавить промпт

## Главный принцип

Промпт пишется так, будто ты ставишь задачу умному коллеге, а не настраиваешь
скрипт. Никаких плейсхолдеров `{{...}}`, никаких пошаговых инструкций для
очевидных вещей. Если агенту чего-то не хватит — он сам спросит.

## Формат файла

Один промпт — один `.md` файл в подходящей категории `prompts/<категория>/`.
Имя файла — короткое, на латинице, kebab-case: `code-review.md`,
`refactor-legacy.md`.

В начале файла — YAML-frontmatter:

```markdown
---
key: code-review-changes
kind: prompt
title: Код-ревью текущих изменений
tags: [code-review, git]
use_case: Когда нужно получить вдумчивый разбор изменений в ветке перед PR.
---

Текст промпта...
```

Поля:

- `key` — стабильный kebab-case идентификатор. Один раз выбран — не
  переименовываем без согласования: на него ссылаются manifest'ы
  подключённых проектов и `prompts/index.yml`.
- `kind` — тип промпта, обязательное поле. Значения:
  - `prompt` — обычный самостоятельный промпт;
  - `contract` — базовый контракт для развёртывания проектной
    документации (например, `agent-operational-contract-v2`);
  - `pattern` — переиспользуемый блок правил в `patterns/` (обычно
    заполняется в самих паттернах, не в промптах);
  - `module` — расширение над базой, живёт в `prompts/modules/` (см.
    ниже).
- `title` — человекочитаемое название.
- `tags` — массив тегов для поиска.
- `use_case` — одна строка: в какой ситуации этот промпт полезен.

## Что писать в теле промпта

- **Цель** — чего хотим в итоге.
- **Рамки** — что важно учесть, что нельзя делать.
- **Поведение при нехватке контекста** — явно скажи агенту задавать вопросы,
  а не выдумывать.

Чего **не** надо:

- Жёстких шагов «сначала сделай X, потом Y» — пусть агент сам решает.
- Плейсхолдеров и шаблонных переменных.
- Дублирования того, что любой нормальный агент и так знает.

## Паттерны промптов

В `patterns/` живут переиспользуемые блоки правил (например,
`source-sync` — механизм синхронизации промпта с источником через
индекс и SHA-256 checkpoint). Промпт может декларировать применённые
паттерны в frontmatter:

```yaml
patterns: [source-sync]
```

Содержимое соответствующего паттерна инлайнится в тело промпта как
отдельный раздел (гибрид «декларация + inline-копия»).

При добавлении или правке промпта — посмотри `patterns/README.md` и
список файлов в `patterns/`, оцени применимость. Правила процесса для
агента — в `AGENTS.md`. Контракт v2.1 и его skills паттерны не применяют:
их правила живут в skills.

## Модули расширения

В `prompts/modules/` живут модули — надстройки над конкретной базой
(обычно над контрактом), опционально подключаемые проектом-потребителем.
В отличие от паттернов, модули не инлайнятся в базу, а применяются
самостоятельно.

Обязательный frontmatter модуля:

```yaml
---
key: <kebab-case>
kind: module
applicable_to: [<base-key>, ...]
patterns: [source-sync]
title: ...
use_case: ...
tags: [...]
---
```

Правило WRITE > UPDATE: модуль только добавляет новые слои, файлы,
правила; редактировать базу нельзя. Модуль-возможность ядра v3
дополнительно объявляет блок `feature` (строка для чеклиста, `default`,
`requires`, `conflicts`, `asks`). Полная спецификация — в
`prompts/modules/README.md`.

## Skills и субагенты

Канон skill в источнике — `skills/<name>/SKILL.md` и необходимые файлы
того же каталога; во frontmatter только `name` (совпадает с каталогом) и
однострочный `description` (что делает и когда загружать). Контракт или
модуль, который поставляет skill, объявляет его в `provides.skills`;
для обязательной поставки v2 — сам контракт v2. Файлы skill включаются
в `prompts/index.yml` штатной пересборкой индекса, без второй копии канона.
Контракт v2.1 (`agent-operational-contract-v2-1`) ставит skills без модулей
и паттернов: обязательный комплект — в его `provides.skills`, необязательные
подключаются из каталога по `source-sync`.

Поставляемые субагенты живут в `agents/<name>.md`: frontmatter `name`,
`description`, `model`, `tools`, тело — инструкция субагента. Привязки
skills в v3 задаются его реестром, не файлом роли. Это source products,
не обязательные локальные роли. В самом ai-prompts канон skills —
`skills/`, discovery — `./skills`; копий `.agents/skills` не создаём.
До авторской правки skill загрузи `skill-builder`.

## Пресеты

`presets/<key>.yml` — готовый набор возможностей под тип проекта:

```yaml
key: <совпадает с именем файла>
title: <одна строка для вопроса «пресет или вручную»>
contract: agent-operational-contract-v3
modules:
  - key: <модуль>
    answers: # дефолты для feature.asks модуля
      <ask-key>: <значение или список>
```

`index build` падает, если контракта или модуля нет в индексе или
модуль не применим к контракту. Если skill содержит inline-копию паттерна — правится
вместе с паттерном.

## Индекс промптов

`prompts/index.yml` — сгенерированный каталог всех промптов репозитория
(ключ, путь, raw-URL, SHA-256, `applicable_to`). Проекты-потребители
пользуются им для быстрой синхронизации через `source-sync`.

**После правки любого промпта, паттерна или модуля обязательно запусти:**

```bash
npm run index:build
```

Команда пересобирает `prompts/index.yml`. Обновлённый индекс включай в
тот же коммит, что и правку. CI (`npm run index:check`) сверяет
консистентность и валит билд при рассинхроне.

Для разработки нужен Node ≥24; перед первым запуском —
`npm ci && npm run build`. Пересборка индекса — обычная команда
репозитория, не обязательный локальный ролевой процесс или OC3 refresh.

## Проверки репозитория

`npm run ci` выполняет format/build/models/typecheck/lint/packages/index;
канон команд — `package.json`. Package tests, memory и expectations
в этот CI не входят. Целевые Node tests repo-native скрипта моделей и
нужные package tests запускаются отдельно по эффекту изменения.
Свежий PASS общего CI не выводится из старого лога или targeted tests.
Локальная схема — standalone v2; код и документацию ведёт основная сессия.
Поставляемые v3 продукты и их схемы проверяются в собственном scope.

## Продуктовый verification-контракт пакетов

Standalone/prepublish preparation contract и границы проверенного для
ai-core — в [README пакета](packages/ai-core/README.md#тестирование-исходников).

Продуктовый proof baseline не отменяет preparation, freshness или
current-run single-flight. Reuse ограничен
reviewed bounded guards и registered changelog; arbitrary Vitest/CI не
объявлены cacheable. Unknown ordinary context исполняет весь selected scope
run-only с реальным exit; incomplete repeat требует нового run.
Default tests/report/lint/CI не вызывают judge при miss, force не даёт это
право. Legacy-needs-review/nonzero не исправляется ручным trusted upgrade.
Полный [контракт верификации](design/incremental-verification.md) отделяет
source/conformance evidence от actual full CI PASS; warm сохраняет build/hashing.

## Pull request

1. Форкни репо.
2. Добавь файл в нужную категорию (`prompts/<category>/` для обычных
   промптов, `prompts/modules/` для модулей).
3. Запусти `npm run index:build`, добавь `prompts/index.yml` в
   коммит.
4. Открой PR с коротким описанием: что за промпт/модуль и зачем.

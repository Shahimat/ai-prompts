# docs-keeper

Единственный путь записи в проектную документацию. Основной агент
передаёт **намерения**, docs-keeper раскладывает их по слоям, проверяет
и отчитывается.

## Вход: намерения

<!-- expect:docs-keeper-intents -->
```yaml
- kind: decision | fact | rule | behavior-change | task | manual
  summary: <одна строка>
  evidence: <файл, команда, коммит — чем подтверждено>
```

- `decision` — принятое решение: CHANGELOG (если проходит критерий) +
  слой, который оно меняет;
- `fact` — как устроено сейчас: слой возможности (например, entity) или
  `context/project.yml`;
- `rule` — договорённость, как работаем: `context/conventions/<key>.yml`;
- `behavior-change` — изменилось ожидаемое поведение: слой возможности
  (например, behavior + `verified`);
- `task` — работа на будущее: очередь работы (skill `goals`, если
  подключён), иначе — сказать пользователю, куда записать;
- `manual` — ручная процедура: слой manuals, если подключён.

Без `evidence` факт не записывается как проверенный: пометь `unknown`
или спроси.

`reason`, `why`, `evidence` и `summary` записи берутся только из
переданного `evidence`: следствие, которого в нём нет (результат прогона,
которого не было, — «без X не работало»), не дописывается. Для мотива
данных мало — короткий мотив без утверждений о проверках.

В harness намерения проверяются схемой `intents` (JSON или YAML: тот же
список или объект `{intents: [...]}`) и хранятся в сессии процесса, а
не в файле проекта.
<!-- /expect:docs-keeper-intents -->

Виды намерений модулей — по их skills: например, analysis — `source`,
`claim`, `position`, `post`, `analysis`, `tension`.

## Ответственные за запись

<!-- expect:docs-owners -->
У каждой записи в проектную документацию один ответственный.

<!-- expect:skill-runs -->
| Что | Кто пишет |
| --- | --- |
| `context/project.yml` | docs-keeper |
| `context/conventions/` | docs-keeper |
| `CHANGELOG.md` | docs-keeper |
| слои ядра в `docs/` и слои модулей (`provides.layers`) | docs-keeper |
| `context/.delta/` — создание и правка | docs-keeper |
| `context/.delta/` — удаление после приёмки | `ai delta close`; шаг `close` harness `docs-delta`, без harness — docs-keeper |
| `context/index.yml` | `ai context index`; шаг `verify` harness `docs-delta` |
| адаптеры (`CLAUDE.md`, `.claude/`, `.codex/`) | `ai adapters sync`; шаг `verify` harness `docs-delta` |
<!-- /expect:skill-runs -->

Основная сессия в документацию не пишет.
<!-- /expect:docs-owners -->

## Дельта

<!-- expect:docs-delta -->
Документация — система ожиданий: каждый факт, правило, позиция уже
чему-то соответствует. Тихо удалить или ослабить знание — потерять его.
Поэтому намерения сначала становятся дельтой —
`context/.delta/<имя>.yml`, временными ожиданиями к целевому состоянию
документации:

```yaml
summary: <что меняем, одной строкой>
source: <откуда — задача, разбор или анализ>
items:
  - op: add                        # add | refine | revise
    kind: rule                     # вид намерения
    target: naming                 # путь от корня или id
    summary: <какое знание появится>
    evidence: <чем подтверждено>
  - op: revise
    kind: rule
    target: context/conventions/branches.yml
    summary: <каким знание станет>
    evidence: <чем подтверждено>
    was: <каким было>
    why: <почему пересмотрено>
```

<!-- expect:skill-runs -->
<!-- metadata.runs: docs-delta -->
С harness запись ведёт `ai docs-delta start --name <имя>`: он
выдаёт задание — шаги 1–4 ниже — и короткий id сессии; после них
`ai docs-delta open <id>` проверяет, ревьюит и закрывает дельту
(шаги 5–6). С `--file <намерения | ->` шаги 1–4 выполняет роль
`docs-keeper` сама, без задания агенту. Ревью — роль `judge`: ищет
противоречия правки с остальной документацией, цитаты сверяются
дословно. Провал проверки или найденное противоречие возвращает задание
с нарушениями, после трёх провалов процесс останавливается — это «не
прошло» в отчёте.
<!-- /expect:skill-runs -->

1. Собери дельту из намерений. Сверь каждый пункт с текущей
   документацией: новое знание — `add`, совместимое уточнение —
   `refine`, удаление или изменение существующего — `revise` с `was` и
   `why`. Пункт дельты — всегда правка файла документации:
   - решение «ничего не менять» — не пункт, а строка отчёта (принятое
     решение с тегом журнала — пункт `add` в `CHANGELOG.md`);
   - пункт, которому нужно «да» пользователя, в дельту не входит:
     вопрос в `questions` отчёта, после «да» — новая сессия;
   - лимиты схемы: `summary` дельты и пункта — одна строка до 200
     символов, `target` — путь от корня или id (якорь `#поле`
     допустим, сверяется по файлу); проверь до передачи на приёмку.
2. `add` и `refine` вниманием пользователя не требуют — строка в отчёте.
3. `revise` работу не блокирует: он объявлен в дельте, попадает в отчёт
   и в тело сообщения коммита. Ошибочный
   пересмотр откатывается сценарием `recover` (skill `workflow`).
4. Примени пункты по правилам слоёв.
5. Приёмка: пункты дельты выполнены, прежнее знание без `revise` не
   нарушено, производные файлы пересобраны, проверки чисты — с harness
   это шаг `verify` процесса; противоречий с остальной документацией
   нет — с harness это шаг `review` (роль `judge`).
6. После приёмки дельта удаляется, её `revise` до коммита
   пользователя помнит `context/.delta/.accepted.json` — следующая
   сессия не дублирует их; строки `revise` — в отчёт:
   <!-- expect:skill-runs -->
   с harness — шаг `close` процесса, `ai delta close`.
   <!-- /expect:skill-runs -->

Без harness — та же сверка вручную по `git diff HEAD` слоёв, дельту
удаляет docs-keeper. Дельта — рабочий файл docs-keeper: в маршруты и
`context/index.yml` она не входит, основная сессия её не читает.
<!-- /expect:docs-delta -->

## Правила слоёв

Слои ядра — ниже. Слои подключённых возможностей: прочитай
`context/modules/*.yml`, для каждого модуля загрузи skills из
`provides.skills` и пиши по их правилам.

Поля, которые модуль добавляет в чужие слои (`provides.extends`),
пишутся по правилам skill этого модуля. Поле, не объявленное ни слоем,
ни чьим-то `extends`, — не заводи: это сигнал, что нужен модуль или
convention.

### `context/project.yml`

Реквизиты и константы: имя, `summary`, стек, `namespaces`, `external`,
`sync`. Компактный YAML, без narrative. Новый namespace — только с «да»
пользователя.

### `context/conventions/<key>.yml`

- одно правило — один файл; поля `key`, `summary`, `rule`;
- `key` — kebab-case, совпадает с именем файла, не переименовывается;
- `summary` — одна строка: по ней агент находит правило;
- в `rule` — только принятое правило, без разбора отклонённых
  альтернатив; нужна мотивация — одна строка `reason:`;
- правила контракта и модулей сюда не копируются — они в skills.

### `CHANGELOG.md`

<!-- expect:module-tags -->
Журнал решений: «когда» и «почему», не «как сейчас».

```
- YYYY-MM-DD · [tag] <суть> · <почему>
```

- строка до 120 символов, включая дату и маркер;
- ровно три части через ` · `;
- `tag`: `arch` (архитектура), `stack` (выбор или отказ от
  технологии), `dep` (внешняя зависимость, провайдер, major-версия),
  `milestone` (веха: релиз, закрытая миграция, новый namespace) — плюс
  теги из `provides.changelog_tags` подключённых модулей, со смыслом
  из их skills;
- тег не подбирается — запись не для журнала;
- тест: поможет ли строка через год ответить «почему»? Нет — это git
  log;
- не попадают: багфиксы, рефакторинг, перекладка документации,
  конфиги, списки доменов и адресов, ход расследования, WIP;
- свежее сверху, дата — день принятия решения;
- не влезает в строку — уровень абстракции не тот: детали — в слой
  или в описание коммита.
<!-- /expect:module-tags -->

## Правило полноты

Новая сущность, правило или процедура появились — файл заводится сразу,
со всеми ссылками. Запись не закончена, пока:

- обновлены связанные файлы (ссылки в обе стороны, если слой их
  требует);
- выполнены правила слоёв подключённых возможностей;
- решение, проходящее критерий, записано в CHANGELOG;
- проверки чисты: с harness — `verify` процесса, иначе — ручная сверка
  по тем же правилам;
- неочевидные изменения существующих правил подтверждены пользователем.

Частичная запись и молча сохранённое противоречие — ошибка.

## Противоречия

Нашёл противоречие между документами или между документом и кодом — не
сохраняй молча: одной строкой назови конфликт, предложи разрешение,
дождись решения. Документ и источник реальности (`reality` в
`context/project.yml`) расходятся — прав источник.

## Чего не делать

<!-- expect:docs-readonly -->
- документацию пишет только субагент docs-keeper; основная сессия её
  только читает и передаёт намерения;
- docs-keeper меняет только слои документации проекта — код, тесты,
  конфиги сборки не трогает;
- не править сгенерированные файлы (`context/index.yml`, адаптеры в
  `.claude/`, `.codex/`, `CLAUDE.md`) — при подключённом harness их меняет
  только harness: правится источник, затем генерация;
<!-- /expect:docs-readonly -->
<!-- expect:docs-secrets -->
- не записывать секреты — ключи, токены, пароли, приватные ключи: в
  документации — указатель на хранилище (`vault:…`, переменная
  окружения, секрет CI), не значение; намерение с секретом — отказ и
  вопрос. При подключённом harness это ловит проверка `secrets` в
  `verify` процесса;
<!-- /expect:docs-secrets -->
- не писать в memory агента и в файлы вне репозитория;
- не дублировать факт в двух слоях: уместен в двух — границы проведены
  неверно, подними вопрос;
- не создавать, не переносить, не удалять без «да» основного агента
  (а он — пользователя).

## Отчёт

<!-- expect:docs-keeper-report -->
Отчёт основной сессии — не длиннее 10 строк:

```
изменено: <файл> — <что>
revise: <цель>: было «…» → <стало>; почему: <…>
не прошло: <проверка> — <почему>
вопросы: <что решает пользователь>
```

Основная сессия показывает его пользователю как есть, строки `revise`
идут в тело сообщения коммита.
<!-- /expect:docs-keeper-report -->

## Язык

Содержимое — на русском. Английский — в `key`, `id`, `namespace`,
ключах YAML, именах файлов и устоявшихся терминах.

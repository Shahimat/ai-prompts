# docs-keeper

Единственный путь записи в проектную документацию. Основной агент
передаёт **намерения**, docs-keeper раскладывает их по слоям, проверяет
и отчитывается.

## Вход: намерения

```yaml
- kind: decision | fact | rule | behavior-change | task | manual
  summary: <одна строка>
  evidence: <файл, команда, коммит — чем подтверждено>
```

- `decision` — принятое решение: CHANGELOG (если проходит критерий) +
  слой, который оно меняет;
- `fact` — как устроено сейчас: слой возможности (например, entity) или
  `context/project.yml`;
- `rule` — договорённость, как работаем: `context/conventions/<key>.yml`;
- `behavior-change` — изменилось ожидаемое поведение: слой возможности
  (например, behavior + `verified`);
- `task` — работа на будущее: очередь работы (skill `goals`, если
  подключён), иначе — сказать пользователю, куда записать;
- `manual` — ручная процедура: слой manuals, если подключён.

Без `evidence` факт не записывается как проверенный: пометь `unknown`
или спроси.

## Правила слоёв

Слои ядра — ниже. Слои подключённых возможностей: прочитай
`context/modules/*.yml`, для каждого модуля загрузи skills из
`provides.skills` и пиши по их правилам.

Поля, которые модуль добавляет в чужие слои (`provides.extends`),
пишутся по правилам skill этого модуля. Поле, не объявленное ни слоем,
ни чьим-то `extends`, — не заводи: это сигнал, что нужен модуль или
convention.

### `context/project.yml`

Реквизиты и константы: имя, `summary`, стек, `namespaces`, `external`,
`sync`. Компактный YAML, без narrative. Новый namespace — только с «да»
пользователя.

### `context/conventions/<key>.yml`

- одно правило — один файл; поля `key`, `summary`, `rule`;
- `key` — kebab-case, совпадает с именем файла, не переименовывается;
- `summary` — одна строка: по ней агент находит правило;
- в `rule` — только принятое правило, без разбора отклонённых
  альтернатив; нужна мотивация — одна строка `reason:`;
- правила контракта и модулей сюда не копируются — они в skills.

### `CHANGELOG.md`

<!-- expect:module-tags -->
Журнал решений: «когда» и «почему», не «как сейчас».

```
- YYYY-MM-DD · [tag] <суть> · <почему>
```

- строка до 120 символов, включая дату и маркер;
- ровно три части через ` · `;
- `tag`: `arch` (архитектура), `stack` (выбор или отказ от
  технологии), `dep` (внешняя зависимость, провайдер, major-версия),
  `milestone` (веха: релиз, закрытая миграция, новый namespace) — плюс
  теги из `provides.changelog_tags` подключённых модулей, со смыслом
  из их skills;
- тег не подбирается — запись не для журнала;
- тест: поможет ли строка через год ответить «почему»? Нет — это git
  log;
- не попадают: багфиксы, рефакторинг, перекладка документации,
  конфиги, списки доменов и адресов, ход расследования, WIP;
- свежее сверху, дата — день принятия решения;
- не влезает в строку — уровень абстракции не тот: детали — в слой
  или в описание коммита.
<!-- /expect:module-tags -->

## Правило полноты

Новая сущность, правило или процедура появились — файл заводится сразу,
со всеми ссылками. Запись не закончена, пока:

- обновлены связанные файлы (ссылки в обе стороны, если слой их
  требует);
- выполнены правила слоёв подключённых возможностей;
- решение, проходящее критерий, записано в CHANGELOG;
- `harness check` чист, если подключён harness (иначе — ручная сверка
  по тем же правилам);
- неочевидные изменения существующих правил подтверждены пользователем.

Частичная запись и молча сохранённое противоречие — ошибка.

## Противоречия

Нашёл противоречие между документами или между документом и кодом — не
сохраняй молча: одной строкой назови конфликт, предложи разрешение,
дождись решения. Документ и источник реальности (`reality` в
`context/project.yml`) расходятся — прав источник.

## Чего не делать

<!-- expect:docs-readonly -->
- документацию пишет только субагент docs-keeper; основная сессия её
  только читает и передаёт намерения;
- docs-keeper меняет только слои документации проекта — код, тесты,
  конфиги сборки не трогает;
- не править сгенерированные файлы (`context/index.yml`, адаптеры в
  `.claude/`, `.codex/`, `CLAUDE.md`) — при подключённом harness их меняет
  только harness: правится источник, затем генерация;
<!-- /expect:docs-readonly -->
- не писать в memory агента и в файлы вне репозитория;
- не дублировать факт в двух слоях: уместен в двух — границы проведены
  неверно, подними вопрос;
- не создавать, не переносить, не удалять без «да» основного агента
  (а он — пользователя).

## Отчёт

```
изменено: <файл> — <что>
не прошло: <проверка> — <почему>
вопросы: <что решает пользователь>
```

Содержимое — на русском. Английский — в `key`, `id`, `namespace`,

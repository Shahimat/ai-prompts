# Установка и миграция документации v2

Цель — полностью действующий самостоятельный v2: открытое проектное знание
в индексируемых переносимых файлах, одна действующая точка входа `AGENTS.md`,
YAML-очередь `context/views/`. Роли, CLI, сборка и переход на v3 не требуются.
Схемы и обязательные принципы берутся из проверенного контракта v2,
а не из протокола установки v3. Этот файл не отчёт о конкретном переходе.

## Общие границы

Не создавай, не переноси и не удаляй ничего без явного «да» на объём.
Собственные правила, RFC-процессы, имена и структуры проекта не заменяются
молча: выяви расхождения, предложи согласование с trade-off, дождись решения.
Нет явных соглашений — используй дефолт v2, но согласуй ключевые решения
до создания файлов. Необходимое выравнивание документации внутри одобренного
тикета не требует отдельного «запомни» или остановок между пунктами.

Согласованный план охватывает весь переход: знания, структуру, очередь,
ссылки, сопровождающие skills и действующие настройки агента. Нужные
разрешения и человеческие действия выявляй при планировании, не после
объявления готовности. Новое решение или расширение объёма согласуй отдельно.

К плану применяй «Единство источника правды» из раздела контракта «Куда
записываются уточнения по проекту» (в установленном проекте — convention
`project-knowledge`). При классификации определи владельцев значений и
инструкций; существующие конфиги и схемы не превращай в дубли в слоях.

Не добавляй разработку, аудит или отрицательные пробы отдельного memory-guard
в критерии, очередь или отчёт о миграции. Открытая документация действует
сразу; отсутствие защиты не разрешает memory как параллельный слой.
Сохраняй действующие независимые запреты, не обходи их и не меняй глобальные
настройки без отдельного разрешения.

## Greenfield

Документации нет или есть только пустые заготовки:

1. Прочитай известные точки входа и пути документации. Отсутствие документов
   не разрешает сначала обойти весь код: обозначь пробел, затем исследуй
   только нужные фрагменты для первичного наполнения.
2. Предложи структуру по v2 и согласуй объём. Не создавай пустые manuals,
   программы, модули или отчётные файлы только ради полноты дерева.
3. Поставь объявленный контрактом комплект skills по его bootstrap.
   Проверка файлов и SHA — skill `source-sync`; не читай все инструкции.
4. Разверни нужные слои по схемам контракта, настрой индекс и одну точку
   входа. Все существенные факты и правила сразу фиксируй в проекте.
5. Для очереди загрузи `goals`, для настоящей человеческой процедуры —
   `manuals`; для подключения опционального модуля — `source-sync`.
6. Проверь полный критерий готовности ниже, затем сохрани итоговые sync-SHA.

## Brownfield

Документация уже есть: `AGENTS.md`, wiki-выгрузки, свои YAML/JSON, tickets,
RFC, длинные README или ad-hoc markdown. Сначала инвентаризация, затем план;
не переписывай молча. Если режим неясен — уточни.

### Инвентаризация

Прочитай существующие артефакты:

- `AGENTS.md`, `README.md`, известные `docs/` и `context/`;
- wiki-выгрузки, `NOTES.md`, `ARCHITECTURE.md`, `SPEC.md`;
- собственные схемы, tickets / RFC / ADR / changelog, ad-hoc markdown;
- действующие проектные настройки агента, подключения прежнего контракта,
  сгенерированные роли и адаптеры, если они есть.

Верни короткую карту: «файл X — спецификация Y», «файл Z — ручная
процедура», «файл W — устаревший draft». Пока ничего не переписывай.

### Классификация и матрица соответствия

Для каждого куска предложи место:

- человеческая процедура — `docs/manuals/<name>.md`, не отчёт;
- спецификация — `docs/entities/<id>.yml`;
- поведение и проверка — `docs/behavior/<id>.yml`;
- договорённость — `context/conventions/<key>.yml`;
- реквизиты — `context/project.yml`;
- оставшаяся работа — подходящая цель или программа `context/views/`;
- крупное принятое решение — `CHANGELOG.md` по его критерию;
- шум — согласованное удаление или архив.

Покажи списком, не таблицей: «существующий файл → целевой слой → что
выигрываем и теряем». Спорное размещение в двух слоях требует границы,
а не копии. Manuals перерабатывай по `manuals`: сохрани существенные факты,
реальные ручные шаги оставь процедурой, отчётные заглушки и ссылки убери
в согласованном объёме. Не переноси отчёт целиком в новый каталог.

### Расхождения и конфликты

Перечисли противоречия соглашений проекта целевой модели и вариант разрешения
каждого с trade-off. Проверь собственные tickets / `active.todo` / roadmap
против YAML-очереди, BDD без `verified`, монолитные conventions, обязательные
RFC для мелких решений, README как второй набор агентских правил.

Полные типовые правила, вынесенные в skills, не копируй в workflow или
conventions. В прежних `goals.yml` / `goal-consistency.yml` отдели копии
поставки от проектных дополнений: дополнения сохрани в атомарных conventions
с индексом, удаление подтверждённых дублей включи в согласованный план.
Не удаляй пользовательские правила только из-за совпадения имени файла.

### План поэтапного перехода

Разбей переход на самостоятельно ценные тикеты по правилам v2: один тикет —
один коммит, внутри — последовательный чеклист по типам, не фазы-коммиты.
Между тикетами проект остаётся связным и рабочим. Типовая последовательность:

1. Ввести `context/` без разрушения существующих слоёв и поставить все
   skills из `provides.skills`; конфликт имён разрешить в плане.
2. Перенести entity и behavior в `docs/entities/` и `docs/behavior/`.
   Сохранить знания и подтверждённое происхождение `verified`; недостающее
   подтверждение не выдумывать.
3. Перенести только настоящие ручные процедуры по skill `manuals`, без
   отчётных заглушек.
4. Привести документы к схемам v2, проверить поля, двусторонние ссылки и
   индекс. Миграция не требует продуктового аудита или порога `verified: true`.
5. Каждую живую legacy-задачу разложить по целям и программам через `goals`.
   Нет подходящей цели — предложить новую. Прогнать `goal-consistency` по
   всему множеству; legacy-очередь удалять только после полного маппинга.
   Закрытые задачи не переносить: история — git, крупные решения — CHANGELOG.
6. Привести действующие проектные настройки к v2. Вывести из использования
   старую точку входа, обязательный ролевой маршрут и ненужные подключения
   прежнего контракта; архив не должен управлять работой как второй канон.
   Не удалить новый комплект skills вместе со старой ролевой обвязкой.
   Независимые глобальные guards, MCP и чужие настройки не удалять из-за
   смены контракта; необходимые внешние изменения согласовать отдельно.
7. Убрать согласованный legacy без потери знаний, обновить README, индекс,
   ссылки. После проверки полного перехода сохранить `sync.contract.key`,
   SHA источников и всех skills в `sync.contract.parts.skills`.

Точный набор тикетов зависит от проекта. До перехода согласуй весь набор
и объём; внутри тикета не запрашивай «ок» после каждого пункта. Опасное,
спорное, неожиданное или новое решение — стоп. В конце тикета — короткий
отчёт, проверки и одно английское сообщение коммита; дальше — по выбранному
режиму работы. Git/arc-запись выполняет пользователь.

### Миграция точки входа отдельно

Если входом служит старое имя файла или другая обвязка, предложи отдельный
тикет: перенести маршрутизацию в `AGENTS.md`, распределить содержание по
слоям без потери знания, заменить self-references и ссылки в индексе.
Проверь нативное чтение `AGENTS.md` и обязательный маршрут до кода.
Не оставляй правил только в точке входа или вторую действующую копию.
Sync-checkpoint обновляй только для реально завершённого объёма: замена
одного входного файла не закрывает полный переход и не разрешает молча
мигрировать остальное.

### Что не мигрирует

Внешние трекеры/доски, живые wiki, чужие репозитории/зависимости,
деплой-конфиги и infrastructure-as-code со своей жизнью, внешние release
notes — указатели в `context/project.yml`, не копии и не новый журнал.
Но существенные собственные выводы, решения и ограничения фиксируются
в документации проекта с происхождением: одна внешняя ссылка их не заменяет.

## Проверки и критерий полного перехода

Выбирай проверки по эффекту: структура, схемы, ссылки, индекс, очередь,
действующие инструкции/подключения и файлы skills. Если продуктовый код,
его конфигурация и поведение не менялись, повторные продуктовые тесты из
миграции документации не следуют. Если затронуты — проверь их в составе
изменения. Состояние проверки продукта не подменяет готовность перехода.

Переход завершён, только когда:

- существенные знания, факты, решения и правила явно разложены по слоям,
  доступны через индекс и переносятся с проектом без прежней личной среды;
  нет memory или неиндексируемых заметок как параллельного слоя;
- обязательные документы, поля и двусторонние ссылки корректны; индекс
  актуален, `verified` отражает реальные подтверждения, не заданный процент;
- skills и инструментальные файлы не стали вторым каноном проектного знания;
  типовые инструкции не продублированы целиком в conventions/workflow;
- владельцы определений и их потребители согласованы с «Единством источника
  правды»; документирование значений не подменено их ручным размножением;
- README ведёт на новую структуру, conventions атомарны;
- действующие инструкции, настройки, подключения и sync соответствуют v2,
  прежний контракт больше не управляет работой;
- весь комплект `provides.skills` установлен, доступен по триггерам,
  файлы сверены по SHA, checkpoints сохранены после полной поставки;
- manuals — только нужные человеческие процедуры, без миграционных отчётов,
  guard-аудитов и отчётных заглушек;
- живые задачи разложены по целям/программам, `goal-consistency` проходит,
  старый плоский `active.todo` / roadmap не остался параллельной очередью;
- выполнены все обязательные пункты перехода, не оставлена часть,
  без которой v2 ещё не действует целиком.

До этого доводи саму миграцию; при реальном блокере назови нужное решение
или действие. Нельзя объявить её завершённой с оговоркой об обязательной
приёмке «потом».

## Итог

Кратко подтверди полный переход и существенные изменения. Дальше проект
работает по v2 без постоянного статусного хвоста о защите и без перечисления
неприменимых продуктовых проверок. Реальную ошибку обязательной проверки
исправь либо назови блокер, не скрывай.

Не создавай отдельный отчёт о переходе в manuals или другом каталоге.
Устойчивые знания уже в слоях; завершённое крупное решение — одна запись
в CHANGELOG по его обычному правилу, без журнала прогонов.

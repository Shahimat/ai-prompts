# Установка и миграция документации v2.1

Цель — полностью действующий контракт v2.1: открытое проектное знание в `.oc/`,
одна действующая точка входа `AGENTS.md`, правила в skills, факты в структурах
данных со схемами. Роли, harness и runtime v3 не требуются; из инструментов
ставится `@shahimat/cli` с командой `ai data check`. Схемы и принципы берутся
из проверенного контракта v2.1, а не из протоколов v2 или v3. Этот файл —
процедура, не отчёт о конкретном переходе.

## Общие границы

Не создавай, не переноси и не удаляй ничего без явного «да» на объём.
Собственные правила, RFC-процессы, имена и структуры проекта не заменяются
молча: выяви расхождения, предложи согласование с trade-off, дождись решения.
Нет явных соглашений — используй дефолт контракта, но согласуй ключевые решения
до создания файлов. Необходимое выравнивание документации внутри одобренного
тикета не требует отдельного «запомни» или остановок между пунктами.

Согласованный план охватывает весь переход: знания, структуру, очередь, ссылки,
skills и действующие настройки агента. Нужные разрешения и человеческие
действия выявляй при планировании, не после объявления готовности. Новое
решение или расширение объёма согласуй отдельно.

К плану применяй правила записи skill `project-docs`: при классификации
определи владельцев значений и инструкций; существующие конфиги и схемы не
превращай в дубли.

Переход на v2.1 — по одному проекту за раз, начиная с некритичного. Контракт
должен быть стабилен в источнике: не переводи проект, от которого зависят
остальные, первым. Между тикетами проект остаётся связным и рабочим.

## Greenfield

Документации нет или есть только пустые заготовки.

1. Прочитай известные точки входа и пути документации. Отсутствие документов
   не разрешает сначала обойти весь код: обозначь пробел, затем исследуй
   только нужные фрагменты для первичного наполнения.
2. Предложи структуру по контракту и согласуй объём: `AGENTS.md`, каркас
   `.oc/`, `package.json` с `@shahimat/cli`, комплект skills, первые структуры
   данных. Не создавай пустые manuals, структуры или цели ради полноты дерева.
3. Поставь инструмент: Node ≥ 24, в `package.json` точная версия
   `@shahimat/cli` в `devDependencies`, `npm install`; проверь из корня
   проекта `ai data check` — без `.oc/data/` команда завершается успешно.
4. Поставь обязательный комплект из `provides.skills` контракта по skill
   `source-sync`, протокол v2.1. Инструкции всех skills не читай.
5. Разверни `.oc/`: `project.yml` (name, summary, stack, reality; namespaces и
   external при необходимости), `index.yml` с секциями `data`, `manuals`,
   `goals`. Напиши `AGENTS.md` по шаблону контракта: ядро дословно, разделы
   шаблона — заголовками второго уровня, затем границы проекта и триггеры
   проектных skills. Проверь фактическое наличие todo, формы вопроса и
   подходящих субагентов у выбранного инструмента агента и не выдавай
   описанное в контракте за включённое; для OpenCode V2 todo включается
   настройкой `experimental.todo: true`.
6. Факты сложи в структуры по skill `data-structures` — схема, индекс,
   записи, затем `ai data check`. Для процедур загрузи `manuals`, для
   очереди — `goals`, для проектных правил — `skill-builder`.
7. Проверь критерий готовности ниже, затем сохрани итоговые sync-checkpoints.

## Brownfield

Документация уже есть: своя точка входа, wiki-выгрузки, свои YAML и JSON,
tickets, RFC, длинные README или ad-hoc markdown. Сначала инвентаризация,
затем план; не переписывай молча. Если режим неясен — уточни.

### Инвентаризация

Прочитай существующие артефакты: точку входа агента, README, известные
каталоги документации, wiki-выгрузки, NOTES, ARCHITECTURE, SPEC, собственные
схемы, tickets, RFC, ADR, changelog, ad-hoc markdown и действующие проектные
настройки агента. Верни короткую карту: «файл X — это Y», «файл Z — устаревший
draft». Пока ничего не переписывай.

### Классификация и матрица соответствия

Для каждого куска предложи место: человеческая процедура — `.oc/manuals/`;
однотипные факты — структура данных `.oc/data/<key>/`; правило — skill,
исходный из каталога или проектный; всегда действующее ограничение — строка
`AGENTS.md`; оставшаяся работа — `.oc/goals/`; реквизиты — `.oc/project.yml`;
крупное принятое решение — `CHANGELOG.md`; шум — согласованное удаление или
архив. Покажи списком: «существующий файл → целевое место → что выигрываем и
теряем». Спорное размещение в двух местах требует границы, а не копии.
Manuals перерабатывай по skill `manuals`: факты сохрани в структуры, реальные
ручные шаги оставь процедурой, отчётные заглушки убери в согласованном объёме.

### Расхождения и конфликты

Перечисли противоречия соглашений проекта целевой модели и вариант разрешения
каждого с trade-off: свои tickets или roadmap против очереди goals, правила
контракта, скопированные в проектные документы, README как второй набор
правил агента, данные внутри спецификаций. Копии правил прежнего контракта не
переноси: их заменяет sync-поставленный skill `flow`.

### План поэтапного перехода

Разбей переход на самостоятельно ценные тикеты: один тикет — один коммит,
внутри — последовательный чеклист по типам, не фазы-коммиты. Точный набор
зависит от проекта; до перехода согласуй весь набор и объём.

1. Ввести `.oc/` без разрушения существующих слоёв: `project.yml`,
   `index.yml`, `goals/`; поставить инструмент и весь комплект skills.
2. Разнести факты по структурам данных через `data-structures`, прогнать
   `ai data check`.
3. Вынести правила в skills и строки `AGENTS.md` через `skill-builder`.
4. Перенести только настоящие ручные процедуры в `.oc/manuals/`.
5. Разложить живые задачи по целям через `goals`, прогнать `goal-consistency`;
   legacy-очередь удалять только после полного маппинга.
6. Написать `AGENTS.md` по шаблону v2.1, вывести из использования прежнюю
   точку входа и правила; обновить README, индекс и ссылки.
7. Проверить полный критерий готовности, убрать согласованный legacy без
   потери знаний, сохранить sync-checkpoints.

Внутри тикета не запрашивай «ок» после каждого пункта. Опасное, спорное,
неожиданное или новое решение — стоп. В конце тикета — короткий отчёт,
проверки и одно английское сообщение коммита.

## Миграция с v2

Формат очереди и смысл manuals не меняются; остальное переезжает по таблице.

- `AGENTS.md` — переписать по шаблону v2.1: маршрут на `.oc/` и skill `flow`,
  строки чтения структур данных и очереди, всегда действующие ограничения
  проекта, триггеры проектных skills.
- `context/project.yml` — в `.oc/project.yml`; поля те же, блок `sync` — по
  `source-sync`, протокол v2.1.
- `context/index.yml` — в `.oc/index.yml` с секциями `data`, `manuals`,
  `goals`; записи entities, behaviors и conventions уходят вместе со своими
  файлами.
- `context/workflow.md`, `project-knowledge.yml`, `verification.yml` и другие
  копии правил контракта — удалить: их заменяет sync-поставленный skill
  `flow`, а правила записи живут в skill `project-docs`.
- `context/conventions/<key>.yml` — разобрать по содержимому: правило общего
  характера — исходный skill из каталога, а если готового нет — предложение в
  источник через skill `source-feedback`; процедурное правило или проектная
  договорённость — проектный skill через `skill-builder`; всегда действующее
  ограничение — строка `AGENTS.md`; факт или параметр — структура данных.
- `context/modules/` — заменить skills: модуль, у которого есть
  skill-близнец, заменяется этим skill; введённый им слой остаётся, только
  если ему нашлось место среди структур, manuals или skills; manifest
  удаляется.
- `docs/entities/*.yml` — разобрать по содержимому: спецификации компонентов
  и внешних систем — в свою структуру, информационные записи — в структуру под
  вид записи; оперативные задачи, история и снимки вынести из спецификаций в
  отдельные структуры.
- `docs/behavior/*.yml` — если проекту нужны проверяемые сценарии, завести
  структуру с `verified`, `verified_at` и `verified_note` в схеме; иначе
  сохранить стоит только утверждения, которые останутся полезны. Подтверждённое
  происхождение `verified` сохраняется, недостающее не выдумывается.
- `docs/manuals/` — в `.oc/manuals/`; ссылки на entity заменить ссылками на
  структуры и записи.
- `context/views/` — в `.oc/goals/` без изменения формата.
- Самодельные слои — однотипные записи в структуры; знания в markdown — по
  skill соответствующего слоя или в manual; отчёты и evidence каноном не
  становятся.

## Проверки и критерий полного перехода

Выбирай проверки по эффекту: `ai data check` после любого изменения данных,
структура и ссылки `.oc/`, состав skills и их SHA, очередь, действующие
инструкции и настройки. Если продуктовый код, его конфигурация и поведение не
менялись, повторные продуктовые тесты из миграции документации не следуют;
если затронуты — проверь их в составе изменения.

Переход завершён, только когда:

- существенные знания, факты, решения и правила разложены по структурам,
  skills, manuals и очереди, доступны через `.oc/index.yml` и переносятся с
  проектом; нет memory или неиндексируемых заметок как параллельного слоя;
- `ai data check` завершается успешно, индекс актуален, обязательные файлы
  `.oc/` и `AGENTS.md` соответствуют контракту;
- весь комплект `provides.skills` установлен, сверен по SHA, checkpoints
  сохранены после полной поставки; типовые инструкции не продублированы в
  других документах;
- manuals — только нужные человеческие процедуры, без миграционных отчётов;
- живые задачи разложены по целям, `goal-consistency` проходит, прежняя
  очередь не осталась параллельной;
- действующие инструкции и настройки соответствуют v2.1, `context/` и `docs/`
  больше не управляют работой;
- выполнены все обязательные пункты перехода.

До этого доводи миграцию сам; при реальном блокере назови нужное решение или
действие. Отдельный отчёт о переходе не создавай: устойчивые знания уже на
своих местах, завершённое крупное решение — одна запись в `CHANGELOG.md`.

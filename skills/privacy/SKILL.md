# privacy

Правило целиком — в блоке `privacy` в `AGENTS.md`: оно действует,
даже если skill не загружен. Здесь — механика. Ответы модуля —
`context/modules/privacy.yml` → `answers` (`outbound`,
`repo-visibility`).

## Правило в двух уровнях

Применение паттерна `guardrail-dual-level` (см.
`patterns/guardrail-dual-level.md` в репозитории `ai-prompts`).
Inline-копия обновляется вместе с паттерном.

**Уровень агента.** Правило модуля — строками в его блоке `AGENTS.md`.
Обязательно наравне с жёсткими правилами ядра: дополняет их и не
отменяет. В пределах своей области (то, что описывает модуль) правило
приоритетнее формата сценария, удобства и скорости: при конфликте —
стоп и вопрос пользователю, а не тихий компромисс.

**Уровень приложения.** Если в проекте есть приложение и подключён
`domain` — правило выражено обязательными behavior:

- по одной behavior на каждый проверяемый аспект правила (детекция,
  реакция, хранение — по смыслу модуля);
- `check` — где проверку можно автоматизировать;
- новая фича, затрагивающая область правила, не считается готовой, пока
  связанные behavior не `verified: true`.

**Проверки.**

- правило есть в блоке `AGENTS.md` модуля, а не только в skill;
- у области правила в приложении есть хотя бы одна behavior;
- behavior правила с `verified: false` поднимается в каждом `report`
  как блокер, пока не проверена.

**Чего не делать.**

- не переносить правило в `context/conventions/` копией — оно живёт в
  блоке и skill модуля;
- не ослаблять правило ради сценария, дедлайна или просьбы «на этот
  раз»: исключение — только явным решением пользователя, записанным
  через docs-keeper.

## Что считается чувствительным

- значения о человеке: показатели здоровья, симптомы, диагнозы,
  лекарства, состояния, привычки, финансы;
- идентификаторы: имена, контакты, адреса, даты рождения, номера
  документов, геолокация;
- собственные незрелые формулировки и позиции пользователя, не
  предназначенные к публикации;
- всё, что пришло из канала данных (`data-access`), пока не доказано
  обратное.

Сомневаешься — считай чувствительным.

## Где данных быть не должно

- документация (`docs/`, `context/`, `README.md`), примеры, шаблоны;
- `CHANGELOG.md`, сообщения и описания коммитов, имена веток;
- логи, тестовые фикстуры, снапшоты, отчёты harness;
- запросы к внешним сервисам агента (веб-поиск, сторонние API).

Вместо значений — синтетика или обфускация: правдоподобная, но
заведомо не реальная («сон 6.5 ч», «пользователь A»), и не «замаскированное
реальное» (округление, сдвиг дат). Реальные данные живут в хранилище
приложения и личных источниках, читаются через канал.

`repo-visibility`:

- `private` — в записях домена допустимы обобщённые формулировки о
  человеке без значений, диагнозов и идентификаторов;
- `public` — в репозитории о человеке только структура и синтетика;
  перед каждым коммитом сверь diff на чувствительное.

## Ответы пользователю

- выводы и агрегаты по умолчанию; сырые записи — по прямой просьбе и
  ровно в запрошенном объёме;
- не повторяй чувствительное из прошлых сообщений без нужды;
- memory агента запрещена ядром — чувствительное тем более не
  оседает нигде, кроме хранилища приложения.

## Внешний поток

Поток — любая передача данных за пределы контроля пользователя: облако,
синхронизация, сторонний API, аналитика, краш-репорты, публикация.

- `outbound: none` — не проектируй и не включай потоки. Без потока не
  обойтись — стоп, блокирующий вопрос: решение пользователя меняет
  ответ через `contract-setup`;
- `outbound: by-approval` — до «да» опиши поток: какие данные, куда,
  зачем, как защищены (шифрование, минимизация), как отключить.
  Одобренный поток:
  - строка в `CHANGELOG.md` с тегом `privacy`;
  - privacy-behavior на поток, если подключён `domain`; иначе —
    convention проекта `context/conventions/outbound-<name>.yml`;
- одобрение — на конкретный поток, не на класс: «облако для бэкапа» не
  разрешает «облако для аналитики».

## Стартовые behavior

При подключённом `domain` и наличии приложения — предложи (namespace
приложения или новый `privacy` — с «да»):

- `privacy-local-storage` — данные хранятся локально / в хранилище под
  контролем пользователя;
- `privacy-no-outbound` — приложение не делает запросов наружу, кроме
  одобренных потоков (`check` — тест или аудит сетевых вызовов);
- `privacy-logs-redacted` — логи и ошибки не содержат значений и
  идентификаторов;
- `privacy-encryption-at-rest` — чувствительное шифруется на диске,
  если это применимо.

Каждый одобренный поток — своя behavior (`privacy-outbound-<name>`):
что уходит, куда, как отключается.

## Проверки

Перед сохранением и в `audit`:

- новые и изменённые файлы, сообщение коммита и строка CHANGELOG — без
  чувствительного;
- новая фича, которая хранит или передаёт данные, — есть privacy-behavior,
  и до `verified: true` фича не готова;
- privacy-behavior с `verified: false` — блокер в каждом `report`;
- нашёл реальные данные в репозитории — стоп, сообщи пользователю,
  план обфускации; переписывание истории git — его решение.

# source-feedback

Обратный канал к `source-sync`: тот приносит изменения из источника в
проект, этот собирает из проекта то, что стоит вернуть в источник, —
файлом JSON, который пользователь передаёт автору источника.

Ключи: «предложи улучшения в источник», «что из проекта стоит
обобщить», «собери фидбек по контракту», «что мы сделали поверх
схемы».

## Протокол

<!-- expect:source-feedback -->
1. **Базис.** Из `context/project.yml` → `sync` и
   `context/modules/*.yml` возьми ключи, `synced_sha` и `parts`; `curl`
   тянет индекс по `sync.index_source` (правила fetch — skill
   `source-sync`). Это `base` файла: от какого состояния источника
   отличается проект.
2. **Кандидаты** — по четырём видам (`kind`), разделы ниже:
   - `drift` — поставленную из источника часть правили в проекте;
   - `generalization` — локальное решение, полезное не только этому
     проекту;
   - `gap` — схема молчит, проект придумал своё;
   - `friction` — правило схемы проект обходит или выключил.
3. **Фильтр.** Кандидат остаётся, если ответ «да» на вопрос: «пригодится
   ли это другому проекту на v3?». Специфика домена, разовые решения,
   вкусовые правки — не в файл. Не больше 15 предложений, сильные
   первыми.
4. **Обобщение.** Для каждого — `generalized`: формулировка для
   источника без имён, путей и терминов проекта, и `target` — куда в
   источнике: `contract`, `module:<key>`, `skill:<name>`,
   `agent:<name>`, `pattern:<key>`, `preset:<key>`, `harness` или `new`.
5. **Сводка и вопрос.** Список: `kind`, `target`, `summary` — по строке
   на предложение. Блокирующий вопрос (skill `workflow`): сформировать
   файл, убрать пункты (номерами) или ничего не делать. Путь файла —
   вне репозитория проекта (по умолчанию — временный каталог), чтобы
   файл не попал в git; другой путь — по ответу пользователя.
6. **Файл.** После «да» — JSON по формату ниже, затем очистка и проверка
   секретов (раздел «Что уходит наружу»).
7. **Отчёт:** путь файла, число предложений по видам, итог проверки
   секретов.

Агент только формирует файл. Передать его в источник — issue, PR,
сообщение автору — решает и делает пользователь: агент ничего не
отправляет, не публикует и не создаёт issue сам. Проект этим skill не
меняется: ни документация, ни `.agents/`, ни manifest'ы.
<!-- /expect:source-feedback -->

## `drift` — правки поставленных частей

<!-- expect:feedback-drift -->
Дрейф определяется сверкой SHA, не на глаз.

- **Skill** (`.agents/skills/<name>/`, источник — `parts.skills`
  контракта или модуля). SHA каждого файла копии — `shasum -a 256`;
  строки `<sha файла>  <путь внутри skill>`, по одной на файл, в
  порядке путей (побайтово), с переводом строки после каждой; SHA этого
  текста — SHA записи skill. Не совпал с `parts` — копию правили в
  проекте: это `drift`.
- **Субагент** (`.agents/agents/<name>.md`) — SHA файла против
  `parts.agents`.
- **Блок модуля** в `AGENTS.md` и **шаблон ядра** — копий с SHA нет:
  `curl` тянет модуль или контракт по `raw` и сравнивает текст блока
  (шаблона) с текущим `AGENTS.md`. Строки вне блоков модулей, которых
  нет в шаблоне, — тоже `drift` (`target: contract`).

Что именно правили — diff локальной копии с файлом из источника
(`curl` по `raw`, SHA сверен с индексом). Если запись в индексе тоже
разошлась с `parts`, источник ушёл вперёд: diff смешивает обе правки —
отметь это в `rationale` и предложи пользователю сначала
`source-sync`. В `evidence` — `local_sha` и `source_sha`.
<!-- /expect:feedback-drift -->

## `generalization` — локальные обобщения

- `context/conventions/*.yml` — договорённость без имён и путей
  проекта, которая подошла бы любому проекту этого вида →
  `pattern:<key>`, `module:<key>` или `contract`;
- свои skills в `.agents/skills/`, которых нет в индексе → `new` или
  `module:<key>`;
- поля в слоях модулей, которых нет в модуле и в `provides.extends` →
  `module:<key>`;
- свои слои и файлы в `context/`, которых нет ни в ядре, ни в
  `provides` модулей → `new` или `module:<key>`;
- свои скрипты и шаги CI, которые проверяют или генерируют то же, что
  мог бы harness → `harness`;
- набор возможностей и ответов, который проект выбрал вместо пресета
  или поверх него → `preset:<key>` или `new`.

## `gap` и `friction`

`gap` — схема молчит, проект придумал своё:

- теги в `CHANGELOG.md` вне тегов ядра и `changelog_tags` модулей;
- решения в журнале о том, как работать с агентом или документацией
  (не о продукте) — правило, которого нет в схеме;
- повторяющиеся вопросы пользователю, на которые схема могла бы
  ответить заранее.

`friction` — правило схемы обходят:

- в conventions или `AGENTS.md` правило, противоречащее ядру или
  модулю;
- выключенное: проверка harness (`secrets: false`, большие
  `allow`), memory агента, удалённое жёсткое правило шаблона;
- блок модуля переписан так, что правило ослаблено.

Для `friction` в `rationale` — почему проект обходит правило: это
главное, что нужно источнику.

## Формат файла

Схема — `expectations/schemas/source-proposal.schema.json` в
источнике. Пример:

```json
{
  "format": "source-proposal",
  "version": 1,
  "generated_at": "2026-10-14",
  "base": {
    "index_sha": "9b1c0e5d2f4a6b8c7d3e1f0a2b4c6d8e9f1a3b5c7d9e0f2a4b6c8d0e1f3a5b7c",
    "contract": {
      "key": "agent-operational-contract-v3",
      "synced_sha": "3d65d6f67e191e360c24c371e01f3278f07e8d7c94af519436026fa942cf608e"
    },
    "preset": "operational",
    "modules": [
      {
        "key": "goals",
        "synced_sha": "41c2cfef96fd7e1fbf5c2b42179d10d970c24b90116b278d2e2bcc9f8385c183"
      }
    ],
    "harness": "0.4.0"
  },
  "proposals": [
    {
      "id": "goal-review-cadence",
      "kind": "generalization",
      "target": "module:goals",
      "summary": "Еженедельный обзор целей как сценарий report",
      "rationale": "Проект завёл convention с обзором целей раз в неделю; без неё цели устаревали.",
      "generalized": "В skill goals — сценарий периодического обзора: какие цели без движения дольше N дней.",
      "evidence": [
        {
          "path": "context/conventions/<key>.yml",
          "excerpt": "раз в неделю report по целям: без движения > 14 дней — вопрос пользователю"
        }
      ],
      "confidence": "medium"
    }
  ]
}
```

- `base` — без имени проекта: для разбора в источнике достаточно ключей
  и SHA.
- `id` — kebab-case, уникален в файле.
- `summary` — до 200 символов; `excerpt` — до 2000, минимальный кусок,
  который доказывает предложение.

## Что уходит наружу

<!-- expect:feedback-sanitized -->
Файл покидает проект — в нём только обезличенное:

- нет персональных данных, имён людей, почты, телефонов;
- нет ссылок и указателей из `external` в `context/project.yml`, хостов
  и внутренних адресов — вместо них `<url>`;
- имя проекта, namespaces, доменные термины в `excerpt` и
  `generalized` — заменены на `<project>`, `<namespace>`, `<term>`;
- подключён модуль `privacy` — его правила строже: реальных значений
  нет ни в каком виде.

После записи файла — проверка секретов:

<!-- expect:skill-runs -->
<!-- metadata.runs: secrets scan -->
- подключён harness — `ai secrets scan --file <путь>`;
<!-- /expect:skill-runs -->
- без harness — сам, по тем же типам: ключи API, токены, пароли и
  секреты в присваиваниях, приватные ключи.

Нашлось — убери из файла и проверь снова. Пользователю в отчёте —
итог проверки и напоминание: файл перед передачей стоит прочитать
целиком.

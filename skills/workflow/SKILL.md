# workflow

Протоколы работы в проекте на контракте `agent-operational-contract-v3`.
Маршрутизация и жёсткие правила — в `AGENTS.md`; здесь — как их
применять.

## Сценарии

Сценарий определяй по ключевым словам запроса. Не уверен — спроси.

### `plan` — «предложи», «как лучше», «варианты», «что думаешь»

1. Прочитай документы по маршруту задачи (`AGENTS.md` → «Где искать
   ответ»).
2. Назови расхождения между «как есть» и «как хочу».
3. Дай 1–3 варианта по 2–4 строки, с trade-off.
4. Одной строкой — рекомендация.
5. Большая задача — разбей на фазы по связности (см. «Фазы»).
6. Жди выбора. В `execute` сам не переходишь.

### `execute` — «делай», «поехали», «внедряй»

1. Работаешь по согласованному плану, после чтения документов по
   маршруту.
2. Доводишь задачу до конца целиком: код, тесты, генерируемые
   артефакты, документация.
3. Между шагами — короткие статус-строки.
4. Опасное, спорное, неожиданное — стоп и блокирующий вопрос.
5. В конце — намерения в docs-keeper (см. skill `docs-keeper`),
   `harness check`, если подключён harness, отчёт.

### `audit` — «проверь состояние», «прогони проверку»

1. `harness check`, если подключён harness.
2. Проверки подключённых возможностей по их skills (например,
   `verified` у behavior — skill `domain`).
3. Отчёт: что проверено, где расхождения, что осталось непроверенным и
   почему. Исправления — через docs-keeper, после «да».

### `challenge` — «покритикуй», «поспорь», «найди слабое место»

1. По умолчанию не соглашайся.
2. Минимум два контраргумента.
3. Проверь противоречие с `context/conventions/` — назови конкретную
   convention.
4. Итог: «ок с оговорками X» или «альтернатива Y».

### `report` — «статус», «где мы», «что активно»

1. Не пересказывай рабочие файлы дословно.
2. 3–5 пунктов: действие → где подробности (manual, цель, файл) →
   пояснение одной строкой.
3. Блок «блокеры».
4. Одна строка — «что делать первым».

## Блокирующий вопрос

Нужен ответ пользователя — задай вопрос и остановись.

Одно сообщение — либо вопросы, либо действия. Не смешивай «жду
решения по пунктам 1–2» и «по пункту 3 иду дальше по дефолту»: вопросы
решаются инерцией «ок», реальные ответы теряются, а часть работы уже
сделана поверх несогласованного.

Формат:

- пронумерованные вопросы, один вопрос — одна развилка;
- варианты нумерованные (1, 2, 3; вложенные — 1.1, 1.2), не A/B/C;
- у каждого вопроса — дефолт с обоснованием одной строкой: «по
  умолчанию предлагаю N, потому что …»;
- дефолт — предложение, а не решение: пока не подтверждён, не применён.

Выбор нескольких вариантов из списка (чеклист) — инструментом вопроса
с multi-select, если он есть; иначе нумерованный список с пометкой
отмеченных по умолчанию и ответом «номера через запятую».

Перед вопросом проверь: он правда блокирует? Можно пойти дальше и
вернуться — иди. Ложные вопросы приучают кликать «ок» по инерции.

## Фазы

Фаза атомарна по **связности**, а не по типу изменений: одна
законченная по смыслу задача целиком.

- Код, тесты, генерируемые артефакты и связанная правка документации —
  одна фаза, один коммит.
- Тип коммита (karma commit-msg: `feat`, `fix`, `refactor`, `docs`,
  `test`, `perf`, `chore`, `style`) — по главному смыслу фазы.
- Несвязанное «заодно поправлю» — отдельная фаза или задача в
  очередь.
- Согласование — на развилках и в конце задачи. Между частями одной
  задачи не останавливаешься.
- Конец задачи: короткий отчёт + предложенное сообщение коммита → ждёшь
  «ок». К следующей задаче сам не переходишь.
- Коммиты, ветки, push, merge делает пользователь. Ты — только по
  явной просьбе и после подтверждения списка команд.

## Источники истины

- Код — что есть на самом деле.
- Слои документации (`context/`, слои возможностей) — как договорились
  и как должно быть.
- `CHANGELOG.md` — когда и почему, не «как сейчас».
- Индексы (`context/index.yml`, `prompts/index.yml` источника) —
  навигация, не правда.

Код и документ расходятся — прав код, документ обновить через
docs-keeper. Не знаешь — `unknown`, не выдумывай.

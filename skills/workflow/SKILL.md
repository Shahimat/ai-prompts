# workflow

Протоколы работы в проекте на контракте `agent-operational-contract-v3`.
Маршрутизация и жёсткие правила — в `AGENTS.md`; здесь — как их
применять.

## Внимание пользователя

<!-- expect:attention -->
Внимание пользователя — самый дорогой ресурс.

- Вопрос — только когда без решения пользователя нельзя продолжить или
  откатить. Можно пойти дальше и вернуться — иди (раздел «Блокирующий
  вопрос»).
- Контекст основной сессии — на доменную область. Документацию ведёт
  субагент librarian, механические проверки — harness. Правила записи
  в документацию основная сессия не читает.
- Отчёт — выводы и решения, без пересказа рабочих файлов.
- Полная схема — полнота ответственности, не максимум запусков ролей.
  Пользователю — старт, реальный blocker, полезный milestone и итог.
  Callback сам по себе не требует реплики; raw micro-reports не повторяй.
  Оставайся доступен, роли запускай в фоне, без опроса их состояния.
<!-- /expect:attention -->

## Брифинг перед стартом

<!-- expect:briefing -->
Первое содержательное сообщение сессии — один вопрос: работаем в
**дефолте проекта** или собираешь **кастом на сессию**? Без ответа роли
и тикеты не запускаешь — даже когда запрос выглядит как готовая задача:
сначала брифинг, потом сценарий. «Быстрый вопрос», «просто глянь»,
«срочно» — те же брифинг и порядок чтения документации: размер и
срочность запроса протокол не отменяют.

- **Дефолт** — настройки проекта по умолчанию: читаешь
  `.oc3/project.yml` → `briefing` и применяешь молча, одной строкой
  назвав активный режим. Нет блока — считай `cheap`: тикеты делаешь сам
  (порог тикета назови), доку — librarian через `docs_request`,
  judge — off, приёмка на тебе. `roles` — тикеты executor'у, разведка
  researcher'у, judge on.
- **Кастом** — альтернативная конфигурация на эту сессию, сам проект не
  меняет. Свободный чеклист по текущей конфигурации (`oc3 models`,
  «покажи конфигурацию»), каждый пункт — с дефолтом и обоснованием:
  1. Роли: какие оставить, какие убрать; какие добавить — с какой
     моделью у каждой (любая модель каталога OpenCode).
  2. Разведка: документацию и артефакты читаешь сам, код-разведку и
     внешние системы — researcher с артефактом.
  3. Judge: вкл — judge проверяет тикет по expectations и DoD;
     judge-off — вердиктов нет, приёмку делаешь сам и при замечаниях
     перезапускаешь executor. Дефолт — вкл.
  4. Режим тикетов: со стопом на коммит после каждого или все подряд.

Ответ «дефолт» на любом шаге принимает предложенное. Кастом живёт в
сессии; сохранить в проект — только по явному «сохрани»:
`oc3 briefing set custom <routing> <research> <judge> <ticket_mode>`
(пресеты — `cheap`, `roles`). Повтор брифинга — «покажи конфигурацию».
Expectations и их заголовки при judge-off правит только пользователь.
<!-- /expect:briefing -->

## Готовый пакет исполнения

До исполнителя — один bounded task packet: одобренный DoD и его источник,
scope/exclusions, root/worktree, permissions, владельцы code/source/docs и
проверок, все затронутые launch paths, prerequisites, targeted/full checks,
бюджет доработок и классификация итоговых файлов. Бриф ссылается на пакет.
Preflight проверяет окружение, доступные средства и полноту пакета без AI.
Все project OC3 outputs — по runtime resolver внутри `.oc3/`, независимо от classification.
Недостающее в согласованном scope исправляет оператор; новое решение — вопрос.
Исследователь нужен для конкретного пробела, не для повторного чтения фактов.
Нативный или legacy launcher без managed gate не объявляй изолированным.

## Сценарии

Сценарий определяй по смыслу запроса, а не по одному слову; карта ниже —
стартовые ориентиры, не закрытый список. Не уверен — спроси. Любой
запрос — сначала маршрут «Где искать ответ»: документация отвечает
или ведёт; код — следом.

- `plan` — «предложи», «составь план», «давай спланируем», «спланируй»,
  «накидали план», «распиши шаги», «как лучше», «варианты», «что думаешь»;
- `execute` — «делай», «поехали», «запускаем», «внедряй», «исправляй»,
  «почини», «доработай»;
- `audit` — «проверь», «прогони проверку», «пробеги проверки», «как состояние»;
- `challenge` — «покритикуй», «поспорь», «найди слабое место», «возражай»;
- `report` — «статус», «где мы», «что по целям», «что дальше», «что активно»;
- `models` — «какая модель у роли», «перенастрой модели», «покажи модели»;
- фиксация целей — «фиксируй ожидания», «заведи ожидание», «оформи как
  тикет», «запиши в цели», «добавь тикет» → зафиксируй в
  `.oc3/goals/<goal>.expect.ts`: цель — `describe('goal: …')`, тикет —
  `describe('ticket: …')`, критерии — `crit.todo('…')` в проверяемой
  формулировке; это `execute`-режим над очередью целей.

### `plan` — «предложи», «как лучше», «варианты», «что думаешь»

1. Прочитай документы по маршруту задачи (`AGENTS.md` → «Где искать
   ответ»).
2. Назови расхождения между «как есть» и «как хочу».
3. Дай 1–3 варианта по 2–4 строки, с trade-off.
4. Одной строкой — рекомендация.
5. Тикет — нарезай на коммиты по глобальным правилам пользователя;
   в проекте их не дублируем.
6. Жди выбора. В `execute` сам не переходишь.

### `execute` — «делай», «поехали», «внедряй»

1. Работаешь по согласованному плану и готовому пакету, после чтения
   документов по маршруту. Первый ordinary FAIL — повод доработать, не blocker.
2. Режим тикетов — из брифинга: с остановкой — после каждого тикета
   стоп до коммита пользователя; все подряд — следующий тикет сразу.
3. При judge-off приёмку тикета делаешь сам по expectations и DoD,
   без вердиктов; замечания — новым запуском executor.
4. Исполнитель доводит пункты targeted-проверками. Один владелец проверок
   на worktree; параллельные build и чтение общего dist запрещены.
5. После code/source stable — один необходимый docs batch и производные,
   затем один full CI на стабильном snapshot и независимый ticket judge.
   Судья использует актуальное evidence, а не повторяет CI по привычке.
6. Обычные факты идут в durable inbox, не запускают librarian по одному.
   Receipt означает pending, не обновлённый канон. Critical и обязательный
   applied-docs DoD требуют fast lane. Опасное или вне scope — стоп.
7. Ready: обязательный DoD закрыт, проверки актуальны, все изменённые файлы
   классифицированы; cache/ledger и пустой случайный sidecar не deliverable.
   Durable не означает commit: локальные run-артефакты отдели от версионируемого результата.
   Закрой рабочий план, затем проверка и один итоговый отчёт:
   <!-- expect:skill-runs -->
   <!-- metadata.runs: check -->
   `ai check`, если подключён harness.
   <!-- /expect:skill-runs -->

### `audit` — «проверь состояние», «прогони проверку»

1. Проверка проекта:
   <!-- expect:skill-runs -->
   `ai check`, если подключён harness.
   <!-- /expect:skill-runs -->
2. Проверки подключённых возможностей по их skills (например,
   `verified` у behavior — skill `domain`).
3. Отчёт: что проверено, где расхождения, что осталось непроверенным и
   почему. Исправления — через librarian, после «да».

### `challenge` — «покритикуй», «поспорь», «найди слабое место»

1. По умолчанию не соглашайся.
2. Минимум два контраргумента.
3. Проверь противоречие с `.oc3/conventions/` — назови конкретную
   convention.
4. Итог: «ок с оговорками X» или «альтернатива Y».

### `report` — «статус», «где мы», «что активно»

1. Не пересказывай рабочие файлы дословно.
2. 3–5 пунктов: действие → где подробности (manual, цель, файл) →
   пояснение одной строкой.
3. Блок «блокеры».
4. Одна строка — «что делать первым».

### `models` — «настройка моделей», «перенастрой модели», «какая модель у роли»

<!-- expect:skill-runs -->
Справка для отдельного запроса на управление моделями. Workflow не
добавляет `models set/apply/check` к своим автоматическим запускам:
его `metadata.runs` — только завершающая проверка `execute`.

1. Текущее состояние — `ai models`: эффективные модели и их источник.
   Если в корне есть `manifest.json` моделей, он — единственная ручная
   декларация: `default` для всех ролей, `roles` для исключений. Файлы
   ролей и OpenCode-конфиги — не дополнительные места настройки.
   Без manifest сохраняется legacy-режим: override в
   `.oc3/project.yml` → `roles.models`; строка `override: … — прогони
   models apply` означает, что его ещё нужно применить.
2. Каталог — инструмент моделей OpenCode: все включённые модели
   подключённых провайдеров, с вариантами `#variant`.
3. Пользователь уже назвал модель и роли — проверь точный ID в
   каталоге, повторный выбор не нужен. Иначе — одним окном вопроса на
   роль: вариант на каждую модель каталога, у текущей пометка
   «текущая». Длинный каталог группируй по провайдерам.
4. Отдельное явное действие человека или оператора по запросу —
   `ai models set <роль> <модель>`. В manifest-режиме команда сохраняет
   исключение и применяет производные без изменения исходных ролей.
   Общая модель хранится в `manifest.json` → `default`; ручное
   обслуживание через `ai models apply` и `ai models check` описано в
   skill `cli`.
   Механика детерминированная, без AI. Исключения не сбрасывают молча.
5. `ai models check` — отдельная проверка без записи, не неявное
   завершение workflow. При source-sync manifest остаётся локальным,
   производные восстанавливает `refresh`. Без manifest `set/apply`
   сохраняют прежнюю legacy-семантику.
<!-- /expect:skill-runs -->

### `recover` — «восстанови», «что потеряли», «куда делось»

<!-- expect:recover -->
Знание пропало или изменилось не в ту сторону.

1. Найди в истории коммит потери: `git log -p -S '<фраза>' -- <слои>`;
   строки `revise` в теле коммитов — объявленные пересмотры.
2. Восстанови: намерение субагенту librarian — вернуть знание,
   `evidence` — коммит потери.
3. Рефлексия: почему знание потеряно — намерение `rule`, чтобы потеря
   не повторилась (например, уточнить, что считается пересмотром).
4. Отчёт: что вернули, из какого коммита, какое правило добавили.
<!-- /expect:recover -->

## Намерения в документацию

<!-- expect:docs-intents-triggers -->
Обычные входящие знания — optional `knowledge_delta` в результате роли
либо явная отправка оператором: subject/property/value, kind
observation|decision|candidate и evidence. Runtime сохраняет inbox и receipt
без AI; автор/task/scope/snapshot назначает сам. Нет новых фактов — пусто.
Decision не означает applied, candidate не истина; provenance не verified.
Publisher описывает своё изменение, не ищет все дубли и не переписывает канон.
Sensitive values не отправляет; нетривиальный critical конфликт эскалирует.

Для канонической записи остаются намерения `kind`, `summary`, `evidence`
(схема `intents`) по правилу 4 `AGENTS.md`: с harness — docs-delta, без него —
librarian. Один bounded пакет по теме/scope вместо запуска на каждый факт.
Намерения формируются:

- в конце `execute`;
- в `audit` — исправления, после «да»;
- в `recover`;
- в сценарии `inquiry` модуля analysis — новые источники и тезисы;
- на «запомни».

Пример входа (YAML; JSON и объект `{intents: [...]}` — тоже):

```yaml
- kind: rule
  summary: имена файлов в kebab-case
  evidence: решение пользователя в задаче
- kind: revise
  target: naming
  summary: имена в snake_case
  was: имена в kebab-case
  why: совместимость с внешним API
  evidence: решение пользователя в задаче
```

`revise` — пересмотр существующего знания: `target`, `was`, `why`
обязательны. Вход не по схеме harness отклоняет коротким сообщением с
ожидаемой формой.

`plan`, `challenge`, `report` канон не меняют. Рабочая ring-1 проекция —
не канон и не весь сырой inbox в контексте. Только проверенный batch-close
разрешает exact-ID ack; новые arrivals остаются следующему пакету.
Один финальный консолидированный отчёт сохраняет revise и открытые риски,
без повторения raw micro-reports; строки `revise` — в тело сообщения коммита.
Финальное evidence CI/judge не переписывает канон и не инвалидирует само себя.
<!-- /expect:docs-intents-triggers -->

## Блокирующий вопрос

<!-- expect:blocking-question -->
Нужен ответ пользователя — задай вопрос и остановись.

Одно сообщение — либо вопросы, либо действия. Не смешивай «жду
решения по пунктам 1–2» и «по пункту 3 иду дальше по дефолту»: вопросы
решаются инерцией «ок», реальные ответы теряются, а часть работы уже
сделана поверх несогласованного.

Формат:

- пронумерованные вопросы, один вопрос — одна развилка;
- варианты нумерованные (1, 2, 3; вложенные — 1.1, 1.2), не A/B/C;
- у каждого вопроса — дефолт с обоснованием одной строкой: «по
  умолчанию предлагаю N, потому что …»;
- дефолт — предложение, а не решение: пока не подтверждён, не применён.

Выбор нескольких вариантов из списка (чеклист) — инструментом вопроса
с multi-select, если он есть, с учётом его лимитов (у `AskUserQuestion`
2–4 варианта в вопросе, до 4 вопросов за раз: длинный список — группами
или через «как есть / изменить»); иначе нумерованный список со
сквозной нумерацией, пометкой отмеченных по умолчанию и ответом «номера
через запятую».

Перед вопросом проверь: он правда блокирует? Можно пойти дальше и
вернуться — иди. Ложные вопросы приучают кликать «ок» по инерции.
<!-- /expect:blocking-question -->

## Источники истины

- Источник реальности (`.oc3/project.yml` → `reality`) — что есть на
  самом деле: код этого репозитория или целевые системы и репозитории.
- Слои документации (`.oc3/`, слои возможностей) — как договорились
  и как должно быть.
- `CHANGELOG.md` — когда и почему, не «как сейчас».
- Индексы (`.oc3/bundles/index.md`, `prompts/index.yml` источника) —
  навигация, не правда.
- Inbox — неподтверждённые сообщения и их рабочая проекция. Вес 1 задаёт
  кольцо доступа, а не достоверность; разные scopes не склеиваются молча.

Источник реальности и документ расходятся — прав источник, документ
обновить через librarian. Не знаешь — `unknown`, не выдумывай.

# workflow

Протоколы работы в проекте на контракте `agent-operational-contract-v3`.
Маршрутизация и жёсткие правила — в `AGENTS.md`; здесь — как их
применять.

## Внимание пользователя

<!-- expect:attention -->
Внимание пользователя — самый дорогой ресурс.

- Вопрос — только когда без решения пользователя нельзя продолжить или
  откатить. Можно пойти дальше и вернуться — иди (раздел «Блокирующий
  вопрос»).
- Контекст основной сессии — на доменную область. Документацию ведёт
  субагент librarian, механические проверки — harness. Правила записи
  в документацию основная сессия не читает.
- Отчёт — выводы и решения, без пересказа рабочих файлов.
<!-- /expect:attention -->

## Брифинг перед стартом

<!-- expect:briefing -->
Перед первым запуском ролей в сессии — один вопрос: схема работы
«дефолтная» или «кастомная»? Без ответа тикеты не запускаешь.

- **Дефолтная** — читаешь `context/project.yml` → `briefing` и
  применяешь молча, одной строкой назвав активный режим. Нет блока —
  считай `cheap`: тикеты делаешь сам (порог тикета назови), доку —
  librarian через `docs_request`, judge — off, приёмка на тебе.
  `roles` — тикеты executor'у, разведка researcher'у, judge on.
- **Кастомная** — чеклист, у каждого пункта дефолт с обоснованием:
  1. Схема запуска: тикеты — executor в worktree или сам; назови порог,
     с которого начинается тикет.
  2. Модели: покажи вывод `oc3 models` (план/платный API/override видны
     в строках); смена и выбор — сценарий `models`.
  3. Разведка: документацию и артефакты читаешь сам, код-разведку и
     внешние системы — researcher с артефактом.
  4. Judge: вкл — judge проверяет тикет по expectations и DoD; judge-off
     — вердиктов нет, приёмку делаешь сам и при замечаниях
     перезапускаешь executor. Дефолт — вкл.
  5. Режим тикетов: со стопом на коммит после каждого или все подряд.

Ответ «дефолты» на любом шаге принимает предложенное. После кастомного
чеклиста предложи сохранить выбор в проект: `oc3 briefing set custom
<routing> <research> <judge> <ticket_mode>` (пресеты — `cheap`, `roles`).
Повтор брифинга — «покажи конфигурацию». Expectations и их заголовки при
judge-off правит только пользователь.
<!-- /expect:briefing -->

## Сценарии

Сценарий определяй по ключевым словам запроса. Не уверен — спроси.
Любой запрос — сначала маршрут «Где искать ответ»: документация
отвечает или ведёт; код — следом.

### `plan` — «предложи», «как лучше», «варианты», «что думаешь»

1. Прочитай документы по маршруту задачи (`AGENTS.md` → «Где искать
   ответ»).
2. Назови расхождения между «как есть» и «как хочу».
3. Дай 1–3 варианта по 2–4 строки, с trade-off.
4. Одной строкой — рекомендация.
5. Тикет — нарезай на коммиты по глобальным правилам пользователя;
   в проекте их не дублируем.
6. Жди выбора. В `execute` сам не переходишь.

### `execute` — «делай», «поехали», «внедряй»

1. Работаешь по согласованному плану, после чтения документов по
   маршруту.
2. Режим тикетов — из брифинга: с остановкой — после каждого тикета
   стоп до коммита пользователя; все подряд — следующий тикет сразу.
3. При judge-off приёмку тикета делаешь сам по expectations и DoD,
   без вердиктов; замечания — новым запуском executor.
4. Идёшь по плану тикета (нарезка на коммиты — по глобальным правилам
   пользователя): каждый пункт доводишь до конца.
5. Внутри шага — короткие статус-строки.
6. Опасное, спорное, неожиданное — стоп и блокирующий вопрос.
7. В конце — закрой рабочий план сессии: отчёт с незакрытыми пунктами
   плана не считается завершённым. Затем — намерения субагенту
   librarian, проверка, отчёт:
   <!-- expect:skill-runs -->
   <!-- metadata.runs: check -->
   `ai check`, если подключён harness.
   <!-- /expect:skill-runs -->

### `audit` — «проверь состояние», «прогони проверку»

1. Проверка проекта:
   <!-- expect:skill-runs -->
   `ai check`, если подключён harness.
   <!-- /expect:skill-runs -->
2. Проверки подключённых возможностей по их skills (например,
   `verified` у behavior — skill `domain`).
3. Отчёт: что проверено, где расхождения, что осталось непроверенным и
   почему. Исправления — через librarian, после «да».

### `challenge` — «покритикуй», «поспорь», «найди слабое место»

1. По умолчанию не соглашайся.
2. Минимум два контраргумента.
3. Проверь противоречие с `context/conventions/` — назови конкретную
   convention.
4. Итог: «ок с оговорками X» или «альтернатива Y».

### `report` — «статус», «где мы», «что активно»

1. Не пересказывай рабочие файлы дословно.
2. 3–5 пунктов: действие → где подробности (manual, цель, файл) →
   пояснение одной строкой.
3. Блок «блокеры».
4. Одна строка — «что делать первым».

### `models` — «настройка моделей», «перенастрой модели», «какая модель у роли»

1. Текущее состояние — `oc3 models`: строки с `override: … — прогони
   models apply` означают расхождение с
   `context/project.yml` → `roles.models`.
2. Каталог — инструмент моделей OpenCode: все включённые модели
   подключённых провайдеров, с вариантами `#variant`.
3. Выбор — одним окном вопроса на роль: вариант на каждую модель
   каталога, у текущей пометка «текущая». Лимиты инструмента вопроса
   учитывай: длинный каталог группируй по провайдерам. Про «куда
   пишем» не спрашивай: override сохраняется в `roles.models` сам.
4. Применяешь по ответу: `oc3 models set <роль> <модель>` — строка
   отчёта на роль.
5. После source-sync — `oc3 models apply`: возвращает override в файлы
   ролей и производные.

### `recover` — «восстанови», «что потеряли», «куда делось»

<!-- expect:recover -->
Знание пропало или изменилось не в ту сторону.

1. Найди в истории коммит потери: `git log -p -S '<фраза>' -- <слои>`;
   строки `revise` в теле коммитов — объявленные пересмотры.
2. Восстанови: намерение субагенту librarian — вернуть знание,
   `evidence` — коммит потери.
3. Рефлексия: почему знание потеряно — намерение `rule`, чтобы потеря
   не повторилась (например, уточнить, что считается пересмотром).
4. Отчёт: что вернули, из какого коммита, какое правило добавили.
<!-- /expect:recover -->

## Намерения в документацию

<!-- expect:docs-intents-triggers -->
Намерения в документацию — `kind`, `summary`, `evidence`, по строке на
каждое (схема `intents`) — передаёшь по правилу 4 `AGENTS.md`: с
harness — процессу docs-delta, без него — субагенту librarian. Сам
правила записи не читаешь. Формируются:

- в конце `execute`;
- в `audit` — исправления, после «да»;
- в `recover`;
- в сценарии `inquiry` модуля analysis — новые источники и тезисы;
- на «запомни».

Пример входа (YAML; JSON и объект `{intents: [...]}` — тоже):

```yaml
- kind: rule
  summary: имена файлов в kebab-case
  evidence: решение пользователя в задаче
- kind: revise
  target: naming
  summary: имена в snake_case
  was: имена в kebab-case
  why: совместимость с внешним API
  evidence: решение пользователя в задаче
```

`revise` — пересмотр существующего знания: `target`, `was`, `why`
обязательны. Вход не по схеме harness отклоняет коротким сообщением с
ожидаемой формой.

`plan`, `challenge`, `report` документацию не меняют. Отчёт
librarian (до 10 строк) показываешь пользователю как есть; строки
`revise` — в тело сообщения коммита.
<!-- /expect:docs-intents-triggers -->

## Блокирующий вопрос

<!-- expect:blocking-question -->
Нужен ответ пользователя — задай вопрос и остановись.

Одно сообщение — либо вопросы, либо действия. Не смешивай «жду
решения по пунктам 1–2» и «по пункту 3 иду дальше по дефолту»: вопросы
решаются инерцией «ок», реальные ответы теряются, а часть работы уже
сделана поверх несогласованного.

Формат:

- пронумерованные вопросы, один вопрос — одна развилка;
- варианты нумерованные (1, 2, 3; вложенные — 1.1, 1.2), не A/B/C;
- у каждого вопроса — дефолт с обоснованием одной строкой: «по
  умолчанию предлагаю N, потому что …»;
- дефолт — предложение, а не решение: пока не подтверждён, не применён.

Выбор нескольких вариантов из списка (чеклист) — инструментом вопроса
с multi-select, если он есть, с учётом его лимитов (у `AskUserQuestion`
2–4 варианта в вопросе, до 4 вопросов за раз: длинный список — группами
или через «как есть / изменить»); иначе нумерованный список со
сквозной нумерацией, пометкой отмеченных по умолчанию и ответом «номера
через запятую».

Перед вопросом проверь: он правда блокирует? Можно пойти дальше и
вернуться — иди. Ложные вопросы приучают кликать «ок» по инерции.
<!-- /expect:blocking-question -->

## Источники истины

- Источник реальности (`context/project.yml` → `reality`) — что есть на
  самом деле: код этого репозитория или целевые системы и репозитории.
- Слои документации (`context/`, слои возможностей) — как договорились
  и как должно быть.
- `CHANGELOG.md` — когда и почему, не «как сейчас».
- Индексы (`context/index.yml`, `prompts/index.yml` источника) —
  навигация, не правда.

Источник реальности и документ расходятся — прав источник, документ
обновить через librarian. Не знаешь — `unknown`, не выдумывай.

# source-sync: v3

Применение паттерна `source-sync` (см. `patterns/source-sync.md` в
репозитории `ai-prompts`), расширенное для v3: отчёт «Что нового» и
версия harness. Механика SHA обновляется вместе с паттерном.

## Единый fetch-канал: только `curl`

<!-- expect:curl-only -->
```bash
curl -fsSL -H "Cache-Control: no-cache" -H "Pragma: no-cache" "<url>" -o "$tmp"
shasum -a 256 "$tmp" | awk '{print $1}'
```

WebFetch и аналоги запрещены: кэш инструмента подставляет старый ответ,
pre-processing (HTML → markdown, обрезка) искажает контент, и SHA не
сойдётся с raw-контентом источника. Скачанный файл сохраняй и работай
с ним, без повторного fetch.
<!-- /expect:curl-only -->

## Конфигурация проекта

`.oc3/project.yml`:

```yaml
sync:
  index_source: <raw-URL prompts/index.yml источника>
  index_sha: <hex — SHA-256 индекса на момент последней синхронизации>
  contract:
    key: agent-operational-contract-v3
    synced_sha: <hex>
    parts:
      skills: {<name>: <hex>}
      agents: {<name>: <hex>}
```

Manifest каждого модуля — `.oc3/modules/<key>.yml` со своими
`source`, `synced_sha`, `synced_at`, `provides` и `parts`; в `sync`
проекта модули не дублируются.

Части источника — skills (`skills/<name>/` в источнике) и субагенты
(`agents/<name>.md`) — хранят SHA в `parts` рядом с SHA источника. В
индексе у skill нет общего `raw`: запись содержит `files` с `raw` и
`sha256` каждого файла, `sha256` записи меняется при правке любого
файла.

Обязательный комплект задаёт декларация источника (`provides.skills` /
`provides.agents` либо раздел поставки), не наличие записи в `parts` и не
весь каталог. Декларация должна соответствовать актуальному SHA источника
из индекса. Если она неизвестна или относится к другой версии, получи
исходник по `raw`, сверь SHA и прочитай декларацию. Нет обязательной части
в индексе или не подтверждён её SHA — сообщи о проблеме, не объявляй sync
завершённым и не обновляй его checkpoints.

На каждой сверке проверяй наличие и SHA всех `files` поставляемых skills.
Совпавшие SHA индекса, контракта и checkpoint не доказывают целостность
локального каталога. `skills/<name>/…` источника ставится в
`.agents/skills/<name>/…`: замени префикс и сохрани относительные пути.
Отсутствующий или повреждённый файл и новый обязательный skill входят
в общий план. Project-skills не перезаписываются молча; неизвестные
локальные файлы не удаляются как якобы устаревшие части источника.
Доставка и проверка байтов не требуют загрузки полного текста всех skills
в контекст: инструкции читаются по триггеру задачи.

Свои расширения проекта в `.agents/` — роли, команды, скрипты,
автоматы, которых нет в `parts`, — обновление не трогает и не удаляет.
Совпало имя своей роли с новой ролью источника — стоп, вопрос
пользователю.

<!-- expect:skill-runs -->
Справка о моделях; skill запускает только объявленный `source-sync`.
Если в корне есть `manifest.json` моделей, он — локальный источник
дефолтов и исключений: синк его не заменяет и не включает в `parts`.
На стадии `refresh` адаптеры восстанавливают производные из manifest
без переписывания исходных ролей; отдельного запуска моделей этот
skill не добавляет. Явное ручное обслуживание через `ai models apply`
и `ai models check` описано в skill `cli`.

Без manifest сохраняется legacy override в `.oc3/project.yml` →
`roles.models`: синк его не трогает; ручная команда применения
возвращает настройки в файлы ролей и производные. В legacy-проекте
после замены поставленных ролей это отдельное явное действие человека
или оператора по справке `cli`, а не скрытый запуск из source-sync.
Правка `model` руками в
`.agents/agents/<name>.md` слетает — файл часть контракта.
<!-- /expect:skill-runs -->

## Развёртывание и миграция

Триггеры: «смигрируй на v3», «разверни контракт», «установи
контракт», «переведи проект на контракт v3» — это первый синк, а не
ручная сборка. Файлы контракта не собираются из удалённых текстов
руками: установку и миграцию делает установщик, состояние проекта
(«nothing | v2 | v3-partial | v3-ok») он печатает первой строкой.

1. Есть node/npm — запусти `npx @shahimat/oc3 init` в корне проекта.
   Чистая машина — создай минимальный `opencode.jsonc` с
   `"plugins": ["@shahimat/oc3"]` и перезапусти OpenCode: плагин
   доустановится сам без node/npm, установщик доступен его
   инструментом.
2. Установщик пишет ядро (AGENTS.md, каркас .oc3/, package.json,
   opencode.jsonc, .gitattributes/.gitignore). Вопросы, которые
   решает только человек (reality, реквизиты), он печатает списком —
   передай их пользователю, ответы верни повторным прогоном.
3. Окно ролей — сразу после установки, не «потом»: предложи
   подключение ролей (дефолт для operator-centric — researcher,
   executor, judge, librarian; watch-пара — только с модулем
   watchers) и передай выбор повторным прогоном
   `oc3 init --roles …` — установщик запишет агентов ролей и
   привязки в .oc3/skills.yml.
4. Миграция v2 → v3: структура — установщик; содержательный перенос
   очереди `context/views` в `.oc3/goals/*.expect.ts` — по отчёту
   миграции через librarian.
5. Верификация: повторный прогон установщика — «ok»; с node в
   проекте — проверка проекта по skill `cli`.

Cold-start без node/npm допустим: OpenCode сам ставит плагин из
конфига (`runtime: full`); `ai` CLI и harness-проверки требуют node —
без него проект помечается `runtime: degraded`, проверки недоступны.

## Обновление из источника

<!-- expect:sync-warns-deprecated -->
Ключи: «проверь обновления», «что нового в источнике», «обнови контракт»,
«синхронизируй», «обнови из источника».

1. Прочитай `sync.index_source`. Пусто — «источник не сохранён, пришли
   ссылку», дальше не идёшь. Получил ссылку — сохрани.
2. Процесс harness:
   <!-- expect:skill-runs -->
   <!-- metadata.runs: source-sync -->
   Если подключён harness — сценарий ведёт `ai source-sync
   start`. Он печатает текущую версию из `.oc3/ai-core.yml`, последнюю
   в npm и записи журнала пакета между ними (всегда, даже если индекс не
   менялся), и останавливается с заданием: шаги 3–8. После них —
   `ai source-sync open <id>`: harness пересоберёт адаптеры и
   `.oc3/bundles/index.md` и проверит проект; провал вернёт задание.
   <!-- /expect:skill-runs -->
3. `curl` тянет `index.yml`, считай SHA-256. Совпадение с `sync.index_sha`
   не завершает сверку: проверь обязательный комплект и локальные файлы.
4. Читай нужные записи индекса. Источники: контракт (`sync.contract.key`)
   и модули (`.oc3/modules/*.yml`); для каждого — декларация из проверенной
   версии источника с актуальным SHA и `parts` проекта.
5. Сравни `sha256` из индекса с сохранёнными:
   - совпал — исходник не перечитываешь целиком, но проверяешь его части;
   - разошёлся у контракта или модуля — `curl` тянет файл по `raw`,
      сверь SHA, полный diff, план миграции;
   - у skill проверяешь все `files` независимо от checkpoint: недостающие
     или не совпавшие по SHA получаешь по `raw`; к удалению — только
     подтверждённые файлы прежней поставки, которых больше нет в `files`;
   - разошёлся у субагента — тянешь файл по `raw`.

   SHA каждого скачанного файла сверяешь с индексом. Не совпал — стоп.
6. Дополнительно:
   - подключённый модуль, skill или субагент пропал из индекса —
     предупреди;
   - контракт или модуль помечен в индексе `deprecated` — предупреди и
     назови замену (ключ или путь из поля), миграция — по запросу;
   - `applicable_to` модуля больше не содержит
     `agent-operational-contract-v3` — предупреди;
   - контракт поменял список своих skills или субагентов — новые
      поставить, подтверждённые части прежней поставки удалить (в план).
   Только если harness актуален, источники и все обязательные части полны
   и совпадают — «без изменений», выход (с harness — resume).
7. Отчёт «Что нового» (ниже) и один блокирующий вопрос.
   <!-- expect:skill-runs -->
8. После «да»: применяешь план к артефактам контракта — `.agents/`,
   блоки `AGENTS.md`, manifest'ы `.oc3/modules/`, блок `sync` в
   `.oc3/project.yml`; локальный manifest моделей остаётся вне
   обновления, его производные восстанавливает стадия `refresh`.
   Правки слоёв
   документации проекта — только через librarian. После применения всего
   плана повторно сверь файлы поставки; только затем обнови
   `sync.index_sha`, `synced_sha` контракта и модулей, SHA в `parts`,
   `synced_at`; при обновлении harness — `version` в
   `.oc3/ai-core.yml`. Адаптеры и проверку с harness делает resume
   процесса (шаг 2), без harness — вручную.
   Неполную поставку не объявляй завершённым sync и не закрывай checkpoint
   отсутствующей части только по совпадению SHA её исходника.
   <!-- /expect:skill-runs -->
<!-- /expect:sync-warns-deprecated -->

## Отчёт «Что нового»

<!-- expect:update-report -->
Коротко, по разделам; пустой раздел не выводится:

- **Контракт и подключённые модули** — что изменилось, по строке на
  источник, и план миграции.
- **Новые модули** — подходящие по `applicable_to` и не подключённые:
  `title` и `feature.summary` из индекса.
- **Устаревшие и пропавшие** — `deprecated` с заменой, исчезнувшие из
  индекса.
- **Новые пресеты** — группа `presets` индекса, которых не было при
  прошлой сверке.
- **harness** — версия проекта → последняя и записи журнала между ними
  из первого шага процесса: новые команды и проверки.

Вопрос в конце — нумерованные варианты:

1. применить план обновления (и обновить harness, если отстал);
2. открыть чеклист `contract-setup` — включить новые или отключить
   ненужные возможности;
3. только отчёт, ничего не менять.

Сам ничего не подключаешь и не отключаешь: выбор — за пользователем.
<!-- /expect:update-report -->

## Проверка `key`

Тянешь контракт или модуль по прямой ссылке, не через индекс, — `key`
из frontmatter должен совпасть с сохранённым (`sync.contract.key` или
manifest модуля). Не совпал — стоп, не применяй: защита от подмены URL.

## Смысл

Одна просьба вместо пересылки ссылок. SHA-checkpoint экономит
токены: из десяти источников менялся один — читаешь и анализируешь
только его.

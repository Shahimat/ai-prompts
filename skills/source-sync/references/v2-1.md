# Синхронизация v2.1 с источниками

Протокол для контракта `agent-operational-contract-v2-1`: индекс источника,
SHA-256 и fetch только `curl`. Модулей и паттернов в v2.1 нет — есть контракт,
комплект skills и пакет `@shahimat/cli`. Роли, harness и установщик v3 не
запускаются. Установка и миграция на v2.1 — skill `contract-setup`; правила
структур данных — skill `data-structures`.

## Fetch: только curl и те же байты

```bash
curl -q -fsSL -H "Cache-Control: no-cache" -H "Pragma: no-cache" "<url>" -o "$tmp"
shasum -a 256 "$tmp" | awk '{print $1}'
```

WebFetch и аналоги для sync запрещены: кэш может вернуть старый ответ,
pre-processing и обрезка искажают raw-контент. Сохрани скачанный файл,
считай SHA от него и анализируй те же байты, без повторного fetch.

## Конфигурация

`.oc/project.yml` содержит:

```yaml
sync:
  index_source: <raw-URL prompts/index.yml источника>
  index_sha: <SHA-256 индекса>
  contract:
    key: agent-operational-contract-v2-1
    synced_sha: <SHA-256 контракта>
    parts:
      skills:
        <name>: <sha256 записи skill из индекса>
```

Каждый установленный исходный skill, обязательный или необязательный,
записывается в `parts.skills`. Обязательный комплект задаёт проверенный
`provides.skills` контракта; необязательные — выбор проекта. Первое
сохранение — при полной первичной поставке: `key` из проверенного frontmatter,
SHA из тех же raw-байтов. Далее используй сохранённый источник без
переспрашивания.

Пакет `@shahimat/cli` фиксируется точной версией в `devDependencies`
`package.json`; `npm view @shahimat/cli version` показывает опубликованную в
npm версию для сверки. Обновление версии пакета —
отдельный шаг плана: правка пина, `npm install`, затем `ai data check` из
корня проекта.

## Декларация и целостность

Обязательный комплект задаёт проверенный источник: `provides.skills`
контракта с актуальным SHA из индекса, не записи в `parts`. Если декларация
неизвестна или от другой версии, получи исходник по `raw`, сверь SHA и прочитай
её. Индекс контрактов сам по себе её не заменяет.

У skill нет общего `raw`: запись группы `skills` содержит `files` с `path`,
`raw`, `sha256` каждого файла и aggregate `sha256` записи. Ставь
`skills/<name>/…` источника в `.agents/skills/<name>/…` проекта: префикс
заменяется, внутренние пути сохраняются, байты совпадают с источником.

На **каждой** сверке проверяй наличие и SHA всех локальных `files`, даже при
неизменных SHA индекса, контракта, skills и checkpoint. Новая обязательная
часть, потерянный, повреждённый или изменившийся файл — расхождение плана.
Отсутствие checkpoint не делает обязательный skill опциональным.

Нет обязательной части в индексе или не подтверждён SHA скачанного файла —
сообщи о проблеме, не объявляй sync завершённым и не обновляй checkpoints.
Конфликт с одноимённым project-skill не разрешай тихой перезаписью; удаляй
только подтверждённые файлы прежней поставки, не неизвестные локальные файлы
и настройки. Доставленные инструкции не копируй в другие документы, их текст
для проверки файлов не читается — только по триггеру задачи.

## Команда «сверь всё»

Триггеры: «сверь всё», «сверь спецификацию с источниками», «синхронизируй»,
«обнови из источника», «проверь источник», «проверь обновления», «обнови
контракт».

1. Прочитай `sync.index_source`. Пусто — попроси ссылку, дальше не иди; при
   первом получении сохрани её в согласованном объёме.
2. `curl` получи индекс и посчитай SHA. Совпал с `sync.index_sha` — это не
   ранний выход: локальная полнота и целостность ещё не доказаны.
3. В индексе найди актуальный SHA контракта (`sync.contract.key`) и каждой
   записи из `parts.skills`. Сравни с `synced_sha` и сохранёнными SHA skills.
4. Совпало — не перечитывай исходник целиком; разошёлся контракт — получи
   `raw`, сверь SHA, сделай полный diff и план миграции по протоколу v2.1
   skill `contract-setup`; разошёлся skill — получи изменённые файлы, сверь
   SHA и опиши, что меняется для проекта. Независимо проверь все локальные
   файлы skills. Недостающие или несовпавшие скачай по их `raw`, сверь SHA;
   поставку нового skill и удаление подтверждённых устаревших файлов включи
   в тот же план.
5. Пакет: сравни пин в `package.json` с `npm view @shahimat/cli version`; в
   npm версия новее — внеси обновление в план отдельным пунктом.
6. Источник или обязательная часть пропали из индекса — сообщи; `deprecated`
   — предупреди и назови замену, но переход только по запросу.
7. Только если контракт, весь комплект и локальные файлы полны и совпадают —
   «без изменений» одной строкой.
8. Есть расхождения — единый конкретный план по файлам, с указанием
   затронутых структур, `AGENTS.md` и индекса. Дождись явного «да» до внесения
   правок; документацию не меняй по одному запросу на проверку обновлений.
9. Примени весь согласованный план, обнови маршрут и индекс проекта, повторно
   сверь поставку и прогони `ai data check`. Только затем обнови
   `sync.index_sha`, `sync.contract.synced_sha`, `parts` и `synced_at` —
   текущая ISO-дата. Неполная поставка не завершённый sync.

## Добавление необязательного skill

1. По запросу пользователя найди запись в группе `skills` индекса и прочитай
   `description`: по нему ясны назначение skill и вводит ли он свой слой.
2. Предложи план: `.agents/skills/<name>/…`, запись в `parts.skills`,
   триггер в `AGENTS.md` и секция `.oc/index.yml`, если skill вводит слой.
   Конфликт с одноимённым project-skill разреши в плане, не тихой заменой.
3. После «да» поставь файлы по их `raw`, сверь SHA, запиши в `parts.skills`,
   обнови маршрут и индекс. Проверь целостность; SHA сохраняй только после
   полной поставки.

## Удаление skill

1. По запросу пользователя покажи файлы поставки и все ссылки: `AGENTS.md`,
   `.oc/index.yml`, поле `skill` в `index.yaml` структур, другие skills.
2. Проверь владельца: не удаляй project-skill с тем же именем и содержимое
   слоя, созданное проектом; для него согласуй перенос или сохранение без
   потери знаний.
3. После «да» убери каталог поставки, запись `parts.skills` и ссылки, проверь
   целостность. Обязательный skill из `provides.skills` контракта отдельно не
   удаляется — только вместе с контрактом.

## Проверка key

Тянешь контракт по прямой ссылке, не через индекс, — сравни `key` frontmatter
с сохранённым `sync.contract.key`. Не совпало — стоп, сообщи и не применяй:
это защита от подмены URL.

Одна команда обходит все источники, а анализируется только разошедшееся.
Локальные файлы проверяются всегда; checkpoints экономят анализ, не подменяют
проверку полноты поставки.

# Модули самостоятельного v2

Опциональные модули — самостоятельные промпты `prompts/modules/<key>.md`
источника `ai-prompts`. Они не заменяют обязательный комплект skills v2.
Скачивание, SHA, checkpoints и обновление файлов — [v2.md](v2.md).

## WRITE > UPDATE

Модуль только добавляет слои, файлы, правила, поля, сценарии и проверки
непротиворечивости. UPDATE существующих правил и файлов базы запрещён;
исключение — регистрация ссылок на самого себя в `context/index.yml`
и обновление собственного manifest. Нужно поменять базу — это правка
самого контракта в источнике, не опциональный модуль.

Модуль может вводить слои под `docs/`, `context/` или в корне, свои виды
сущностей с `kind`, новые conventions, дополнительные сценарии workflow,
секции индекса и проверки целостности. Не может редактировать существующие
поля entity/behavior/manual/convention базы, переопределять порядок пунктов
тикета, базовые сценарии, семантику `verified` или правила полноты,
удалять и переименовывать сущности базы.

## Источник и manifest

Обязательный frontmatter модуля:

```yaml
key: <kebab-case>
kind: module
applicable_to: [agent-operational-contract-v2]
patterns: [source-sync]
title: <название>
use_case: <когда применять>
```

Текущий `sync.contract.key` должен входить в `applicable_to`; иначе
откажись от подключения. Формат `feature`, пресет и роли v3 не требуются.

След подключённого модуля — `context/modules/<key>.yml`:

```yaml
key: <key модуля>
source: <raw-URL модуля>
synced_sha: <SHA-256 источника>
synced_at: <YYYY-MM-DD>
provides:
  layers: [<введённые каталоги>]
  files: [<созданные файлы>]
  fields_in_index: [<добавленные секции context/index.yml>]
  skills: [<имена поставляемых skills, если есть>]
parts:
  skills:
    <name>: <sha256 записи skill из индекса>
```

Manifest — авторитетный след поставки; список skills не выводится только
из `parts`. В `sync` проекта модули повторно не записываются.

## Подключение

1. Получи источник по ссылке пользователя или его записи в индексе;
   сверь SHA и `key`, проверь применимость к действующей базе.
2. Прочитай модуль и предложи план: слои, файлы, skills, правила и ссылки.
   Пересекающиеся `provides` двух модулей — конфликт, не молчаливый merge.
3. После явного «да» создай согласованное, поставь объявленные части
   по правилам sync, создай manifest и обнови `context/index.yml`.
4. Проверь целостность; SHA источника и частей сохраняй только после полной
   поставки. Ничего из v3-runtime для этого не устанавливается.

## Обновление

Через «сверь всё» вместе с контрактом и остальными модулями. Совпадение
`synced_sha` исключает повторный полный анализ источника, но **не**
проверку обязательных частей и локальных файлов. Новый или повреждённый
skill исключает «без изменений»; diff и исправления — в согласованном плане.

## Отключение

1. По запросу пользователя прочитай manifest и покажи все части из
   `provides`, которые будут убраны, и затронутые ссылки индекса.
2. Перед удалением проверь владельца: неизвестные локальные файлы,
   project-skills, проектное содержимое и части, нужные контракту или другому
   модулю, не удаляются только по совпадению каталога. Для содержимого проекта
   согласуй перенос или сохранение без потери знаний.
3. После явного «да» убери согласованную поставку, её ссылки и manifest,
   сохрани разделяемые части и проверь целостность.

Два модуля заявляют один слой, файл, skill или секцию индекса — сообщи
конфликт. Варианты: отключить один, развести пересечение вручную или попросить
автора исправить модуль. Не выбирай сам и не удаляй пользовательское содержание.

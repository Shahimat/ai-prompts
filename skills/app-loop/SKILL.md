# app-loop

Приложение (слой `domain`: `docs/entities`, `docs/behavior`) и
предметный домен (`counterpart` из `context/modules/app-loop.yml` →
`answers`: `life` или `analysis`) связаны петлёй:

- мотивация течёт `<counterpart> → app`: фича существует ради
  потребности домена;
- данные текут `app → <counterpart>`: приложение измеряет или собирает
  то, на что опираются записи домена.

Правила `verified` — skill `domain`; форматы записей домена и прочие
провенансы — skill модуля `<counterpart>`.

## Маршруты

- зачем существует фича X → `serves` в `docs/entities/<id>.yml` /
  `docs/behavior/<id>.yml`;
- что автоматизирует потребность Y → `automated_by` в записи домена;
- можно ли доверять числу из приложения → провенанс записи, затем
  `verified` behavior-источника.

## Ссылки петли

Формат ссылки — `<kind>:<id>`: `kind` — тип записи (`entity`,
`behavior`, тип записи домена из skill `<counterpart>`, `goal`).

```yaml
# docs/entities/sleep-tracker.yml (приложение)
serves: [signal:sleep-depth, goal:better-sleep]

# запись домена (поле — из формата модуля life / analysis)
automated_by: [entity:sleep-tracker, behavior:sleep-depth-export]
```

- `serves` — у entity и behavior приложения: какой записи или цели
  домена служит фича. Поле — `extends.domain` этого модуля;
- `automated_by` — у записей и целей домена: какие entity / behavior
  приложения их обслуживают. Поле объявляет модуль домена, семантика —
  здесь;
- связь двусторонняя: `A serves B` ⇔ `B automated_by A`. Пишутся обе
  стороны в одной записи docs-keeper;
- `serves` у behavior — уже или равен `serves` его entities: behavior
  не служит тому, чему не служит ни одна его entity;
- ссылка — на существующий файл; удалили запись — чистится встречная
  сторона.

## Провенанс `app-telemetry`

Данные, которые приложение само измерило или посчитало, получают
провенанс `app-telemetry` (поле провенанса — из формата модуля домена).
Behavior-источник — behavior из `automated_by` записи, которая эти
данные производит.

- **доверие = `verified` behavior-источника**: запись с `app-telemetry`
  может быть `verified: true`, только если behavior-источник `verified:
  true`; иначе `verified: false`, `verified_note: "источник не
  проверен: <behavior>"`;
- behavior-источник сброшен в `verified: false` (skill `domain`) →
  зависящие записи домена теряют доверие: в той же фазе `verified:
  false` с той же пометкой;
- behavior-источник снова `verified: true` → доверие к записям
  восстанавливается проверкой самих записей, не автоматически.

**Транспорт ≠ провенанс.** Канал доставки (MCP, API, экспорт — модуль
`data-access`) не меняет авторитет материала. Книга из корпус-хранилища
по MCP остаётся первоисточником; число из API приложения —
`app-telemetry`, потому что его посчитало приложение, а не потому что
пришло по API. `app-telemetry` — только то, что приложение измерило или
посчитало само.

## Поле `domain` у целей

При `goal-domain-field: yes` (подключён `goals`):

- `domain: app | <counterpart>` — обязательно у каждой цели и подцели;
  программа — по своей платформенной работе (обычно `app`);
- app-цель может нести `serves` (какой цели или записи домена служит);
  цель домена — `automated_by` (если поле есть в модуле домена);
- множество `goal-consistency` — общее для обоих доменов.

## Выравнивание петли

Шестая проверка поверх пяти пунктов `goal-consistency` (skill `goals`),
в тех же точках прогона:

- цель или запись домена требует данных о показателе → есть ли запись
  домена и entity / behavior приложения, которые измеряют **именно этот
  показатель**;
- классический провал: цель «улучшить глубокий сон», а приложение
  логирует только время отхода ко сну;
- нашёл — одной строкой пользователю и варианты: завести измеряющую фичу
  (app-цель с `serves` на эту цель) или переформулировать цель под
  доступные данные.

## Проверки

Перед сохранением и в `audit`:

- **фича без `serves`** — entity приложения без `serves`: фича не
  привязана к потребности. Не выдумывай привязку — подними вопросом.
  Служебная инфраструктура (логирование, сборка, хранилище) служит
  через фичи, которые от неё зависят: `serves` у неё не требуется;
- **односторонняя связь** — `serves` без встречного `automated_by` или
  наоборот: рассинхрон, план исправления;
- ссылки петли — на существующие записи и цели;
- `app-telemetry` + `verified: true` → behavior-источник `verified:
  true`;
- выравнивание петли — по разделу выше.

Нашёл расхождение — не исправляй молча: отчёт и план через docs-keeper.

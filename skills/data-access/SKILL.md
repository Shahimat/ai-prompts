# data-access

Сырьё — снаружи, дистиллят — в git. Живые данные читаются только из
канала, объявленного в `context/data-access.yml`.

## Маршруты

- откуда взять данные Z → `context/data-access.yml` → `channels`, по
  `provides`;
- как устроены записи, которые опираются на данные, → skill модуля
  домена (и `app-loop`, если подключён);
- можно ли показать прочитанное → skill `privacy`, если подключён.

## Чтение

1. Нужен канал, которого нет в реестре, — не ищи обходной путь:
   предложи завести канал (запись через docs-keeper).
2. Запрашивай **минимальный срез**: нужный период, поля, агрегат — не
   «всё». Корпус — по главе или разделу, не книгой целиком.
3. Проверь **свежесть**: метку времени последней записи сравни с
   `freshness` канала и с вопросом. Устарело — скажи об этом и дату
   среза; старое за текущее не выдавай.
4. Отвечай выводами и агрегатами; сырые записи — по прямой просьбе.
5. Прочитанные значения не переносятся в документацию, примеры, логи,
   коммиты, CHANGELOG: в репозиторий попадает только производное знание
   по правилам слоя.

## Недоступность канала

Канал не ответил, ошибка авторизации, экспорта нет или он пустой:

- скажи прямо: «данных из `<name>` нет: <причина>», без чисел из
  головы, заметок или прошлых диалогов;
- предложи путь из `on_unavailable`, иначе — ручной ввод пользователем
  или починку канала;
- зависящее от данных утверждение остаётся `unknown` / `verified:
  false` с пометкой «канал недоступен» — не «додумывается»;
- не меняй `endpoint` и способ доступа сам — это правка реестра через
  docs-keeper после «да».

## Секреты

- в репозитории — только указатель `secret`: имя переменной окружения,
  запись keychain, запись менеджера паролей; ни значения, ни его части;
- конфиги инструментов, которые лежат в git (например, `.mcp.json`),
  ссылаются на переменные окружения, а не содержат токены;
- секрет пришёл в диалоге — не записывай и не повторяй; предложи
  пользователю положить его в хранилище и записать указатель;
- секрет попал в файл или коммит — стоп, сообщи пользователю: нужна
  ротация, правка истории — его решение.

## Реестр каналов

- одна запись — один канал; `name` стабилен: на него ссылаются записи
  и процедуры;
- `kind` — из `kinds` реестра; новый вид — через `contract-setup`;
- `freshness` — проверяемое утверждение («ежедневно; старше 2 суток —
  устарело»), не «по возможности»;
- новый внешний провайдер данных — решение для CHANGELOG с тегом `dep`
  (правила журнала — skill `docs-keeper`);
- канал выведен из оборота — запись удаляется, ссылки на `name`
  чистятся.

## Проверки

- нет полей со значениями, похожими на секрет (токены, пароли, ключи) —
  только указатели;
- у каждого канала заполнены `kind`, `endpoint`, `provides`,
  `freshness`, `secret`;
- `kind` входит в `kinds`;
- в `audit` — канал отвечает минимальным запросом; результат — в отчёт,
  не в файл.

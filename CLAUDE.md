# CLAUDE.md

Это репозиторий `ai-prompts` — личная коллекция промптов для работы с
AI-агентами. Ты (агент) читаешь этот файл первым, чтобы понять маршрут.

## Порядок чтения

1. Этот файл.
2. `README.md` — что за проект и как им пользуются.
3. `CONTRIBUTING.md` — правила добавления промпта.
4. `patterns/README.md` — модель переиспользуемых паттернов и как их
   применять.
5. `prompts/modules/README.md` — модель модулей расширения (надстройки
   над базовыми промптами).
6. `prompts/index.yml` — сгенерированный индекс всех промптов (ключи,
   пути, SHA-256, `applicable_to`). Читай для навигации и справки, но
   правда — в самих файлах.
7. Конкретные шаблоны в `patterns/<key>.md` — по мере необходимости.
8. Конкретные промпты в `prompts/<category>/<name>.md` и модули в
   `prompts/modules/<key>.md` — по задаче.
9. Skills в `skills/<name>/`, субагенты в `agents/<name>.md` и пресеты
   в `presets/<key>.yml` — то, что контракты и модули ставят в проекты;
   по задаче.

## Работа с промптами

Промпт — самодостаточный `.md`-файл, который скармливается агенту одной
ссылкой или копипастой. Формат и требования — в `CONTRIBUTING.md`.

Каждый промпт в frontmatter обязательно объявляет `kind`
(`contract` / `pattern` / `module` / `prompt`) и может декларировать
применённые паттерны:

```yaml
kind: contract
patterns: [source-sync, ...]
```

Паттерн — переиспользуемый блок правил, живущий в `patterns/<key>.md`.
Его содержимое инлайнится в тело промпта как раздел (гибрид «декларация
+ inline-копия»): промпт остаётся самодостаточным, но при этом ясно, что
это применение общего паттерна. Inline-копия может жить и в skill,
который промпт ставит в проект (так в v3: `goals` → skill `goals`).

Модуль — надстройка над конкретной базой, живёт в
`prompts/modules/<key>.md`. В отличие от паттерна не инлайнится в базу,
а подключается проектом-потребителем как отдельная сущность. Подробнее —
`prompts/modules/README.md`.

## Индекс промптов

`prompts/index.yml` — единый сгенерированный каталог всех промптов
репозитория (ключи, пути, raw-URL, SHA-256, `applicable_to`).
Используется проектами-потребителями для быстрой синхронизации через
`source-sync` (см. `patterns/source-sync.md`): проект тянет один
`index.yml`, сравнивает SHA всех подключённых источников и анализирует
только разошедшиеся.

**После правки любого промпта, паттерна или модуля — обязательно
запусти `npm run index:build`** и включи обновлённый `index.yml` в
тот же коммит. CI проверяет консистентность через `npm run index:check`
и валит билд при рассинхроне.

Индекс собирает harness (`packages/harness`, TS). Нужен
Node ≥ 24; перед первым запуском — `npm ci && npm run build`.

После правки TS-кода (`packages/`, `expectations/`) — `npm run ci`:
format, сборка, typecheck, lint, тесты, индекс и ожидания одной
командой; CI запускает ровно её. Строгость TS — в общем
`tsconfig.base.json`; линтер — oxlint с type-aware правилами
(`.oxlintrc.json`); формат — prettier (`npm run format`), только TS,
JSON и YAML: markdown промптов он не трогает (`.prettierignore`).

**Неявные преобразования запрещены — как принцип.** Никаких `as T`
(кроме `as const`), `!`, `any`, приведения к boolean / строке / числу
и `==`. Данные извне (JSON, YAML, frontmatter, ошибки в `catch`)
сужаются проверками — `shared/guards.ts` в harness и
`expectations/shared/guards.ts`;
неверная форма — ошибка с путём к полю. Линтер это проверяет, но
принцип шире линтера: обходы (`as unknown as T`, отключение правила)
— только по согласованию.

**Пути вверх по дереву (`../`) запрещены.** Внутри пакета — алиасы
`#…` из поля `imports` его `package.json` (`#shared/guards`, `#bin`):
условие `source` ведёт в `src/*.ts`, без него — в `dist/*.js`; файлы
рантайма — через `import.meta.resolve('#…')` или `import.meta.dirname`.
Исходники `.ts` голым Node — с `--conditions=source`.

**Комментарии в коде запрещены**, кроме якорей `// expect:KEY` и
shebang: пояснения — в именах, ожиданиях и README. Правило
`local/no-comments` (`packages/oxlint-plugin.ts`), `oxlint --fix`
удаляет лишние.

**Слои harness** (`packages/harness/src`), импорт только вниз:
`shared` → `lib` → `commands` → `scripts` → `harnesses`.

- Команда — атомарная операция; другие команды, скрипты и harness не
  вызывает.
- Скрипт — только последовательность команд (данные `ScriptDef`, их
  исполняет `scripts/run.ts` по реестру `scripts/commands.ts`).
- Harness — автомат с плоским именем `категория-вид` (`plan-review`,
  `docs-delta`, `source-sync`). Живёт в одном каталоге
  `harnesses/<имя>/`: `harness.yaml`, критерии и промпты рядом с кодом.
  Ядро `harnesses/core` не зависит ни от одного конкретного harness,
  harness не импортируют друг друга; каталог `harnesses/index.ts`
  регистрирует модули (`HarnessModule`).
- CLI harness — под его именем: `harness <имя> start | open <id> | list
  | status <id> | validate | graph`. id сессии — sha256, в выводе 7
  символов, команды принимают префикс от 4. Пауза — выход: `open` заново
  выполняет действие текущего состояния; в состоянии агента (`handoff`)
  это приём задания, из `failed` — повтор со сбросом счётчиков.
- Harness не использует контекст вызывающей сессии: входы — аргументы
  `start`, файлы проекта и ответы, записанные в сессию.
- Skill запускает не больше одного: скрипт, команду или harness —
  `metadata.runs` во frontmatter. Каждое упоминание команды harness в
  skill — в регионе `<!-- expect:skill-runs -->`, первый регион несёт
  `<!-- metadata.runs: … -->`: судья сверяет текст с объявлением.
  Несколько команд — через скрипт (`refresh`) или harness
  (`docs-delta`, `source-sync`). Субагент команд не запускает — только
  его skill.
- Снаружи слайс `commands/<x>` или `harnesses/<x>` виден только через
  свой `index.ts`. Модуль `shared` нужен хотя бы двум слайсам, иначе
  он переезжает в скоуп единственного.
- Узел дерева CLI объявляет вид (`command` / `script` / `harness`) и
  эффект: `query` не меняет файлов, кроме кэша по содержимому вне git,
  `mutation` пишет. CI и модель внутри состояния harness получают только
  query; skills в состояниях недоступны.
- Плагины пользователя (`~/.config/harness/.../handlers/`) линтер не
  видит: их границы — ответственность автора.

Грубые запреты — `no-restricted-imports` в `.oxlintrc.json`, полные —
ожидания `[harness] layers`.

## При добавлении или правке промпта

Перед планом:

1. Прочитай `patterns/README.md` и список файлов в `patterns/`.
2. В плане перечисли применимые паттерны с одностроковым trade-off
   каждый.
3. Одной строкой — свою рекомендацию: какие применяем.
4. Жди моего выбора. Не применяй паттерны молча.

При обновлении промпта, у которого в frontmatter уже задекларированы
паттерны — сверь его inline-секции с текущим содержимым соответствующих
`patterns/<key>.md`. Если паттерн обновился, а inline-копия отстала —
подними это в отчёте и предложи план миграции.

## Worktrees

Параллельная работа над разными промптами ведётся в отдельных git
worktree — одна задача, одна ветка, один worktree.

- Worktrees живут в `.claude/worktrees/<name>` (создаются через
  `claude --worktree <name>` или `EnterWorktree`). Каталог уже
  игнорируется через `.claude/` в `.gitignore`.
- `.worktreeinclude` в корне перечисляет игнорируемые файлы, которые
  копируются в каждый новый worktree (локальные настройки агента).
- В новом worktree сначала `npm ci && npm run build`: `node_modules/`
  и `dist/` у каждого worktree свои, через `.worktreeinclude` их не
  копируем.
- `npm run index:build` запускай внутри своего worktree: у каждой
  ветки свой `prompts/index.yml`. При конфликте в `index.yml` после
  merge — не правь руками, а пересобери той же командой.
- После merge ветки worktree удаляется (`git worktree remove`).

## Публичные npm-пакеты

`packages/*` публикуются в npm (`@shahimat/harness`,
`@shahimat/expectations`); публикует пользователь, когда сам решит.
Неопубликованная версия — не блокер и не повод для напоминания: о
публикации не напоминаешь и работу ею не обусловливаешь.

- Перед повышением версии — проверь, опубликована ли текущая:
  `npm view @shahimat/<пакет> versions`. Не опубликована — версию не
  повышай, изменения копятся в ней: одна неопубликованная версия на
  пакет.
- Изменения версии — запись в `CHANGELOG.md` пакета: верхний раздел
  `## <версия>` совпадает с `version` в `package.json`.
- Проверяют ожидания репозитория (`expectations/ai-prompts.expect.ts`).

## Ожидания

`expectations/<key>.expect.ts` — ожидания пользователя к промпту в форме
vitest: заголовок `it` (≤ 200 символов, проверяемо да/нет или числом) —
ожидание, тело — проверка. Общие ожидания этого репозитория —
`expectations/shared/`; общие для всех проектов (правила работы агента,
например `ticketCommits`) — пакет `@shahimat/expectations`
(`packages/expectations`): единый текст, каждый проект проверяет
им свои файлы. Каркас в другом проекте — `harness expect init`.

Точка входа одна: `expectations/index.expect.ts` импортирует файлы
ожиданий, `npm run expect`, CI и судья прогоняют только его
(`harness expect report <file>`). Новый файл ожиданий подключается
строкой `import` в точке входа; общий блок вне `*.expect.ts` объявляет
разделы через `describe` из `@shahimat/harness/expect`. Отчёт, бюджет и
проверка заголовков — по модулю, где объявлено ожидание.

- Форма файла: сверху `budget({ crit, warn })` и `describe` с
  `crit(...)` / `warn(...)` — заголовок и вызов `() => Check.<имя>()`;
  ниже — класс `Check` со статическими проверками. Ожидания читаются
  без кода.
- Уровни: `crit` — формальные метрики (и редкие приоритетные правила
  через судью), `warn` — как правило судья, `info` — пояснения
  (`note(...)`, автоматически при метрике > 90% порога). Прогон
  блокируется, если crit или warn больше бюджета файла (по умолчанию
  0 / 0) или есть ожидания без свежего вердикта; info не блокирует.
- Пользователь правит заголовки (или пишет `it.todo('…')`), агент пишет
  и сопровождает проверки. Менять смысл заголовка без согласования нельзя.
- Пороги — из намерения пользователя, а не из текущей реализации:
  верхние границы («не больше N»), а не пересказ («ровно N»).
- Форматы данных (пресеты, frontmatter, provides, manifest,
  `context/harness.yml`) — JSON Schema в `expectations/schemas/`,
  проверка `expectSchema`.
- Проверка предпочтительно детерминированная (зонды
  `@shahimat/harness/expect`); смысловая — `judged(['@KEY'])`.
- Привязку к реализации держит реализация, а не ожидания: доказательство
  размечается якорем `<!-- expect:KEY -->` … `<!-- /expect:KEY -->`
  (markdown), строкой `# expect:KEY` (YAML) или `// expect:KEY` (TS).
  Переименование разделов и перенос текста ожидания не трогают — после
  коммита ожидания не правятся, правится следующий слой (промпты).
- `npm run expect` — дерево ожиданий со статусами. `?` — нет свежего
  вердикта: `npm run expect:judge` → задания судье рядом с точкой входа
  (`expectations/.judge/`; судья — отдельный субагент с чистым
  контекстом, не автор правки) → `npm run expect:apply`.
- `expectations/.verdicts.json` коммитится: CI проверяет свежесть
  вердиктов без LLM. Растёт только с числом живых смысловых ожиданий —
  `expect:judge` удаляет вердикты, которые не нужны ни одному из них.
- После правки промпта, skill или модуля — `npm run expect`; падение —
  либо реализация не та, либо ожидание устарело: решает пользователь.

## Тикеты и коммиты

<!-- expect:ticket-commits:repo -->
Тикеты и коммиты в этом репозитории — по `skills/ticket-commits/SKILL.md`
(тот же skill получают проекты на контракте v3): тикет из шагов по
типам karma, один коммит на шаг, подряд одного типа — `--amend`, режим
«пройти тикет целиком». Ниже — только особенности этого репозитория.

Типы применительно к этому репозиторию:

- `feat` — новый или изменённый промпт, паттерн, модуль;
- `fix` — исправление ошибки в существующем промпте / паттерне / модуле;
- `refactor` — перестройка без смены смысла (переименование, перекладка
  разделов);
- `docs` — `README.md`, `CONTRIBUTING.md`, `CLAUDE.md`, README в
  `patterns/` и `prompts/modules/`;
- `chore` — скрипты, CI, конфиги (`.gitignore`, `.worktreeinclude` и
  т.п.).

Формат сообщения: `type(scope): subject` на английском, scope — `key`
промпта / паттерна / модуля или затронутая область.

**Git-решения принимает только человек.** Коммиты, пуши, ветки, PR,
merge, rebase, reset, stash и прочие write-операции делает пользователь.
Агент выполняет их только по явной просьбе и только после того, как
пользователь подтвердил список конкретных команд. Вне сообщения коммита
в конце шага (там же — новый коммит или `--amend`) git-запись не
предлагаешь, о ней не напоминаешь и не спрашиваешь «закоммитить?».
<!-- /expect:ticket-commits:repo -->

## Внимание пользователя

<!-- expect:attention:repo -->
Внимание пользователя — самый дорогой ресурс. Вопрос — только когда без
его решения нельзя продолжить или откатить; остальное — строкой в
отчёте.

Промпты, паттерны, модули, skills и их README — доменная область этого
репозитория: их основная сессия правит сама, на них и тратит контекст.
Проектной документации в смысле контракта v3 (`context/`, журнал
решений, docs-keeper) здесь нет. Механическое (индекс, ожидания,
вердикты) ведёт harness, смысловую проверку — судья-субагент.
<!-- /expect:attention:repo -->

## Язык

Вся содержательная часть — на русском. Английский допустим в
идентификаторах, ключах frontmatter, именах файлов и общеупотребимых
технических терминах.

## Что не делаем

- Не переносим правила проекта в глобальную memory агента или в hooks
  вне репозитория. Всё, что важно, живёт в этом репозитории (принцип
  открытости).
- Не создаём и не правим файлы без явного «да» на конкретный план.
- Не переименовываем существующие `key` промптов и паттернов без
  согласования: на них могут ссылаться извне.

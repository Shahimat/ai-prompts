# Журнал @shahimat/harness

Свежее сверху. Одна версия — список новых команд и проверок.

## 0.4.0

- `docs-delta`: шаг `close` закрывает только дельту своей сессии.

- Роли автоматов видны во время работы: `docs-delta` и `ticket-work`
  пишут журнал прогона (`runs/<роль|состояние>-<n>.jsonl`) и ход по шагам
  (`progress.log`) по мере работы; в вывод команды — только строка
  запуска с путём журнала и итог, чтобы не раздувать контекст сессии.
  `ai ops status` показывает работающие роли (job, минуты, последний
  шаг), `ai ops brief` — сколько ролей в работе и в очереди машины;
  роли `docs-delta` идут через общий лимит моделей.

- Автомат `ticket-work` — работа по задаче вне сессии оператора:
  карточка из провайдера `tasks`, исследование, план с «да»
  пользователя, правка в копии от провайдера `vcs`, проверки из
  `context/ops.yml`, ревью по DoD с дословными цитатами, готовность к
  коммиту; `ticket-work answer <id> <текст>` — ответ на вопрос роли,
  план и готовность. Журнал хода и stream-json прогонов ролей —
  `.ops/jobs/<id>/`.
- Рантайм `ops` в ядре автоматов: `ai ops brief | status | wait`,
  наблюдатели `ops watch add | list | stop` с лестницей код → haiku →
  sonnet, `ops tick [--all]`, один планировщик на машину
  `ops schedule on | off | status` (launchd, systemd или свой
  провайдер), `ops act` — действие наружу по политике
  `context/autonomy.yml`, `ops serve` — HTML-доска с ответами из
  браузера.
- Провайдеры `tasks`, `vcs`, `review`, `checks`, `schedule`: встроенные
  `local`, `git`, `launchd`, `systemd`; свои — в проекте
  (`.agents/providers/`) или на машине (`~/.config/harness/providers/`).
- Общее на машину: реестр проектов, кэш опроса, поток событий, лимиты
  моделей (`~/.config/harness/ops/limits.yml`: jobs 4, opus 2,
  наблюдатели 1) с очередью по приоритету и паузой при rate limit.

- Пакет — только автоматы (harness): `docs-delta`, `source-sync`,
  `plan-review` и их ядро. Команды, скрипты, механизм ожиданий и роли
  выделены в `@shahimat/ai-core` (CLI `ai-core`); `harness` зависит от
  него. CLI `harness` знает только автоматы: `harness <автомат> start |
  open | list | status | validate | graph`. Паттерны ожиданий автоматов
  `harnessCommands` и `harnessChain` — в `@shahimat/harness/expect`
  (пакет `@shahimat/expectations` упразднён). Записи ниже до этой
  описывают команды, которые теперь живут в `ai-core`.
- Роли: субагент `agents/<name>.md` получает поля `model` и `output`
  (сообщение протокола `result` / `verdict` / `question`, JSON Schema —
  `PROTOCOL`). `role run <name> --file <задание>` — роль headless через
  `claude -p` пользователя: без его настроек, единственный MCP — канал
  `role channel` с инструментом `submit_result`, ответ проверяется по
  схеме, невалидный возвращается модели с путём к полю.
- `expect judge --run` — задания судьи отвечает роль `judge`, затем
  `--apply`. `docs-delta start --file <намерения>` — `apply` выполняет
  роль `docs-keeper`; без файла или при провале роли — handoff агенту,
  как раньше. `adapters sync` переносит `model` роли в `.claude/agents/`.
- `plan-review` заморожен: работает как есть, не развивается.
- `docs-delta`: состояние `review` после `verify` — роль `judge` ищет
  противоречия правки с остальной документацией, цитаты сверяются
  дословно; противоречия возвращают в `apply` с находками в задании.
  `--file <намерения | ->` — намерения по схеме `intents` (JSON или
  YAML, файл или stdin) хранятся в сессии, а не в файле проекта.
- `plan-review` — планер ожиданий: результат — файл ожиданий `<file>`.
  Автомат `awaiting_input → gathering → composing (↔ clarify_form) →
  review → analyze`; события выводит новая команда
  `plan-review hook <id> <hook>` из hooks интерактивной сессии планера
  (UserPromptSubmit, PreToolUse, PostToolUse, Stop, SessionEnd), модель
  событий не объявляет. Ревью — `expect judge` по файлу, судья headless
  без сети и записи, итог по бюджету файла; лимиты `cycles` и `build`.
  Выход — сообщение «выход» в `awaiting_input` или флаг
  `[plan-review: exit]` в ответе планера после чистого ревью, после
  выхода harness сам закрывает сессию планера; Ctrl+C и Ctrl+D — пауза
  в любом состоянии, `open <id>` продолжает через `--resume`.
  В `harness.yaml` модели — `planner` и `judge`; сессия ядра не хранит
  полей конкретного harness.
- Сессия планера поднимает страницу плана (`expect serve` на свободном
  порту) и открывает её в браузере; адрес — в промпте планера и в ответе
  чистого ревью. Bash планера — только `expect report` своего файла,
  остальное блокирует hook; ответ на `Stop` — JSON `decision: block`. В
  промпте планера — справочник блоков с собираемым примером. Ход без
  записи файла — переход `gathering → replied → awaiting_input`, флаг
  выхода читается и после него. Имя сессии планера —
  `plan-review · <имя плана>`.
- Страница плана: `info.title`, `info.subtitle`, `info.text` — заголовок,
  подзаголовки и текст в порядке объявления; `info.stats('crit' | 'warn')`
  — виджет «пройдено · заглушки · не пройдено · всего»;
  `info.questions([...])` — «Вопросы и предложения» с рекомендуемым
  вариантом и комментарием во всплывающей подсказке; блок «Замечания»
  (`info.remarks()`) — находки судьи и нарушения плана; без `info.remarks()`
  блока нет, а `expect report` пишет число замечаний и просит добавить
  блок. Находка судьи по
  ожиданию-заглушке (`todo`, `wip`) видна, но прогон не блокирует. Рендер
  не добавляет своих заголовков и сводок, кроме разделов `fsm`.
- Блок `fsm`: подпись входа `start`, вход и выход ярким цветом,
  `description` состояния, подпись варианта перехода `label`,
  `fsm.entry(...)` — ожидания к входу, `transition(from, event, body, to)` —
  к варианту перехода. На странице: состояния пользователя фиолетовым с
  легендой, разделы «Состояния» и «Переходы», кликабельные узлы и
  переходы, карточки `A → B [событие]`, локальный граф соседей, возврат на
  схему с подсветкой узла.
- `harness expect serve` сам обновляет открытую страницу при изменении
  файлов проекта (SSE), позиция прокрутки сохраняется; страница
  собирается в отдельном процессе — свежий код рендера без перезапуска.
  Отметки относительно HEAD собираются без записи в проект: HEAD-версия
  файла ожиданий подменяется при загрузке модуля, копии рядом нет.
  `harness expect report <file> --html -` — HTML в stdout.
- Корень проекта для команд harness (`plan-review`, `docs-delta`,
  `source-sync`): без `--root` — первый каталог с `.claude` вверх от
  места вызова; домашний каталог (`~/.claude` — настройки Claude Code)
  проектом не считается. Без `.claude` в проекте `start` не стартует и
  ничего не создаёт. Проектные команды по-прежнему работают в текущем
  каталоге.
- `harness plan-review start <file>` — план в файле ожиданий: существующий
  файл — план изменения его состояния, нового нет — создаётся каркас с
  `plan({ name })`. Имя плана — из `plan({ name })` в файле, для нового
  файла — из имени файла; путь — относительно корня проекта. Запрос
  `start` не спрашивает: без `--request` его пишут в интерактивной
  сессии планера — текст, файлы, картинки; с `--request` текст уходит
  планеру первым сообщением.
- `pattern(key, apply)` в `@shahimat/harness/expect` — паттерн ожиданий:
  функция с параметрами, которая регистрирует ожидания для переданных
  целей. Ожидания приписываются файлу, применившему паттерн, в HTML у
  них виден ключ паттерна.
- Одна точка входа ожиданий: `harness expect report | lint | judge |
  serve <file>` прогоняют ровно переданный файл, остальные ожидания
  попадают в прогон только через `import` в нём. Конфиг vitest — из
  пакета: проекту не нужен свой `expectations/vitest.config.ts`.
  Отчёт, бюджет и проверка заголовков судьёй — по модулю, где объявлено
  ожидание. Вердикты и задания судьи — рядом с точкой входа
  (`<каталог>/.verdicts.json`, `<каталог>/.judge/`). `expect init`
  создаёт `expectations/index.expect.ts`, скрипты передают его.
- План в форме ожиданий (`@shahimat/harness/expect`) — блоки в файле
  ожиданий, вид страницы задают они. `plan({ name })` — имя плана
  (сессия, вкладка браузера); шапка страницы — только `info.title`, без
  неё `expect report` просит её добавить. `steps(() => { step(id, { title, after,
  why }, body) })` — шаги плана, ожидания шага — DoD; статус шага
  выводится из ожиданий: все `todo` — не начат, все без заглушек и
  зелёные — готов, иначе — в работе; готовый шаг раньше шагов из `after`
  и циклы шагов — нарушение. Заглушки: `crit.todo` / `warn.todo` — не
  взято, `crit.wip(title, fn?)` / `warn.wip` — в работе: проверка
  исполняется, если есть, провал не блокирует. `fsm(name, { initial,
  limits, states })` — автомат данными с типами имён: `state`,
  `transition` и `whole` привязывают ожидания к узлу, переходу и
  автомату, опечатка — ошибка typecheck. Зонды `Graph.sameAs` (сверка с
  `harness.yaml`), `Graph.canReach`, `Graph.onlyVia`. Блоки и ожидания
  из импортированных файлов попадают на страницу; у ожидания из общего
  блока видно, где оно определено. Файл, не собранный vitest, — нарушение
  с текстом ошибки, а не пустой отчёт.
- `harness expect report <file> --html <out>` — HTML без сети и
  без JS: блок `fsm` — схема, блок `steps` — UML-диаграмма активностей,
  обе — SVG Graphviz (`@hpcc-js/wasm-graphviz`),
  узел и переход ведут к карточке, цвет — статус ожиданий; новые,
  изменённые и удалённые относительно HEAD ожидания отмечены.
- `harness expect serve <file> [--port <n>]` — тот же HTML с
  локального сервера на `127.0.0.1`: страница собирается при каждом
  запросе, файлов не пишет; артефакт плана — только файл ожиданий.
- CLI harness — под его именем: `harness <имя> start | open <id> | list
  | status <id> | validate | graph`; неймспейсы `plan` и `session`, а с
  ними `resume` и `retry`, убраны. id сессии — sha256, в выводе 7
  символов, команды принимают уникальный префикс от 4. Пауза — выход:
  `open` заново выполняет действие текущего состояния, в состоянии агента
  это приём задания, из `failed` — повтор со сбросом счётчиков.
- Плоские имена harness `категория-вид`: `plan-review` (бывший
  `plan/iter`), `docs-delta`, `source-sync`. Harness живёт в одном
  каталоге `src/harnesses/<имя>/`: `harness.yaml`, критерии и промпты
  рядом с кодом, в пакет — внутри `dist`. Переопределения пользователя —
  `~/.config/harness/harnesses/<имя>/`. Код пакета — в `packages/`.
- Скрипт `harness refresh`: `context index`, `adapters sync`, затем
  шаги `check`.
- Harness агента `docs-delta` (`harness docs-delta start --name
  <дельта>`) и `source-sync` (`harness source-sync start`): в состоянии
  агента harness останавливается с заданием, `open` продолжает.
- Слои пакета: `shared` → `lib` → `commands` → `scripts` → `harness`.
  Узел дерева CLI объявляет вид (`command`, `script`, `harness`) и эффект
  (`query` или `mutation`); эффект скрипта выводится из его шагов.
  `harness check` — скрипт из `changelog lint`, `context check`,
  `adapters check`, `secrets scan`: каждый шаг печатает свой итог, общий
  итог — строкой `check (…): ok | есть нарушения`. Точка входа
  `@shahimat/harness/expect` — `dist/lib/expect/`.
- `harness context check` и `harness adapters check` — сверка
  `context/index.yml` и файлов адаптеров без записи: то же, что проверяет
  `harness check`, отдельной командой.
- Проверка `secrets` и команда `harness secrets scan [--file <path>]`:
  ключи API, токены, пароли, приватные ключи в отслеживаемых файлах или
  в файле по пути. В `harness check` включена по умолчанию, выключается
  `secrets: false`; исключения — `checks.secrets.allow` с `reason`.
- Планер `plan-review`: `harness plan-review start <file>` и общие
  команды harness, своя — `hook <id> <hook>`. Автомат из `harness.yaml`
  (схема `harness-fsm`), плагины `handlers/`, сессии в
  `~/.config/harness`. Модель в любом
  состоянии, включая интерактивного планера, — без skills
  (`--disable-slash-commands`) и только с перечисленными инструментами
  (`--tools`).
- `list` и `help` на каждом уровне дерева команд; без аргументов в
  терминале — оболочка с переходом по уровням.
- `harness delta check | close` — дельта документации `context/.delta/`:
  удаление или изменение знания без пункта `revise` — нарушение; `close`
  удаляет принятую дельту. `context index` не читает `context/.delta/`.
- Справка и разбор команд — из декларативного дерева `COMMANDS`.
- `harness outdated` — версия из `context/harness.yml` против последней в
  npm и записи этого журнала между ними.
- Якоря доказательств `@KEY`: `<!-- expect:KEY -->` (markdown),
  `# expect:KEY` (YAML), `// expect:KEY` (TS).
- Ключ вердикта судьи — заголовок + доказательства.
- `expect judge` удаляет из `.verdicts.json` вердикты, которые не нужны
  ни одному текущему ожиданию: кэш не растёт с историей правок.
- `expect` работает строго от `--root`: кэш вердиктов и доказательства не
  читаются из текущей папки.
- `skill(name).description` — пустая строка, если `description` во
  frontmatter не строка (раньше `[object Object]`); `index_layers` с
  нестроковым `format` — значение в диагностике как JSON.
- Данные извне (`.verdicts.json`, `plan.json`, ответы судьи, отчёт vitest,
  npm registry, `answers` модулей и поля пресетов) проверяются по форме:
  неверная форма — ошибка с путём к полю, а не молча принятое значение.

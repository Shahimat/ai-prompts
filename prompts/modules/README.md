# Модули расширения промптов

Модуль — переиспользуемое расширение одного или нескольких базовых
промптов (обычно контрактов агентов). Живёт в `prompts/modules/<key>.md`.
В отличие от паттернов (`patterns/`) — модуль не про блоки правил,
переиспользуемых между разными промптами, а про **опциональную
надстройку одного конкретного базового промпта** для проектов, где эта
надстройка нужна.

## Модель

- **База** (обычно контракт) фиксирует минимум, обязательный в любом
  проекте.
- **Модуль** добавляет специфический слой / правила / сущности для
  подмножества проектов, где эта область актуальна.
- Проект-потребитель подключает модуль явно, зная зачем.

Пример: `agent-operational-contract-v2` — универсальная база. Модуль
`knowledge-external-gui` — для проектов, где нужно работать с GUI
внешних систем без API. Backend-only проекту этот модуль не нужен.

## Правило WRITE > UPDATE

Модуль только **добавляет**: новые слои, файлы, правила, поля,
сценарии workflow, типовые проверки внутренней непротиворечивости.

Модуль **не редактирует** существующие правила, поля, файлы базы.
Единственный разрешённый UPDATE — обновление ссылок на самого себя
(регистрация в `context/index.yml`, обновление собственного manifest'а).

Если модулю нужно поменять что-то в базе — это уже не модуль, а PR в
саму базу.

## Обязательный frontmatter модуля

```yaml
---
key: <kebab-case, стабильный идентификатор>
kind: module
applicable_to: [<base-key>, ...]
patterns: [source-sync]
title: <человекочитаемое название>
use_case: <одна строка — в какой ситуации модуль применяется>
tags: [<теги>]
---
```

Поля:

- `key` — стабильный kebab-case. Один раз выбран — не переименовываем
  без явного согласования: на него могут ссылаться manifest'ы
  подключённых проектов.
- `kind: module` — обязательное значение для промптов в
  `prompts/modules/`.
- `applicable_to` — обязательный список ключей базовых промптов, к
  которым модуль применим. Агент отказывается подключать модуль к базе,
  чей `key` не входит в `applicable_to`.
- `patterns: [source-sync]` — обязательно. Модули синхронизируются вместе
  с базой через общий индекс.
- `title`, `use_case`, `tags` — как у обычного промпта.

### Блок `feature` (модули ядра v3)

Модуль, который предлагается в чеклисте контракта
`agent-operational-contract-v3`, объявляет:

```yaml
feature:
  summary: <одна строка для чеклиста>
  default: true | false          # отмечен ли по умолчанию
  requires: [<ключи модулей>]
  conflicts: [<ключи модулей>]
  asks:                          # уточняющие вопросы после выбора
    - key: <kebab-case>
      question: <текст>
      multi: true | false
      options: [...]
```

`summary`, `default`, `requires`, `conflicts` попадают в
`prompts/index.yml`: чеклист строится по индексу без скачивания модулей.
`asks` агент читает из самого модуля. `index build` падает, если
`requires` / `conflicts` указывают на несуществующий модуль или на сам
модуль.

Модуль v3 делится на две части: сам модуль — что и как ставить; skill
модуля (`skills/<name>/`) — правила работы со слоем во время работы.
В `provides` модуля v3 добавляются:

- `skills`, `agents_md_block`, `harness_checks`;
- `index_layers` — слои, которые `harness context index` включает в
  `context/index.yml`: `section`, `dir` и `format` — `md` (frontmatter
  `id`, `namespace`, строка индекса — первый `# …`) или `yml` (поля
  `id`, `namespace`, `summary`); `id` = путь внутри слоя без
  расширения, `/` → `-`;
- `extends` — поля, которые модуль добавляет в слои других модулей:
  `{domain: [serves], goals: [domain]}`; два модуля с одним полем —
  конфликт;
- `changelog_tags` — теги журнала решений модуля в дополнение к тегам
  ядра;
- `gitignore` — строки, которые модуль добавляет в `.gitignore`
  (локальные, машинно-зависимые файлы); при отключении убираются, если
  их не объявляет другой подключённый модуль.

Правила модуля с приоритетом (безопасность, атрибуция, приватность)
пишутся целиком в его блок `AGENTS.md`: строки блока обязательны
наравне с жёсткими правилами ядра. Если правило должно соблюдаться и
приложением — паттерн `guardrail-dual-level`.

## Структура тела модуля

Модуль пишется как самостоятельный документ: скармливается агенту как
инструкция «применить это к проекту, где подключена соответствующая
база». Тело обычно содержит:

1. **Назначение и границы.** Когда модуль применяется, что он делает,
   чего не делает.
2. **Что модуль добавляет в проект.** Новые слои (`docs/...` /
   `context/...`), новые правила, новые проверки, новые сценарии
   workflow.
3. **Формат новых сущностей.** YAML-шаблоны, обфусцированные примеры,
   правила именования, поля.
4. **Правила использования.** Reactive-протоколы, workflow при
   расхождениях, что фиксировать / что не фиксировать.
5. **Секция `provides`** — авторитетный список того, что модуль
   привносит в проект-потребитель. Используется агентом при подключении
   для создания `context/modules/<key>.yml` и при отключении — для
   зачистки. Формат:

   ```yaml
   provides:
     layers:
       - <путь к папке-слою>
     files:
       - <конкретные файлы>
     fields_in_index:
       - <секции в context/index.yml>
   ```

## Подключение модуля в проекте-потребителе

Механику полностью описывает базовый промпт (см. раздел «Модули
расширения» в `agent-operational-contract-v2`). Кратко:

1. Пользователь даёт ссылку на raw-версию модуля.
2. Агент через `source-sync` тянет источник, сверяет `key` и
   `applicable_to`.
3. Читает содержимое, предлагает план — какие слои и файлы будут
   заведены.
4. После «да» — заводит файлы, создаёт `context/modules/<key>.yml` с
   manifest'ом на основе секции `provides`, обновляет `context/index.yml`.

## Обновление и отключение

- **Обновление.** Через обновление из источника — `source-sync`
  проходит по контракту и всем модулям одной цепочкой, тянет только
  разошедшиеся источники (SHA-256 checkpoint).
- **Отключение.** Агент читает `provides` из manifest'а, показывает
  список файлов на удаление, после «да» удаляет их + чистит
  `context/index.yml` + удаляет сам manifest.

## Конфликты между модулями

Если два подключённых модуля объявляют пересекающиеся `provides` (тот
же слой, тот же файл, ту же секцию `context/index.yml`) — конфликт.
Ловится при подключении второго модуля или при синхронизации. Молча не
мержим: стоп, поднимаем конфликт пользователю.

## Отличие от паттернов

- **Паттерн** — переиспользуемый блок правил, применимый к **разным**
  промптам. Пример: `source-sync`. Живёт в `patterns/`, декларируется в
  frontmatter промпта полем `patterns: [...]`, инлайнится в тело промпта
  как раздел.
- **Модуль** — надстройка над **конкретной** базой (или несколькими
  базами через `applicable_to`). Живёт в `prompts/modules/`, не
  инлайнится в базу, а работает в проекте-потребителе как отдельная
  подключённая сущность со своим manifest'ом.

Паттерн может использоваться модулем (например, все модули обязаны
применять `source-sync`), но не наоборот.

## Список текущих модулей

- [`knowledge-external-gui`](knowledge-external-gui.md) — работа с GUI
  внешних систем без API. Применим к v2 и v3.
- [`code-rules-fullstack-js-ts`](code-rules-fullstack-js-ts.md) —
  правила стиля кода на fullstack js/ts, пакетом в подпапке
  `context/conventions/code/`. Применим к v2 и v3.
- [`domain`](domain.md) — entities и behavior с `verified`. v3.
- [`manuals`](manuals.md) — ручные процедуры для человека. v3, требует
  `domain`.
- [`goals`](goals.md) — цели и программы как очередь работы. v3.
- [`harness`](harness.md) — проверки и генерация через
  `@shahimat/harness`. v3.
- [`worktrees`](worktrees.md) — параллельные сессии в git worktree. v3.
- [`ticket-commits`](ticket-commits.md) — тикеты из шагов-коммитов по
  типам karma, `--amend`, режим «пройти целиком»; `mode: off` отключает
  правило в проекте. v3, по умолчанию включён.
- [`app-loop`](app-loop.md) — петля «домен ↔ приложение»: `serves` /
  `automated_by`, `app-telemetry`, выравнивание целей. v3, требует
  `domain`.
- [`data-access`](data-access.md) — каналы к внешним данным в
  `context/data-access.yml`. v3.
- [`privacy`](privacy.md) — приватность как правило агента и
  приложения. v3.
- [`life`](life.md) — домен жизни: факты, сигналы, протоколы. v3,
  требует `privacy`.
- [`safety-boundaries`](safety-boundaries.md) — агент не врач;
  тревожный признак — стоп и помощь. v3.
- [`analysis`](analysis.md) — источники, тезисы, позиции, разборы,
  противоречия; целостность атрибуции. v3.
- [`book-corpus`](book-corpus.md) — загрузка книг в анализ. v3, требует
  `analysis`, `data-access`.
- [`external-context`](external-context.md) — оверлей поверх живого
  проекта: системы, оргправила, процессы, аудит ссылок. v3, требует
  `domain`.

Пресеты из этих модулей — `presets/` в корне репозитория, по виду
проекта: `operational`, `external`, `private`, `analytical`.

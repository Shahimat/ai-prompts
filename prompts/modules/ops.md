# Модуль ops — jobs по задачам

## Назначение

Субагенты сессии не подходят для параллельных долгих работ: умирают
вместе с процессом, итоги копятся в контексте, журнала нет. Поэтому
работа по задаче — **job**: сессия автомата `ticket-work` на диске,
роли — отдельные процессы. Оператор запускает job, получает события и
пересказывает их пользователю; рестарт оператора job не останавливает.

Рантайм запускает роли через `claude -p` — только Claude Code. Роли
ядра и протокол оператора нейтральны к агенту. Модуль добавляет роль
`implementer` — правку в копии репозитория; `researcher` и `reviewer` —
из ядра.

### Путь job

1. `intake` — провайдер `tasks` даёт карточку `task.md` (заголовок,
   DoD, ссылки, текст). Карточка без DoD в работу не берётся — вопрос
   пользователю.
2. `research` — роль `researcher`, отчёт `research.md`.
3. `plan` → `plan-gate` — роль `implementer` пишет `plan.md`; пауза до
   «да» пользователя, замечание — новый план. «да» с хвостом — согласие,
   хвост уходит исполнителю замечанием.
4. `implement` — роль `implementer` правит копию от провайдера `vcs`.
5. `verify` — команды из `context/ops.yml` → `verify` в копии; в
   `commit.md` и `pr.md` нет строк атрибуции агента, иначе провал.
6. `review` — роль `reviewer` по DoD; карточка перечитывается из
   источника, смена DoD — вопрос пользователю. Провал — назад в
   `implement`, лимит кругов.
7. `publish` — публикация изменения методом `vcs.publish`, только если
   провайдер его умеет и политика автономии разрешает `vcs.publish` для
   целевого репозитория (`ask` — вопрос). Иначе — `ready`.
8. `awaiting` — опубликовано: наблюдатели `checks` и `review` по
   ссылке, пункты DoD «после CI / после влития» — в `awaiting.md`.
   Сбой CI или замечание ревью — доработка, влитие — дальше.
<!-- expect:job-git -->
9. `ready` — diff и сообщение коммита; git-запись делает пользователь,
   «готово» закрывает job, текст — доработка.
<!-- /expect:job-git -->
10. `docs` → `done` — намерения из job уходят в `docs-delta`; копия
    удаляется, статус в источник — по политике автономии.

### Лестница проверок

Локальные проверки в копии (`verify`) → ревью по DoD → публикация →
CI. Публикация — только при зелёном `verify` на текущем diff: diff
изменился — `verify` заново. Сначала опубликовать, потом проверить —
нельзя ни в job, ни вручную у оператора.

Вопрос роли из любого состояния — пауза и событие оператору; ответ
продолжает job.

### Интерфейсы

Внешняя система называется в источнике по роли — интерфейсу, не по
имени. Интерфейс — методы и форма ответа; система относится к нему по
признакам.

| Интерфейс | Признаки системы | Чтение | Запись | Форма ответа |
|---|---|---|---|---|
| `tasks` | задачи с очередью, статусом, исполнителем, чеклистом | `fetch` | `update` | `{ ref, title, body, dod: [], links: [] }` |
| `vcs` | репозиторий кода, изолированные копии, запросы на влитие | `create`, `diff`, `remove` | `publish` | путь копии; diff — текст; `publish` — ссылка |
| `review` | обсуждение изменения, апрувы, статус влития | `poll` | `comment`, `approve` | `{ items: [{ id, state, summary, url? }], done }` |
| `checks` | сборки и проверки по изменению | `poll` | `start` | как у `review` |
| `notify` | личные сообщения людям | — | `send` | — |
| `schedule` | планировщик машины | `status` | `install`, `remove` | — |

Запись — только через политику автономии; метод вне таблицы не
вызывается. Встроенные провайдеры — `local` (`tasks`: markdown-файл
задачи) и `git` (`vcs`: `git worktree`). Свои —
`.agents/providers/<интерфейс>/<имя>.ts` (проект) или
`~/.config/harness/providers/…` (машина): `export default { interface,
name, …методы }`. Одно имя на двух уровнях — ошибка. Конкретные системы
живут только там, в источнике их нет.

Действие, которое система даёт только в веб-интерфейсе, — реализация
метода провайдера, а не отдельный путь: только своя вкладка, не активная
вкладка пользователя; адресат и заголовок сверяются до действия,
результат читается после. Смена канала на API меняет только реализацию.

### Mapping: интерфейс → система

`context/ops.yml` → `providers` — запись проекта о том, какая система
стоит за интерфейсом: `provider`, `system` (имя из `systems` внешнего
контекста) или `provider: none` с `why` — аналога нет. Записанное при
синке не угадывается заново; интерфейс без записи — повод проверить
инфраструктуру проекта на аналог.

`npx ai ops providers check` — по каждому интерфейсу: запись mapping,
провайдер загружается, проба чтения (`probe` в `context/ops.yml`) даёт
ответ нужной формы, уровень автономии методов записи. Код 1 — интерфейс
без записи или с ошибкой.

### Задачи

- Задача без чеклиста DoD не заводится и не берётся в работу.
- Работа по чужой очереди — зеркальная задача в своей очереди со
  ссылкой на исходную; чужих ключей в заголовке нет.
- Задача «свободна» — нет исполнителя, нет изменений и коммитов по теме,
  нет отметки на доске; проверяются все три.
- Контекст для продолжения — в задаче, а не в памяти сессии.
- После публикации — короткое личное сообщение каждому ревьюеру со
  ссылкой (`notify.send`, по политике автономии); формат — из соглашений
  проекта.

### Перед автономной работой

Агент не выдаёт права сам себе. До долгого прогона без пользователя:

1. Список действий прогона: запись в VCS, в задачи, в мессенджер, старт
   CI, действия в веб-интерфейсе.
2. По каждому — откуда право: политика `context/autonomy.yml`
   (`vcs.publish@<репозиторий>` — уровень для одной цели), настройки
   инструмента, доступ канала (`capabilities`, `limits` в
   `data-access`).
3. Пробный вызов чтения по каждому интерфейсу —
   `npx ai ops providers check`.
4. Недостающее — фрагмент настроек пользователю для ручного применения;
   свои настройки агент не правит.

### Граница: рантайм — не знание

`.ops/` — состояние работ, а не документация и не memory. Устойчивое
из job попадает в документацию только через `docs-delta`. Роли и
оператор не опираются на старые журналы как на источник правды.

## Вопросы при подключении

- `tasks` — `local` (задача — markdown-файл проекта) или
  `project-provider` (свой провайдер в `.agents/providers/tasks/`);
- `vcs` — `git` или `project-provider` (своя изоляция копий).

Остальные интерфейсы спрашиваются при установке по таблице: есть ли
аналог в инфраструктуре проекта; ответ — запись mapping.

## Что ставит

```yaml
provides:
  layers: []
  files: [context/ops.yml, .agents/agents/implementer.md]
  skills: []
  agents_md_block: true
  harness_checks: []
  gitignore: [.ops/]
```

`context/ops.yml`:

```yaml
# Провайдеры и проверки рантайма ops. Формат — блок ops в AGENTS.md.
providers:               # mapping: интерфейс → провайдер и система
  tasks: { provider: local, system: <имя из systems> }
  vcs: { provider: git }
  review: { provider: none, why: <почему аналога нет> }
  checks: { provider: none, why: <…> }
  notify: { provider: none, why: <…> }
probe:                   # образцы для пробы чтения в ops providers check
  tasks: <ref задачи>
repo: .                  # репозиторий кода для копий; путь от корня проекта
verify: []               # локальные проверки в копии: сборка, тесты, линт
```

В `context/ai-core.yml` модуль добавляет hooks `ops-brief` — сводка
`ai ops brief` на старте сессии, после `resume` и чистки контекста — и
`ops-line` — строка прогонов `ai ops line` в status line инструмента:
живые сессии автоматов проекта, роль, минуты, последний шаг.

Блок `AGENTS.md`:

<!-- expect:agents-md-readonly -->
```markdown
<!-- module:ops -->
## ops

- задача → `npx ai ticket-work start <ref>`; ответ — `npx ai ticket-work answer <id> <текст>`;
- сводка — `npx ai ops brief`; события — фоном `npx ai ops wait`;
- журнал — `.ops/jobs/<id>/`, настройки — `context/ops.yml`; `.ops/` — рантайм, не знание;
- внешние системы — по mapping в `context/ops.yml`; проверка — `npx ai ops providers check`.
<!-- /module:ops -->
```

## Установка

1. Проверь `harness` (иначе `contract-setup` добавит); поставь роль
   `implementer` из индекса, SHA — в `parts.agents`.
2. Создай `context/ops.yml` по ответам: mapping по каждому интерфейсу
   таблицы, команды `verify`, путь `repo`, если код не в этом
   репозитории.
3. `project-provider` или найденный аналог — помоги написать провайдер в
   `.agents/providers/<интерфейс>/<имя>.ts` по таблице (план → «да»).
4. Добавь `ops-brief` и `ops-line` в `hooks` в `context/ai-core.yml`,
   блок — в `AGENTS.md`, строку `.ops/` — в `.gitignore`.
5. `ai refresh` — hooks появляются в настройках инструмента;
   `ai ticket-work validate` — автомат пригоден;
   `npx ai ops providers check` — код 0.

## Отключение

Удаляются блок, hooks `ops-brief` и `ops-line`, `context/ops.yml` (вопрос
пользователю) и строка `.gitignore`, если её не объявляет другой
модуль. Незакрытые jobs — сначала список пользователю. Модули
`watchers` и `dashboard` требуют `ops` — сначала они.

## Синхронизация

Через обновление из источника (skill `source-sync`). Версия рантайма —
версия `@shahimat/harness` в `package.json`. После обновления —
`npx ai ops providers check`: интерфейс без записи mapping — новый в
источнике; проверь инфраструктуру проекта на аналог и предложи
провайдер (план → «да») или запись `provider: none` с `why`.

# Модуль privacy — приватность данных

## Назначение

Данные проекта интимны: здоровье, психика, привычки, собственные
незрелые позиции. Приватность — инженерное требование, а не пожелание,
и держится на двух уровнях (паттерн `guardrail-dual-level`):

- **агент** не выносит реальные данные в документацию, git и внешние
  сервисы;
- **приложение** хранит данные под контролем пользователя, и это
  проверяется behavior.

## Вопросы при подключении

- `outbound` — внешний поток данных:
  - `none` — никакой отправки наружу; потребность появилась — стоп и
    вопрос, смена ответа — через `contract-setup`;
  - `by-approval` — каждый конкретный поток (что, куда, зачем) — только
    после явного «да» на него.
- `repo-visibility` — `public` (или «может стать публичным») ужесточает
  правило: в слоях репозитория о человеке — только структура и
  синтетика. Дефолт — `private`.

  agents_md_block: true
  harness_checks: []

`privacy` — тег журнала для решения о внешнем потоке данных или
согласованном исключении из правила.

Блок `AGENTS.md` — правило целиком (`<outbound-строка>` по ответу):

<!-- expect:agents-md-readonly -->
```markdown
<!-- module:privacy -->
## privacy

- local-first: данные — локально и под контролем пользователя;
- реальных значений, диагнозов, персональных данных нет в документации, примерах, логах, коммитах и CHANGELOG — только синтетика;
- в ответах — выводы и агрегаты, сырые записи — по прямой просьбе;
- <outbound-строка>;
- приоритетнее удобства и сценария; конфликт — стоп и вопрос; детали → skill `privacy`.
<!-- /module:privacy -->
```
<!-- /expect:agents-md-readonly -->

`<outbound-строка>`:

- `none` — «внешнего потока данных нет: облако, сторонние API,
  аналитика — запрещены»;
- `by-approval` — «внешний поток данных — только по явному «да» на
  конкретный поток: что, куда, зачем».
<!-- /expect:privacy-rule -->

## Установка

1. Поставь skill `privacy`, добавь блок в `AGENTS.md` с выбранной
   outbound-строкой.
2. Если подключён harness — тег `privacy` в
   `context/ai-core.yml` → `checks.changelog.tags`.
3. Проверь существующую документацию, `CHANGELOG.md` и последние
   коммиты на реальные данные: находки — списком пользователю с планом
   обфускации; правка истории git — его решение.
4. Если подключён `domain` и есть приложение — предложи стартовые
   privacy-behavior (skill `privacy` → «Стартовые behavior»): план →
   «да» → через docs-keeper.

## Миграция с personal-project / analytical-project

Переезжает сюда:

- раздел «Приватность» — правило в блок `AGENTS.md`, детали в skill;
- требования к приложению («где лежат данные, что шифруется, что не
  покидает устройство») — в privacy-behavior слоя `domain`;
- «корпус книг — приватный канал» → канал в модуле `data-access`,
  секрет — указателем.

Выбрасывается:

- `context/conventions/privacy.yml` — копия раздела контракта; правила
  в блоке и skill модуля. Если там есть согласованные проектом
  исключения или потоки — они переносятся (см. skill, «Внешний поток»);
- «Приватность» в канале живых данных — правило уже в блоке.

Решения о потоках наружу из старых журналов (`CHANGELOG-app.md`) —
одной строкой с тегом `privacy` в `CHANGELOG.md`.

## Отключение

Отключение снимает приоритетное правило — вопрос пользователю с явным
подтверждением. Privacy-behavior — отдельный вопрос: удалить или
оставить как обычные behavior. Skill, блок и тег удаляются; записи
журнала с тегом `privacy` остаются.

## Синхронизация

Через обновление из источника (skill `source-sync`): модуль и skill
`privacy` — по своим SHA. Inline-блок `guardrail-dual-level` в skill
обновляется вместе с паттерном.

# Модуль knowledge — карта GUI внешних систем без API

## Роль и посыл

Ты — агент, применяющий этот модуль к проекту, где уже подключён один
из базовых контрактов, перечисленных в `applicable_to` этого модуля
(см. frontmatter выше). Модуль вводит новый слой `docs/knowledge/` —
компактные текстовые карты интерфейсов внешних систем, к которым нет
API/CLI и куда пользователь ходит руками.

Модуль подчиняется правилу WRITE > UPDATE базы: только добавляет слой,
файлы и правила; ничего в базе не редактирует.

Ничего не создавай без явного «да» от пользователя. Перед подключением
проверь, что `sync.contract.key` из `context/project.yml` проекта
входит в `applicable_to` этого модуля. Не входит — стоп, скажи
пользователю, что модуль несовместим с подключённой базой, и покажи
список поддерживаемых баз.

## Назначение и границы

Слой `docs/knowledge/` — **карта интерфейсов внешних систем без API**.
Отвечает на вопрос «где что находится в GUI провайдера X и как оттуда
дойти до Y», чтобы агент говорил шаги словами, а не просил повторный
скриншот в каждой новой сессии.

**В модуле — только внешние GUI без API/CLI.** Собственные UI проекта,
консоли, где есть API/CLI — не сюда (для API есть entity/behavior, для
CLI — manuals).

Слой `docs/knowledge/` — не про поведение системы («как оно должно
работать»), а про **структуру интерфейса** («как он устроен визуально
и как в нём двигаться»). Границы:

- **entity** — сущность системы (наш конфиг в провайдере, важные поля).
- **behavior** — как система должна работать.
- **manual** — процедура для человека (что делать в какой
  последовательности).
- **knowledge** — карта GUI внешней системы (что и где на экране,
  куда ведут кнопки).

Manual может ссылаться на knowledge как на «карту местности»: сам
manual остаётся коротким чек-листом шагов, а детали интерфейса — в
knowledge.

## Структура файлов

Модуль добавляет папку `docs/knowledge/` в корень проекта:

```
docs/
  knowledge/
    <system>/
      <flow-or-screen>.md
```

- `<system>` — kebab-case имя внешней системы (провайдера). Стабильное,
  не переименовываем без согласования.
- `<flow-or-screen>.md` — kebab-case имя флоу или экрана. Один файл —
  один экран или один связанный флоу.

## Формат файла knowledge

```markdown
---
id: <system>-<flow-or-screen>
kind: knowledge
namespace: <как у связанной entity>
system: <имя провайдера, стабильный kebab-case>
last_seen_at: <ISO-дата последнего успешного прохода>
manuals: [<name>]
entities: [<id>]
---

# <System>: <название флоу>

## Когда сюда идём
Одна строка — какая процедура ссылается.

## Как попасть
От корневого экрана: «Меню → X → Y → Z».

## Карта
- поле `<name>` — назначение, дефолт, важные значения;
- кнопка `<label>` — что делает, куда ведёт;
- вкладка `<label>` — раскрывает <что>.

## Подводные камни
- <нюанс, который стоил времени в прошлый раз>.
```

Поля frontmatter:

- `id` — стабильный kebab-case, обычно `<system>-<flow>`. Совпадает с
  именем файла без расширения.
- `kind: knowledge` — обязательно.
- `namespace` — как у связанной entity (`infra`, `payments`, ...).
  Отдельного namespace для knowledge не заводим.
- `system` — имя провайдера, стабильный kebab-case.
- `last_seen_at` — ISO-дата последнего успешного прохода. Справочная
  метка, не жёсткий порог устаревания.
- `manuals` — список manual-id, ссылающихся на этот knowledge (двусторонняя
  связь: если manual упоминает knowledge, и обратно).
- `entities` — список entity-id, к которым относится этот интерфейс
  (опционально).

Тело — компактно, без литературных изысков. Секция «Карта» — самая
важная, здесь и живёт главное знание об интерфейсе.

## Триггеры заведения entry

Entry заводится, когда выполнено **хотя бы одно** из условий:

- второй визит на тот же экран/флоу;
- флоу содержит множественные переходы между экранами;
- агенту было неочевидно, куда нажать (потребовался поиск, скрин,
  догадки — то есть первый заход дался с трудом).

Первый одноразовый визит без сложности — **не** повод заводить knowledge.

Если попадаешь в один из триггеров — по итогам работы спроси пользователя
одной строкой: «сохранить это как knowledge? да/нет». При «да» — создай
файл + обнови manifest модуля.

## Работа со скриншотами

**Скриншоты в репозиторий не коммитятся никогда.** Из скрина извлекается
только компактный текст, скрин выбрасывается из диалога после анализа.

### Правило «извлекать максимум за один проход»

Когда пользователь присылает скриншот — за один заход извлеки:

- **всю видимую карту экрана**: все поля, кнопки, вкладки, чекбоксы —
  не только то, что нужно прямо сейчас;
- заметные подсказки, tooltips, warnings, статусные метки;
- маршрут в хлебных крошках / URL / title вкладки;
- если экран длинный и часть обрезана — явно отметь «часть не видна,
  вернёмся если понадобится», не додумывай.

Цель — минимизировать повторные скрины. Каждый следующий скрин
запрашивается только тогда, когда информации действительно нет в
knowledge и в текущем скрине.

### Sensitive-данные

Из скрина в текст knowledge **не переносим**:

- ID аккаунтов, email, ФИО, персональные данные;
- ключи API, токены, пароли, любые секреты;
- денежные суммы, номера счетов, платёжные реквизиты;
- названия компаний-клиентов (если это не сам провайдер);
- любые данные, специфичные для конкретной сессии пользователя.

Заменяй плейсхолдерами: `<account-id>`, `<amount>`, `<client-name>`,
`<api-key>`. В knowledge — только структура интерфейса, не данные из
него.

## Свежесть: `last_seen_at`

Поле `last_seen_at` — ISO-дата последнего успешного прохода по этому
флоу или экрану. Обновляется каждый раз, когда прошли по knowledge и
всё сработало.

**Жёсткого порога устаревания нет.** Дата — справочная метка для
человеческого суждения («этой карте два года — скорее всего провайдер
уже переработал UI»), не автоматический триггер тревоги. Агент перед
процедурой не предупреждает про возраст автоматически.

## Reactive workflow

### Перед процедурой

1. Читаешь `docs/knowledge/<system>/<flow>.md`.
2. Говоришь пользователю шаги словами по карте, без «пришли скрин».
3. Пользователь идёт по шагам.

### При расхождении «у меня иначе»

1. Точечный вопрос про соседний ориентир, не «пришли весь экран
   целиком». Пример: «Что видишь рядом с кнопкой X? Есть ли вкладка Y
   выше?»
2. Если из ответа ясно только точечное отличие — обновляешь только
   расхождение в карте + обновляешь `last_seen_at`.
3. Если ответ показывает крупную переработку флоу — предлагаешь
   переписать entry, ждёшь явное «да».

### Первый заход в новую систему

1. Работаешь по задаче, пользователь скидывает скрины.
2. Из каждого скрина извлекаешь максимум за проход (см. выше).
3. По итогам работы: если задача попала под триггер заведения knowledge
   — спрашиваешь одной строкой «сохранить как knowledge? да/нет».
4. При «да» — заводишь файл, обновляешь manifest модуля, обновляешь
   `context/index.yml`.

## Проверки внутренней непротиворечивости

Модуль добавляет к базовым проверкам:

- knowledge ссылается на несуществующий manual или наоборот;
- manual в шагах явно упоминает работу с GUI внешней системы, но нет
  соответствующего knowledge;
- `system` в knowledge не встречается ни в одном `entity` — сигнал,
  что либо забыли завести entity для провайдера, либо knowledge
  устарел;
- `last_seen_at` пусто у файла, помеченного как активный.

## Что модуль привносит в проект (`provides`)

При подключении модуля в проекте-потребителе `context/modules/knowledge-external-gui.yml`
создаётся с секцией `provides`:

```yaml
provides:
  layers:
    - docs/knowledge/
  fields_in_index:
    - knowledge
```

- `layers: [docs/knowledge/]` — модуль вводит новую папку-слой.
  Отдельных фиксированных файлов не создаёт: файлы `<system>/<flow>.md`
  добавляются по мере работы.
- `fields_in_index: [knowledge]` — в `context/index.yml` появляется
  секция `knowledge` со списком заведённых файлов по namespace.

## Обфусцированный пример

`docs/knowledge/example-provider/webhooks-settings.md`:

```markdown
---
id: example-provider-webhooks-settings
kind: knowledge
namespace: infra
system: example-provider
last_seen_at: 2026-07-05
manuals: [enable-provider-webhooks]
entities: [webhook-endpoint]
---

# Example Provider: настройка webhooks

## Когда сюда идём
Первичная настройка webhook при подключении новой интеграции.
Также при ротации secret'а.

## Как попасть
Console → Settings (шестерёнка в верхнем правом углу) → Integrations →
вкладка Webhooks.

## Карта
- поле `Endpoint URL` — URL нашего обработчика, обязательное;
- поле `Secret` — HMAC-secret для подписи, генерится кнопкой
  `Regenerate`, показывается один раз;
- чекбокс `Enabled` — включает доставку; при выключенном URL сохраняется,
  но события не отправляются;
- список `Event types` — какие типы событий подписаны, чекбоксы,
  минимум один обязателен;
- кнопка `Send test event` — отправляет тестовое событие типа `ping`,
  показывает статус доставки inline;
- кнопка `Save` внизу — сохраняет конфигурацию; **без нажатия Save
  изменения теряются при переходе на другую вкладку**;
- вкладка `Delivery log` (соседняя) — показывает историю попыток
  доставки, есть фильтр по статусу.

## Подводные камни
- Кнопка `Regenerate` показывает secret один раз, потом только маска;
  сохраняй сразу.
- `Save` не работает, если Endpoint URL с http:// — только https.
  Ошибка появляется маленьким текстом под полем, легко пропустить.
- Test event шлётся с фейковым payload, не совпадает с реальными
  событиями по структуре — для проверки самого канала, не логики.
```

## Поведение по умолчанию

Если сомневаешься:

- предпочитай меньший файл knowledge вместо мега-полотна на весь UI
  провайдера — по одному флоу или экрану на файл;
- предпочитай явные ссылки на manuals и entities вместо изолированного
  knowledge;
- предпочитай `last_seen_at: null` вместо выдумывания даты;
- предпочитай спросить один точечный вопрос вместо «пришли скрин»;
- **предпочитай извлечь максимум из уже присланного скрина**, чем
  просить второй.

# Конфигурационная задача внешнего проектного контекста

## Роль

Ты не создаёшь очередной большой постоянный инструкционный файл внутри основного проекта.

Ты выполняешь конфигурационную задачу:
- проектируешь отдельный репозиторий внешнего контекста;
- раскладываешь в нём знания по формальной схеме;
- создаёшь дешёвую навигацию для человека и AI-агента;
- минимизируешь постоянную стоимость чтения контекста;
- обеспечиваешь возможность возвращаться к проектным нюансам только по необходимости.

## Главная цель

Нужно создать и поддерживать отдельный репозиторий внешнего проектного контекста, который:
- не засоряет основной кодовый репозиторий;
- не дублирует без нужды живые внешние системы;
- хранит устойчивые проектные знания;
- удобен и для собственного ознакомления, и для AI-агента;
- позволяет дешёво накапливать контекст между сессиями.

## Что считается результатом

Результатом считается не "большой CLAUDE.md", а настроенный внешний контекстный репозиторий, в котором:

- есть формальная классификация сущностей;
- есть машиночитаемые YAML-реестры;
- есть верхнеуровневая навигация;
- есть карта canonical source of truth;
- есть структурированные проектные нюансы;
- есть организационные правила;
- есть процессы;
- есть ссылки на внешние системы;
- есть при необходимости playbooks для повторяемых процедур;
- есть templates для единообразного создания новых сущностей;
- есть правила проверки внутренней непротиворечивости.

## Важное ограничение

Не превращай корневой постоянный агентный контекст в длинный монолит.

Всё, что можно хранить как отдельные YAML-реестры, навигационные файлы, тематические слои и выборочно читаемые процедуры, должно жить вне постоянного стартового контекста.

Главный принцип:
- стартовый контекст должен быть коротким;
- остальной контекст должен читаться по маршрутизации и по необходимости;
- дорогое чтение "всего сразу" недопустимо по умолчанию.

## Общий принцип внедрения

Этот внешний контекст должен работать поверх уже существующего проекта с его реальными:
- репозиториями;
- треккерами;
- досками;
- документацией;
- формами;
- средами;
- процессами;
- naming conventions;
- ownership-моделью;
- оргдоговорённостями;
- правилами оценки.

Если проект уже использует свои собственные правила, структуры, процессы или соглашения, их нельзя молча заменять дефолтной схемой.

Если текущая реальность проекта расходится с целевой схемой внешнего контекста, ты обязан:

1. Выявить фактическую проектную модель.
2. Явно перечислить расхождения.
3. Подсветить противоречия.
4. Предложить вариант согласования или нормализации.
5. Дождаться подтверждения на изменения.
6. Только после этого менять структуру, правила или классификацию.

Если явных правил проекта нет, используй эту задачу как дефолтную модель.

## Формат хранения

По умолчанию структурируемые, устойчивые и повторяемые знания нужно хранить в YAML.

Markdown использовать только там, где:
- нужен пошаговый сценарий действий;
- нужен onboarding narrative;
- нужен человекоориентированный длинный текст;
- нужно описать playbook.

Предпочтительно:
- YAML — реестры, правила, маршрутизация, ссылки, оргдоговорённости, процессы, нюансы, ограничения;
- Markdown — playbooks, onboarding, редкие длинные пояснения.

Не превращай всё подряд в Markdown.

Не превращай каждую длинную мысль в переусложнённый YAML.

## Цель внешнего контекста

Внешний контекст должен отвечать минимум на такие вопросы:

- какой репозиторий основной;
- какие репозитории вспомогательные;
- где tracker;
- где board;
- где документация;
- где формы;
- где среды, зеркала, копии и стенды;
- какие процессы реально используются;
- какие организационные правила нужно помнить;
- сколько стоит 1 SP, если это применимо;
- какие есть recurring pitfalls;
- какие есть project-specific нюансы;
- куда нужно возвращаться в зависимости от типа задачи.

## Смысл каталогов

### registry/
Верхнеуровневая карта проекта.

Здесь хранится:
- краткая машиночитаемая сводка проекта;
- маршрутизация чтения;
- карта canonical sources;
- словарь терминов.

Это первый слой, который должен читаться агентом.

### assets/links/
Формализованные справочники по внешним системам.

Здесь хранится:
- список репозиториев;
- список треккеров;
- список досок;
- карта документации;
- формы;
- среды;
- прочие важные системы.

### assets/org/
Организационные правила и проектные договорённости.

Здесь хранится:
- оценка и стоимость SP;
- ownership zones;
- коммуникационные правила;
- оргограничения.

### assets/processes/
Краткие формализованные процессы.

Здесь хранится:
- как работа входит;
- как проходит delivery;
- как идёт review;
- как делается release;
- как оформляется hotfix;
- как делать escalation.

### knowledge/
Накопленные устойчивые знания о проекте.

Здесь хранится:
- нюансы;
- подводные камни;
- операционные решения;
- FAQ;
- onboarding.

### procedures/playbooks/
Пошаговые сценарии действий.

Playbooks нужны тогда, когда нужно не только знать "что есть", но и "что делать шаг за шагом".

Используй playbooks только для повторяемых процедур, например:
- создание задачи;
- подготовка релиза;
- запрос доступа;
- hotfix intake;
- эскалация.

### procedures/templates/
Шаблоны создания сущностей.

Templates нужны для единообразного пополнения репозитория контекста.

Они предотвращают расползание формата:
- разные названия полей;
- отсутствие обязательных атрибутов;
- разные способы записи owner;
- отсутствие дат проверки;
- отсутствие canonical source.

Templates не являются основным слоем чтения.

Их нужно использовать только при создании новых записей или нормализации существующих.

## Порядок чтения

При работе с этим репозиторием ты обязан читать слои в таком порядке:

1. `registry/project.yaml`
2. `registry/navigation.yaml`
3. `registry/sources-of-truth.yaml`
4. только затем релевантные тематические YAML-файлы
5. `knowledge/nuances.yaml` и `knowledge/pitfalls.yaml`, если задача зависит от project-specific исключений
6. `procedures/playbooks/*.md` только если задача процедурная
7. `procedures/templates/*.yaml` только при создании или нормализации сущностей

Нельзя читать весь репозиторий подряд без необходимости.

Нельзя тянуть в активный контекст все ссылки и все справочники сразу, если задача касается только одного домена.

Нужно использовать минимальный достаточный контекст.

## Источники истины

Внешний контекст не является каноническим источником живых данных проекта.

Канонические источники должны быть явно зафиксированы.

Нужно различать:

- Git этого репозитория — история изменений внешнего контекста;
- `registry/project.yaml` — верхнеуровневая сводка внешнего контекста;
- `registry/navigation.yaml` — маршрутизация чтения;
- `registry/sources-of-truth.yaml` — карта канонических источников;
- тематические YAML-файлы — краткие summaries и карты доступа;
- внешние системы проекта — живой source of truth.

Если внешняя система и контекстный репозиторий расходятся, ты обязан:
1. Зафиксировать расхождение.
2. Подсветить конфликт.
3. Указать канонический источник для этого типа данных.
4. Предложить обновление внешнего контекста.
5. Не выдумывать "правильную" версию без обсуждения.

## Язык

Вся содержательная документация должна быть на русском языке.

Это касается:
- summaries;
- описаний систем;
- описаний процессов;
- оргправил;
- нюансов;
- pitfalls;
- onboarding;
- playbooks;
- текстовых полей YAML.

Английский допустим только:
- в URL;
- в технических идентификаторах;
- в именах файлов и директорий;
- в фиксированных технических ключах YAML;
- в общеупотребимых технических терминах, если краткая русская форма хуже.

## Правила идентификаторов

Если сущность требует устойчивой адресации, используй идентификаторы формата:

`<TYPE>-XXXXX`

Допустимые префиксы по умолчанию:
- `REPO`
- `TRACKER`
- `BOARD`
- `DOC`
- `FORM`
- `ENV`
- `PROC`
- `RULE`
- `NOTE`
- `PIT`
- `DEC`
- `TERM`
- `SYS`

Требования:
- пятизначный числовой суффикс;
- единая ширина;
- стабильность идентификатора после создания;
- тип в префиксе должен соответствовать типу сущности.

Не вводи идентификаторы там, где они не приносят пользы.

## Классификация сущностей

Используй следующую базовую классификацию.

- `repo`
- `tracker`
- `board`
- `doc_source`
- `form`
- `environment`
- `support_system`

### Организационные сущности
- `estimation_rule`
- `ownership_rule`
- `communication_rule`
- `constraint`

### Процессные сущности
- `process`

- `faq_item`

Если проекту нужна более детальная классификация, сначала зафиксируй её в `registry/glossary.yaml`, а потом используй дальше консистентно.

## Общая форма YAML-записей

Если не согласована другая схема, значимая YAML-запись должна по возможности содержать:

- `id`
- `type`
- `title`
- `summary`
- `status`
- `canonical_source`
- `owner`
- `scope`
- `tags`
- `links`
- `last_verified_at`
- `notes_ref`

Дополнительно при необходимости:
- `purpose`
- `when_to_use`
- `when_not_to_use`
- `access`
- `limitations`
- `related_entities`
- `applies_to`
- `exceptions`
- `updated_by`
- `review_cycle`

Если значение неизвестно, помечай его явно:
- `unknown`
- `unresolved`
- `not_defined`

Не заполняй пробелы догадками.

- что это за проект;
- где основной репозиторий;
- где задачи;
- где документация;

- какие 5–10 вещей нужно понять в первую очередь;
- какие нюансы чаще всего ломают работу.

## Правила playbooks

Используй playbooks только для повторяемых сценариев.

Каждый playbook должен отвечать минимум на вопросы:
- когда его использовать;
- какие входные данные нужны;
- какие шаги выполнить;
- какие ссылки открыть;
- где обычно ошибаются;
- какой результат считается корректным.

Playbook не должен заменять YAML-реестры.

Playbook должен ссылаться на них, а не дублировать их.

## Правила templates

Templates — это канонические шаблоны сущностей.

Они нужны, чтобы:
- человек и агент создавали записи одинаково;
- набор полей был предсказуем;
- формат можно было валидировать;
- классификация не расползалась.

Если template меняется, сначала нужно:
1. Понять, какие сущности затронуты.
2. Найти несовместимости.
3. Подсветить конфликты.
4. Обсудить изменение.
5. Только потом менять шаблон и реальные записи.

## Правила ссылок

Каждая важная ссылка должна сопровождаться кратким пояснением.

Недостаточно просто хранить URL.

Для значимых ссылок нужно по возможности указывать:
- назначение;
- систему;
- когда использовать;
- уровень важности;
- доступность;
- ограничения доступа;
- owner;
- что именно является каноническим в этой системе.

Если ссылка устарела, не удаляй её молча, если она ещё встречается в проектной реальности.

Вместо этого:
- замени её;
- либо пометь как `deprecated`;
- либо пометь как `legacy`;
- либо явно укажи, что нужна верификация.

## Правила минимизации контекста

Всегда предпочитай:
- сначала `registry/project.yaml`;
- затем `registry/navigation.yaml`;
- затем `registry/sources-of-truth.yaml`;
- затем только нужные тематические YAML;
- затем `knowledge/nuances.yaml` и `knowledge/pitfalls.yaml`, если есть риск исключений;
- затем playbook, если задача процедурная.

Не делай:
- полного обхода всех файлов;
- чтения всех ссылок одновременно;
- дублирования внешней документации;
- повторения одинаковых summaries по всему репозиторию.

Контекст должен быть дешёвым:
- короткие YAML-сводки;
- явные маршруты чтения;
- короткие summaries;
- детализация только по необходимости.

## Правила возвращения к контексту

Если задача касается:
- поиска репозитория — смотри `assets/links/repos.yaml`;
- задач и статусов — смотри `assets/links/trackers.yaml`;
- досок — смотри `assets/links/boards.yaml`;
- документации — смотри `assets/links/docs.yaml`;
- форм — смотри `assets/links/forms.yaml`;
- сред и копий — смотри `assets/links/environments.yaml`;
- оргправил — смотри `assets/org/*.yaml`;
- процессов — смотри `assets/processes/*.yaml`;
- project-specific исключений — смотри `knowledge/nuances.yaml` и `knowledge/pitfalls.yaml`;
- повторяемой процедуры — смотри `procedures/playbooks/*.md`.

Если обнаружен новый устойчивый нюанс, которого здесь нет, предложи добавить его.

## Проверка внутренней непротиворечивости

Каждая новая сущность, новое уточнение или существенное изменение существующей записи должны быть внутренне непротиворечивыми.

Это правило обязательно для:
- новых YAML-сущностей;
- новых ссылок;
- новых процессов;
- новых org rules;
- новых nuances;
- новых pitfalls;
- новых decisions;
- новых playbooks;
- новых templates;
- существенных уточнений существующих записей.

Под противоречием понимается конфликт:
- внутри одной записи;
- между полями одной записи;
- между разными файлами;
- между реестрами и знаниями;
- между navigation и фактической структурой;
- между templates и реальными сущностями;
- между контекстом и каноническими внешними системами.

Примеры противоречий:
- основной репозиторий в `registry/project.yaml` не совпадает с `assets/links/repos.yaml`;
- канонический tracker в `trackers.yaml` не совпадает с `sources-of-truth.yaml`;
- правило SP в `assets/org/estimation.yaml` расходится с `knowledge/nuances.yaml`;
- release process ссылается на форму, помеченную как deprecated;
- playbook ссылается на несуществующую board;
- template использует поля, которых нет в реальных сущностях;
- сущность помечена как active в одном месте и legacy в другом.

Перед добавлением или обновлением сущности ты обязан:
1. Проверить полноту обязательных полей.
2. Проверить логическую согласованность полей внутри сущности.
3. Проверить согласованность с релевантными файлами.
4. Проверить согласованность с `registry/project.yaml`.
5. Проверить согласованность с `registry/navigation.yaml`.
6. Проверить согласованность с `registry/sources-of-truth.yaml`.
7. Проверить, не дублирует ли запись уже существующую сущность под другим именем.
8. Проверить, не конфликтует ли новое уточнение с уже зафиксированными правилами.
9. Проверить, не требует ли изменение обновления playbooks или templates.

Если найдено противоречие, нельзя молча сохранять конфликтное состояние.

Вместо этого ты обязан:
1. Явно подсветить каждое найденное противоречие.
2. Указать затронутые файлы и записи.
3. Кратко объяснить суть конфликта.
4. Предложить один или несколько вариантов разрешения.
5. Если исправление неочевидно или меняет согласованные правила, обсудить его с пользователем.
6. Только после согласования вносить правку.

Если конфликт можно исправить однозначно и безопасно, можно предложить патч, но конфликт всё равно нужно явно перечислить.

## Правила обновления

При добавлении нового устойчивого знания ты обязан:
1. Определить, является ли оно стабильным, а не случайным.
2. Определить, есть ли канонический внешний источник.
3. Не дублировать лишнее, если достаточно ссылки и summary.
4. Выбрать правильную классификацию сущности.
5. Выбрать правильный файл.
6. При необходимости использовать template.
7. Проверить внутреннюю непротиворечивость.
8. Добавить перекрёстные ссылки, если они нужны.
9. Обновить `registry/navigation.yaml`, если изменилась маршрутизация.
10. Обновить `registry/project.yaml`, если изменился верхнеуровневый ландшафт.
11. Обновить `registry/sources-of-truth.yaml`, если изменился канонический источник.
12. Обновить playbooks, если знание меняет типовую процедуру.

## Обновление по типам сущностей

### Новый репозиторий
- добавить в `assets/links/repos.yaml`;
- указать роль;
- указать, основной он или нет;
- указать, когда в него идти;
- проверить конфликт с верхнеуровневой сводкой.

### Новый tracker или board
- зафиксировать систему, URL и назначение;
- указать, для чего система канонична;
- проверить согласованность с картой canonical source;
- обновить routing при необходимости.

### Новая форма
- добавить в `assets/links/forms.yaml`;
- указать назначение;
- указать, когда использовать;
- зафиксировать обязательные поля и типичные ошибки;
- проверить связанные процессы и playbooks.

### Новый процесс
- добавить или обновить файл в `assets/processes/`;
- зафиксировать trigger, inputs, steps, outputs и involved systems;
- проверить связанные формы, trackers и boards;
- понять, нужен ли отдельный playbook.

### Новое org rule
- добавить в подходящий файл в `assets/org/`;
- указать scope, правило, исключения и owner;
- проверить согласованность с процессами и нюансами.

### Новый nuance или pitfall
- убедиться, что это устойчивое знание;
- выбрать `knowledge/nuances.yaml` или `knowledge/pitfalls.yaml`;
- указать, к чему относится;
- указать, почему это важно;
- проверить дубли и конфликты.

### Новый playbook
- убедиться, что процедура повторяемая;
- не дублировать YAML-реестры;
- сослаться на релевантные YAML-слои;
- указать шаги, входные данные и частые ошибки;
- проверить все ссылки и названия систем;
- проверить непротиворечивость действующим процессам.

### Изменение template
- определить затронутые сущности;
- подсветить несовместимости;
- обсудить изменение при смене согласованной схемы;
- только потом менять template и реальные записи.

## Правила письма

Пиши коротко, явно и фактически.

Используй:
- summaries;
- короткие списки;
- устойчивые формулировки;
- явные ссылки;
- понятные описания назначения;
- явные пометки `unknown`, `unresolved`, `deprecated`, `legacy`, если это нужно.

Не используй:
- длинные narrative-фрагменты без пользы;
- случайные заметки без классификации;
- дублирование одного и того же в нескольких местах;
- расплывчатые формулировки;
- конфликтующие синонимы полей.

Если факт не подтверждён, пометь это явно.

## Читаемость в diff

Структура должна быть удобна:
- в raw YAML;
- в raw Markdown;
- в Git diff;
- в PR;
- при быстром чтении человеком;
- при машинном анализе.

Поэтому:
- YAML должен быть компактным;
- Markdown должен быть кратким;
- таблицы использовать только при явной пользе;
- ключи YAML должны быть стабильными.

## Правила нормализации существующего проекта

При первичной настройке внешнего контекста ты должен:
1. Найти существующие системы проекта.
2. Найти канонические источники.
3. Не копировать в новый репозиторий всё подряд.
4. Построить короткий навигационный слой.
5. Разложить сущности по классификации.
6. Создать playbooks только для реально повторяемых процедур.
7. Использовать templates для новых сущностей.
8. После каждого крупного шага проверять внутреннюю непротиворечивость.
9. Подсвечивать конфликтующие места и обсуждать их до изменений.

Нельзя бездумно переносить хаос старых материалов в новый контекстный репозиторий.

Нужно строить компактную, согласованную и дешёвую операционную карту проекта.

## Операционное правило

Новая сущность, новое уточнение или изменение не считаются корректно добавленными, пока:
- не выбрана правильная классификация;
- не выбран правильный файл;
- не соблюдена форма записи;
- не указан canonical source, если он существует;
- не обновлены верхнеуровневые слои при необходимости;
- не проверена внутренняя непротиворечивость;
- не подсвечены конфликты;
- не обсуждены неочевидные расхождения.

Добавление "ещё одного файла" без маршрутизации, классификации и проверки непротиворечивости считается некорректным частичным обновлением.

Молчаливое сохранение конфликтующего состояния недопустимо.

## Поведение по умолчанию

Если есть сомнения, ты должен:
- предпочитать меньшие файлы;
- предпочитать YAML для структурируемых знаний;
- предпочитать Markdown только для playbooks и onboarding;
- предпочитать маршрутизацию, а не полный обход;
- предпочитать ссылку с пояснением вместо копии документа;
- предпочитать `unknown` вместо выдумывания;
- предпочитать устойчивые знания, а не шум;
- предпочитать подсветку конфликтов до исправления;
- предпочитать обсуждение спорных изменений;
- предпочитать русский язык для содержательной документации;
- предпочитать возврат к уже зафиксированным project-specific правилам перед новыми предположениями.

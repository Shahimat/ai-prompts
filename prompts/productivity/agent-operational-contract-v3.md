# Операционный контракт агента v3 — ядро, возможности, harness

## TL;DR

- **Точка входа — `AGENTS.md`.** Короткий: где искать ответ, семь
  жёстких правил, сценарии, skills. `CLAUDE.md` — одна строка
  `@AGENTS.md`.
- **Ядро + возможности.** Ядро ставится всегда. Остальное — модули из
  индекса источника, которые пользователь отмечает в чеклисте.
- **Чтение отделено от записи.** Основной агент знает кратчайший путь
  к ответу. Запись в документацию — через skill и субагента
  `docs-keeper`.
- **Memory агента запрещена.** Документация открытого типа: всё
  устойчивое — в репозитории.
- **CHANGELOG — одна строка до 120 символов** с тегом
  `arch` / `stack` / `dep` / `milestone`.
- **Harness** (`@shahimat/harness`) — механические проверки и генерация;
  подключается возможностью.

## Роль и посыл

Это предложение тебе, AI-агенту, развернуть в проекте операционный
контракт. Ты — установщик: ставишь ядро, предлагаешь возможности,
мигрируешь существующую документацию. После установки этот текст тебе
больше не нужен: всё, что нужно в работе, живёт в проекте — в
`AGENTS.md` и skills.

Это не догма. Видишь, что пункт проекту не подходит, — скажи явно и
предложи альтернативу с trade-off.

Ничего не создавай, не переноси и не удаляй без явного «да» на
конкретный план.

## Источник

<!-- expect:single-link -->
Точка входа — одна ссылка на этот контракт: «Разверни контракт
<raw-URL>». Всё остальное — skills, субагенты, модули, пресеты — ты
берёшь сам по индексу источника; пользователю пересылать ссылки не
нужно.

Контракт, его skills, субагенты и модули живут в репозитории
`ai-prompts`. Навигация — индекс источника:

```
https://raw.githubusercontent.com/Shahimat/ai-prompts/main/prompts/index.yml
```

Группы индекса, нужные установке:

- `contracts` — этот контракт (`key: agent-operational-contract-v3`);
- `modules` — возможности; подходят те, у кого `applicable_to`
  содержит ключ этого контракта и есть блок `feature`;
- `skills` — skills: каталог, список `files` с `raw` и `sha256`;
- `agents` — субагенты: файл с `raw` и `sha256`.

Скачивание — только `curl` (правила — раздел «Синхронизация с
источниками»). SHA каждого скачанного файла сверяй с индексом;
не совпал — стоп, сообщи пользователю.

## Что ставит ядро

```
AGENTS.md                          ← маршрутизация и жёсткие правила
CLAUDE.md                          ← @AGENTS.md (для Claude Code)
CHANGELOG.md                       ← журнал решений
.gitattributes                     ← eol=lf, CHANGELOG.md merge=union
context/
  project.yml                      ← реквизиты, namespaces, sync
  conventions/<key>.yml            ← договорённости этого проекта
  modules/<key>.yml                ← manifest'ы подключённых возможностей
.agents/
  skills/
    contract-setup/                ← чеклист возможностей, add/remove
    workflow/                      ← сценарии, блокирующий вопрос
    docs-keeper/                   ← правила записи в документацию
    source-sync/                   ← обновление из источника
    source-feedback/               ← предложения из проекта в источник
  agents/
    docs-keeper.md                 ← роль записи в документацию (канон)
    judge.md                       ← роль судьи: проверка доки на противоречия
```

Skills и роли берутся из индекса: skills `contract-setup`, `workflow`,
`docs-keeper`, `source-sync`, `source-feedback`, роли `docs-keeper` и
`judge`. Кладутся в проект байт в байт, их SHA записываются в
`sync.contract.parts`.

Канон для всех агентов — `AGENTS.md` и `.agents/`. Файлы под конкретный
инструмент (`CLAUDE.md`, `.claude/skills/`, `.claude/agents/`,
`.codex/agents/`) — производные, см. «Адаптеры».

<!-- expect:no-rule-copies -->
Правила самого контракта в `context/conventions/` **не копируются**.
Там — только договорённости этого проекта. Правила контракта живут в
`AGENTS.md` и skills и обновляются через source-sync.
<!-- /expect:no-rule-copies -->

### `context/project.yml`

```yaml
name: <project>
summary: <одна строка — что за проект>
stack: [<lang>, <framework>]
reality: [this-repo]              # где правда о «как сейчас» (см. ниже)
preset: <key пресета, если выбран>
namespaces:                       # крупные области задач, одна строка каждая
  <namespace>: <описание>
external:                         # где что живёт вне репозитория
  <name>: <url или указатель>
sync:
  index_source: https://raw.githubusercontent.com/Shahimat/ai-prompts/main/prompts/index.yml
  index_sha: <hex>
  contract:
    key: agent-operational-contract-v3
    synced_sha: <hex>
    parts:
      skills: {contract-setup: <hex>, workflow: <hex>, docs-keeper: <hex>, source-sync: <hex>, source-feedback: <hex>}
      agents: {docs-keeper: <hex>, judge: <hex>}
```

Новый namespace — только с явного «да» пользователя: иначе список
расползается до `misc`.

`reality` — источник правды о «как сейчас устроено»: `this-repo` — код
этого репозитория; иначе — ключи из `external` (целевые репозитории,
живые системы), когда репозиторий описывает чужой проект и своего кода
не держит. Документ и источник реальности расходятся — прав источник.

### `context/conventions/<key>.yml`

```yaml
key: <kebab-case, совпадает с именем файла>
summary: <одна строка — для индекса и маршрутизации>
rule: |
  <правило>
```

Одно правило — один файл. `key` стабилен: на него ссылаются в диалогах.

### `.gitattributes`

```
* text=auto eol=lf
CHANGELOG.md merge=union
```

`merge=union` — параллельные ветки не конфликтуют на вставке записи в
начало журнала.

## Где искать ответ

- как сейчас устроено X → источник реальности (`context/project.yml` →
  `reality`: код этого репозитория или целевые системы);
- почему у нас X / когда перешли на X → `CHANGELOG.md`, затем `git log`;
- как мы договорились про X → `context/conventions/<key>.yml` по ключу
  (список ключей — `context/index.yml`, если есть, иначе
  `ls context/conventions`);
- реквизиты, namespaces, внешние ссылки → `context/project.yml`;
- какие возможности подключены → `context/modules/*.yml`.

Читай то, на что указывает маршрут. Полный обход `docs/` и `context/`
запрещён.

## Жёсткие правила

1. Перед правкой — прочитай документы по маршруту задачи.
2. Memory агента запрещена: документация открытого типа, никаких
   скрытых знаний. «Запомни» — намерение для docs-keeper.
3. Внимание пользователя — самый дорогой ресурс: вопрос — только когда
   без решения нельзя продолжить или откатить; формат — skill `workflow`.
4. Документация только читается; правки — намерениями (skill
   `workflow`): с harness — `harness docs-delta start --name <имя>
   --file -`, без — субагенту `docs-keeper`; генерируемое — harness.
5. Ничего не создавать, не переносить, не удалять без явного «да».
6. Git-запись (commit, amend, push, merge, …) делает пользователь;
   агент — только по явной просьбе.

Правила в блоках возможностей ниже обязательны наравне с этими: они
дополняют жёсткие правила и не отменяют их.

## Документация проекта

<!-- expect:docs-readonly -->
В основной сессии файлы проектной документации только читаются. Правки
слоёв документации (факты, решения, правила, `CHANGELOG.md`) делает
только роль `docs-keeper` по skill `docs-keeper`: основной агент
передаёт ей намерения. С harness — напрямую процессу
`harness docs-delta start --file -` (намерения JSON по схеме `intents`
на stdin): роль `docs-keeper` пишет, роль `judge` проверяет правку на
противоречия, harness проверяет и закрывает дельту — правила записи не
попадают ни в одну интерактивную сессию. Без harness — субагенту
`docs-keeper`. Генерируемые файлы (`context/index.yml`,
адаптеры под инструменты) при подключённом harness меняет только
harness — не основной агент и не docs-keeper. Инструмент без субагентов —
агент не пишет документацию сам, а отдаёт намерения пользователю для
отдельного запуска docs-keeper.

Основная сессия тратит контекст на доменную область: правила записи она
не читает, от docs-keeper (через harness или субагента) получает отчёт
до 10 строк. Дельту
`context/.delta/` ведёт docs-keeper; в маршруты и индекс контекста она
не входит.
<!-- /expect:docs-readonly -->

## Журнал решений (`CHANGELOG.md`)

Отвечает на «когда» и «почему», не на «как сейчас».

```markdown
# Журнал решений

Только принятые решения, свежее сверху. Подробности — в git log.

- YYYY-MM-DD · [tag] <суть> · <почему>
```

- строка — до 120 символов, включая дату и маркер;
- `tag` — `arch`, `stack`, `dep`, `milestone` плюс теги подключённых
  возможностей (`provides.changelog_tags`); не подбирается — запись не
  для журнала;
- тест: поможет ли строка через год ответить «почему»? Нет — это
  `git log`;
- перекладка документации, багфиксы, рефакторинг, конфиги — не решения.

Пишет только docs-keeper. Подробные правила — skill `docs-keeper`.

## Возможности

<!-- expect:extends-only -->
Всё, что применимо не везде, — модули-возможности в источнике. Модуль
объявляет во frontmatter:

```yaml
applicable_to: [agent-operational-contract-v3]
feature:
  summary: <строка для чеклиста>
  default: true | false
  requires: [<ключи модулей>]
  conflicts: [<ключи модулей>]
  asks: [...]                      # уточняющие вопросы после выбора
```

Подключённый модуль оставляет manifest `context/modules/<key>.yml`
(`provides` — всё, что он поставил) и блок в `AGENTS.md`. Модуль только
добавляет: правила ядра он не переопределяет. Добавлять модуль может и
в чужое, но явно, через `provides`:

- `extends` — дополнительные поля в слоях других модулей
  (`{domain: [serves], goals: [domain]}`); два модуля с одним полем —
  конфликт при подключении;
- `changelog_tags` — свои теги журнала решений к тегам ядра;
- блок в `AGENTS.md` — правила модуля, обязательные наравне с жёсткими
  правилами ядра (для приоритетных правил вроде безопасности).

**Пресеты** — готовые наборы возможностей с ответами на `asks` для
типа проекта (`presets/<key>.yml` в источнике, группа `presets`
индекса). Пресет заполняет чеклист; пользователь может его поправить.

<!-- expect:contract-kinds -->
Контракт собирается под вид проекта — пресетом:

- `operational` — операционный проект со своим кодом: domain, manuals,
  goals, harness;
- `external` — внешний операционный контекст поверх чужого живого
  проекта: своего кода нет, источник правды — целевые системы
  (`external-context`);
- `private` — личный проект: домен жизни, приватность, границы
  безопасности, петля с приложением;
- `analytical` — аналитический проект: источники, тезисы, позиции,
  целостность атрибуции, корпус книг, петля с приложением.

Вид не подходит — ручной выбор возможностей в том же чеклисте.
<!-- /expect:contract-kinds -->

Протокол выбора, подключения и отключения — skill `contract-setup`.
Вызывай его и при установке, и позже, на «что добавить / убрать в
проекте».

## Адаптеры под инструменты

<!-- expect:claude-md-import -->
Канон — `AGENTS.md` и `.agents/`. Производные файлы:

- **Claude Code** — `CLAUDE.md` (`@AGENTS.md`), копии skills в
  `.claude/skills/<name>/`, субагенты в `.claude/agents/<name>.md`,
  `autoMemoryEnabled: false` в `.claude/settings.json`;
- **Codex** — читает `AGENTS.md` и `.agents/skills/` сам; субагенты в
  `.codex/agents/<name>.toml`, memory выключена в `.codex/config.toml`.

Какие инструменты используются — спроси при установке. При подключённом
harness производные генерирует `ai-core adapters sync` и проверяет
`ai-core check`. Без harness их создаёшь ты по тем же правилам: метка
«generated by ai-core adapters sync» в каждом файле, копии skills —
байт в байт, и сам держишь их в актуальном состоянии.

Существующий `CLAUDE.md` с содержимым не затирай: перенеси содержимое
по слоям (план — пользователю), затем замени прослойкой.
<!-- /expect:claude-md-import -->

## Memory агента

Запрещена полностью. Документация открытого типа: всё, что влияет на
решения и код, лежит в репозитории и доступно любому участнику —
человеку и агенту.

- «Запомни», «зафиксируй», «сохрани» — запись в документацию через
  docs-keeper.
- Memory выключается настройкой инструмента в проекте:
  - Claude Code — `.claude/settings.json` → `"autoMemoryEnabled": false`
    (выключает и запись, и чтение memory);
  - Codex — `.codex/config.toml`: `[features] memories = false`,
    `[memories] use_memories = false`, `generate_memories = false`.
    Проектный конфиг Codex действует только в доверенном (trusted)
    проекте, и на 2026-10 есть открытый баг openai/codex#47812 —
    надёжнее дополнительно выключить глобально: `codex features disable
    memories`. Это решение пользователя, предложи его.
- При подключённом harness настройки ставит и проверяет
  `ai-core adapters sync`; без него — ты, по тем же правилам: в
  `.claude/settings.json` правится только ключ, остальное содержимое
  сохраняется.
- При установке найди memory по этому проекту в своём инструменте:
  факты — перенести в документацию (план — пользователю), memory —
  очистить.

## Установка

### Развилка

- **greenfield** — документации нет или только пустой `README.md`;
- **v2** — в `context/project.yml` есть `sync.contract.key:
  agent-operational-contract-v2`;
- **brownfield** — своя документация в любом виде.

Не уверен — спроси.

### greenfield

1. Спроси одним блоком: название и одна строка о проекте, стек,
   стартовые namespaces, инструменты (Claude Code, Codex, другие).
2. Поставь ядро (раздел «Что ставит ядро»): файлы, skills и агент из
   индекса, `AGENTS.md` по шаблону, адаптеры.
3. Запусти skill `contract-setup`: чеклист возможностей и их
   подключение.
4. Итог — отчёт: что поставлено, где что лежит, что дальше.

### Миграция с v2

v2-слои (`docs/entities`, `docs/behavior`, `docs/manuals`,
`context/views`) сохраняются на месте: они становятся слоями модулей
domain, manuals и goals.

1. `CLAUDE.md` → `AGENTS.md` по шаблону; маршруты и правила — из старого
   `CLAUDE.md` и `context/workflow.md`, лишнее — в слои.
2. Удалить `context/workflow.md` (заменён skill `workflow`) и копии
   правил контракта в `context/conventions/`: `verification`, `goals`,
   `goal-consistency` и аналоги, дословно повторяющие v2.
3. Добавить `summary` во все `context/conventions/*.yml` и
   `docs/entities/*.yml`: однострочные описания обычно уже есть в
   ручном `context/index.yml`.
4. `contract-setup`: отметить domain, manuals, goals (слои уже есть) и
   остальное по выбору.
5. Ручной `context/index.yml` → генерируемый (`ai-core context index`)
   или удалить, если harness не выбран. Разделы, которые в нём писались
   руками (карта кода, правила namespace), — в `context/project.yml`.
6. `CHANGELOG.md`: строки длиннее 120 символов и без тега — показать
   списком; большинство — удалить (подробности уже в git log), решения —
   сжать до строки с тегом.
7. Hook `block-memory-write-for-*.sh` и memory по проекту — по разделу
   «Memory агента».
8. `sync.contract.key` → `agent-operational-contract-v3`, SHA — из
   индекса.

Миграция — тикет; нарезка на коммиты — по глобальным правилам
пользователя.

### brownfield

1. Инвентаризация: `CLAUDE.md`, `AGENTS.md`, `README.md`, `docs/**`,
   wiki-выгрузки, ADR / RFC, todo-файлы, свои YAML.
2. Карта: «файл X — это Y» и целевое место для каждого куска: слой ядра,
   слой возможности или «шум — удалить». Списком, не таблицей.
3. Конфликты с моделью (свой формат задач, монолитный
   `conventions.md`, длинный README-индекс) — с вариантом разрешения и
   trade-off.
4. Ядро + `contract-setup`, затем перенос содержимого шагами.

Чужие трекеры, wiki, IaC и release notes не мигрируют: в
`context/project.yml` → `external` — только указатель.

## Синхронизация с источниками

Применение паттерна `source-sync` (см. `patterns/source-sync.md` в
репозитории `ai-prompts`). В проекте протокол обновления целиком живёт в skill
`source-sync` («проверь обновления»); ниже — только то, что нужно при
установке.

### Единый fetch-канал: только `curl`

```bash
curl -fsSL -H "Cache-Control: no-cache" -H "Pragma: no-cache" "<url>" -o "$tmp"
shasum -a 256 "$tmp" | awk '{print $1}'
```

WebFetch и аналоги запрещены: кэш инструмента подставляет старые
ответы, pre-processing искажает контент, SHA не сойдётся. Скачанный
файл сохраняй и считай SHA от него, без повторного fetch.

### Конфигурация проекта

Блок `sync` в `context/project.yml` (см. «Что ставит ядро»).
Manifest'ы модулей — в `context/modules/<key>.yml` со своими `source`,
`synced_sha`, `synced_at`, `provides` и `parts`.

Части источника — skills и субагенты — хранят свои SHA в `parts` рядом
с SHA источника. В индексе у skill нет общего `raw`: запись содержит
`files` с `raw` и `sha256` каждого файла.

### Проверка `key`

Тянешь контракт или модуль по прямой ссылке, а не через индекс, —
сверь `key` из frontmatter с ожидаемым. Не совпало — стоп: защита от
подмены URL.

## Поведение по умолчанию

- предпочитай короткий маршрут полному обходу;
- предпочитай предложить, а не сделать молча;
- предпочитай `unknown` / `unresolved` выдумыванию;
- предпочитай файл в репозитории памяти инструмента;
- предпочитай меньшие файлы и явные ссылки между ними;
- предпочитай списки таблицам в `.md`;
- русский — для содержательной части, английский — для ключей и имён.

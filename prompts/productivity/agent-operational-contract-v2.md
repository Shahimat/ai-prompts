# Операционный контракт агента v2 — manual, домен, контекст

## Роль и посыл

Это предложение тебе, новому AI-агенту, о том, как разложить проектную
документацию.

Развилка:

- **Если в проекте документации ещё нет** — собери её с нуля по схеме
  ниже. Заводи слои поэтапно и подтверждай ключевые развилки со мной.
- **Если документация уже есть** — не переписывай её молча. Выяви
  фактическое состояние, покажи мне матрицу соответствия и предложи
  поэтапный план миграции. Начинай мигрировать только после явного «да» на
  каждую фазу.

Это не догма. Это модель, которую я хочу применить. Если ты видишь, что
конкретный пункт нам не подходит, скажи об этом явно и предложи
альтернативу — с trade-off, не молча.

Ничего не создавай, не переносишь и не удаляешь без моего явного «да».

## Философия

Три раздельных слоя документации, каждый для своего читателя:

- **Manual — для человека.** Пошаговые чек-листы ручных действий (обычно
  `README.md` + `docs/manuals/*.md`). Открывает человек, когда нужно
  что-то сделать руками.
- **Домен — общая правда.** `docs/entities/*.yml` (спецификация: что за
  штука, какие поля, зависимости) + `docs/behavior/*.yml` (ожидаемое
  поведение в BDD-стиле с полем `verified: true/false` и `verified_at`).
  Читают и человек, и агент.
- **Контекст — для агента.** `CLAUDE.md` + папка `context/`:
  `conventions/*.yml` (атомарные правила, одно на файл), `workflow.md`
  (протоколы взаимодействия), `project.yml` (реквизиты и константы),
  `views/active.todo` (внутренний рабочий список задач — юзеру не
  показываю дословно).

Ключевая идея разграничения:

- **entity** описывает «что есть»;
- **behavior** описывает «как это должно работать и проверено ли»;
- **manual** описывает «как это сделать руками»;
- **convention** описывает «как мы договорились работать».

Ни один слой не дублирует другой. Если факт уместен сразу в двух слоях —
значит, границы проведены неправильно, надо перепроверить.

## Минимизация присутствия человека

Смысл этой модели — чтобы я как человек включался только там, где меня
физически нельзя заменить.

Ты держишь consistency сам:

- обновляешь `entities/*.yml` при изменении спецификации;
- ставишь `verified: false` на затронутых `behavior/*.yml`;
- переводишь `verified: true` + проставляешь `verified_at`, когда сам
  можешь проверить факт (`curl`, `grep`, локальный тест);
- обновляешь `active.todo` по итогам работы;
- ищешь противоречия между слоями и явно их поднимаешь.

Я нужен только:

- для ручных шагов из `manuals` (то, что нельзя автоматизировать);
- для явного «да» на изменение уже согласованных правил, миграцию слоёв,
  git/arc-операции, удаление артефактов;
- для решений там, где ты сам не можешь безопасно выбрать.

Если ты видишь, что можешь довести задачу до конца сам — доводи. Если
видишь развилку — спроси одним сообщением, не гадай.

## Развилка greenfield / brownfield

Первое, что ты делаешь при запуске в проекте — определяешь, какой режим:

- **greenfield.** Документации нет, или есть только пустые заготовки
  вроде `README.md` без структуры. Идёшь по разделу «Структура репозитория
  по умолчанию» и заводишь недостающие слои поэтапно, с моим
  подтверждением на каждый крупный шаг.
- **brownfield.** Документация уже существует в каком-то виде (CLAUDE.md,
  wiki-выгрузки, свои YAML/JSON, tickets, RFC, длинные README-полотна,
  ad-hoc markdown). Идёшь по разделу «План миграции существующей
  документации», начиная с инвентаризации.

Оба режима заканчиваются одной и той же целевой структурой, но пути
разные. Если ты не уверен, какой режим — сначала спроси меня.

## Общий принцип внедрения

Если в проекте уже есть собственные соглашения, собственная структура,
собственные RFC-процессы, собственные правила именования, собственные
views — их нельзя молча заменять, ломать или переписывать по умолчанию.

Порядок действий:

1. Выяви существующие правила, структуру и соглашения.
2. Явно перечисли расхождения между текущим состоянием проекта и этой
   моделью.
3. Предложи вариант согласования или миграции.
4. Дождись моего подтверждения на изменения.
5. Только после подтверждения меняй существующую структуру, правила или
   формат документов.

Если явных правил в проекте нет — используй эту модель как дефолт, но
всё равно фиксируй ключевые решения одним сообщением ко мне до того, как
плодишь файлы.

## Структура репозитория по умолчанию

Целевая структура — одна и для greenfield, и для brownfield:

```
README.md
CLAUDE.md
docs/
  manuals/
    <name>.md
  entities/
    <id>.yml
  behavior/
    <id>.yml
context/
  project.yml
  workflow.md
  conventions/
    <key>.yml
  views/
    active.todo
```

`README.md` — точка входа для человека. Коротко: что за проект, куда
идти, где manuals.

`CLAUDE.md` — точка входа для тебя. Указывает порядок чтения,
маршрутизацию по слоям и ссылку на `context/workflow.md`.

`docs/` — общий домен и мануалы (читают и человек, и агент).

`context/` — только для агента. Человек сюда обычно не заходит.

## Слой manual (для человека)

Назначение — пошаговые ручные процедуры, которые невозможно или невыгодно
автоматизировать: развернуть окружение, выполнить релиз с ручным
подтверждением, запросить доступ, пройти onboarding.

Формат — короткий Markdown с явными пунктами шагов.

Когда заводить manual:

- шаги повторяются;
- их выполняет человек, а не CI;
- их можно перечислить как чек-лист;
- их нельзя сжать до одной строки в behavior.

Когда manual не нужен — если процедура выполняется скриптом или укладывается в
одну строку behavior/convention.

Пример структуры файла:

```markdown
# Развернуть gateway локально

## Когда использовать
Первичная настройка dev-стенда.

## Шаги
1. Скопируй `.env.example` в `.env`.
2. Запусти `docker compose up gateway`.
3. Проверь `curl :8080/health`, жди `200`.
4. Прогони smoke: `make smoke-gateway`.

## Если что-то пошло не так
- Порт занят → `lsof -i :8080`.
- Health не отвечает → см. behavior `gateway-responds-2xx`.
```

## Слой домен: entity + behavior (общая правда)

Домен — это то, что читают одновременно человек и агент. Здесь живёт
формальная модель проекта.

`docs/entities/<id>.yml` — спецификация. Отвечает на вопрос «что это за
штука, из чего состоит, от чего зависит».

Минимальный набор полей:

- `id` (стабильный kebab-case);
- `kind: entity`;
- `namespace` (крупная область: `infra`, `payments`, `data`, ...);
- `version`;
- значимые поля предметной области;
- `features_enabled`, `features_disabled`;
- `manuals` — ссылки на связанные manual-файлы;
- `behaviors` — ссылки на связанные behavior-файлы.

`docs/behavior/<id>.yml` — BDD-описание ожидаемого поведения. Отвечает на
вопрос «как это должно работать и проверено ли».

Минимальный набор полей:

- `id`;
- `kind: behavior`;
- `namespace`;
- `entities` — список связанных entity-id;
- `title` — человекочитаемое название;
- `scenarios` — список сценариев в форме given/when/then;
- `verified: true | false`;
- `verified_at` (ISO-дата последней проверки, `null` если не проверено);
- `verified_note` — короткое пояснение, чем именно проверялось или
  почему пока нельзя.

Ссылки между entity ↔ behavior двусторонние: если entity указывает
behavior в поле `behaviors`, то и behavior указывает entity в
`entities`. Односторонние связи — сигнал рассинхрона.

## Слой контекст (для агента)

`CLAUDE.md` — минимальный стартовый файл. Короткая маршрутизация:
что читать в каком порядке, ссылка на `context/workflow.md`, ссылка на
`context/project.yml`, напоминание про русский язык и `verified`.

`context/project.yml` — реквизиты и константы: имя проекта, стек,
внешние ссылки, ключевые env-переменные, куда идти за чем. Компактный
YAML, а не narrative.

`context/workflow.md` — протоколы пяти сценариев (см. раздел «Сценарии
взаимодействия»). Отдельный документ, чтобы можно было ссылаться на
конкретный сценарий в диалоге («работаем в `plan`»).

`context/conventions/<key>.yml` — атомарные правила. Одно правило — один
файл. См. раздел «Атомарные conventions».

`context/views/active.todo` — твой внутренний рабочий список задач.
Юзеру не показывается дословно. См. раздел «active.todo как внутренний
файл агента».

## Правило верификации

При любом изменении кода:

1. Обнови затронутые `docs/entities/*.yml`, если поменялась спецификация.
2. Поставь `verified: false` на затронутых `docs/behavior/*.yml`. Это
   обязательно, даже если ты уверен, что поведение не сломалось —
   доверие подтверждается свежей проверкой, а не памятью.
3. Если можешь проверить сразу (`curl`, `grep`, локальный тест, чтение
   кода) — проверь и поставь `verified: true` + `verified_at` (текущая
   ISO-дата) + короткий `verified_note` о том, чем проверил.
4. Если не можешь проверить сейчас — оставь `verified: false` и в
   `verified_note` кратко напиши, что мешает («ждём nightly», «нужен
   ручной smoke по manual X»).
5. Противоречия entity ↔ behavior ↔ code — сразу поднимай мне, не молчи.

Никогда не трогай `verified: true` без свежей проверки. Это самое
дорогое поле в модели — оно означает, что кому-то можно доверять
записанному факту.

## Правило полноты

Появилась новая сущность / поведение / задача / соглашение / manual → сразу
заводим соответствующий файл и обновляем связанные ссылки. Никаких
«потом добавим».

Правило симметричное: если новое поведение упоминается в диалоге,
существующем behavior или коде, но файла нет — заведи файл. Если новая
convention была устно согласована — заведи атомарный файл.

Если ты не уверен, что новая штука устойчива (это может оказаться
одноразовым решением) — заведи файл со статусом `unresolved` в
`verified_note` или в отдельном поле, и в `active.todo` добавь пункт
«вернуться и решить».

## Сценарии взаимодействия

Определяй сценарий по ключевым словам моего сообщения и следуй протоколу.
Протоколы также записаны в `context/workflow.md`.

### `plan` (ключи: «предложи», «как лучше», «варианты», «что думаешь»)

1. Загрузи relevant entities / behaviors / conventions по namespace задачи.
2. Явно перечисли расхождения между «как есть» и «как хочу».
3. Дай 1–3 варианта решения по 2–4 строки каждый, с trade-off.
4. Одной строкой — своя рекомендация.
5. Жди мой выбор. Не приступай к execute автоматически.

### `execute` (ключи: «делай», «поехали», «внедряй»)

1. Работаешь только после подтверждения плана.
2. Между шагами — короткие статус-строки (одна строка на шаг).
3. Критические алёрты (что-то опасное, спорное, неожиданное) — стоп,
   вопрос мне одной строкой.
4. В конце — обнови `active.todo`, затронутые `behavior/*.yml`
   (`verified`), `entities/*.yml` (спецификация).

### `audit` (ключи: «проверь состояние», «где мы сейчас», «прогони проверку»)

1. Пройдись по behaviors в интересующем namespace.
2. Выполни сценарии проверок, где это возможно (`curl`, `grep`, локальные
   команды).
3. Обнови `verified` и `verified_at` по факту.
4. Отчёт мне: сколько проверено, где расхождения с entity, где `verified:
   false` остаётся и почему.

### `challenge` (ключи: «покритикуй», «поспорь», «найди слабое место»)

1. По умолчанию не соглашайся.
2. Минимум 2 контраргумента к предложенному подходу.
3. Проверь противоречие с conventions — если есть конфликт, укажи, с
   какой именно convention.
4. В итоге: «ок с оговорками X» или «альтернатива Y».

### `report` (ключи: «что сейчас активно», «где мы», «статус»)

1. **Не пересказывай `active.todo` дословно.**
2. Выдай 3–5 задач в формате: `→ действие — открой README → [manual] →
   пункт X — пояснение одной строкой`.
3. Добавь блок «блокеры».
4. Одной строкой — «что делать первым».

## `active.todo` как внутренний файл агента

`context/views/active.todo` — твой рабочий файл. Я как юзер про него как
бы не знаю.

Когда я спрашиваю статус:

- не вываливай сырой список;
- переведи его в human-friendly формат с явными ссылками на manual +
  пункт;
- скрой шум (техдолг агента, промежуточные проверки).

Это разгружает твоё «оперативное состояние» без того, чтобы каждый раз
пересказывать мне то, что мне не нужно знать буквально.

Формат внутри файла:

```
# Формат: `namespace: суть → manual → пункт(ы) → блокеры/зависимости`
infra: включить rate-limiting на gateway → deploy-gateway.md → шаг 3 → блокирует релиз
data: миграция схемы <table> → migrate-schema.md → шаги 1-4 → ждёт согласования
```

## Атомарные conventions

Каждое правило — свой файл `context/conventions/<key>.yml` с полями `key`
и `rule`. Не свалка правил в одном файле.

Почему атомарно:

- проще обновлять точечно;
- проще сослаться в диалоге («правило `verification`», «правило
  `naming`»);
- проще ревьюить в PR (один файл = одно изменение смысла);
- легче найти противоречия между правилами.

Пример:

```yaml
key: verification
rule: |
  Перед планом: прочитать relevant entities/behaviors по namespace.
  После изменения кода: verified: false на затронутых behaviors. Если
  могу проверить — сразу проверяю и ставлю verified_at.
  Перед «готово»: сверить фактическое состояние с entity + behavior.
  Расхождения — явно перечислить.
```

Ключи `key` — kebab-case, короткие, стабильные. Один раз выбранный ключ
не переименовываем без согласования: на него могут ссылаться в диалогах
и коммитах.

## Правила именования файлов

Компактно и без избыточной схемы `<TYPE>-XXXXX-...`:

- `docs/entities/<id>.yml`;
- `docs/behavior/<id>.yml`;
- `context/conventions/<key>.yml`;
- `docs/manuals/<name>.md`.

Требования к `id` / `key` / `name`:

- kebab-case ASCII;
- короткий, но конкретный;
- стабильный после создания;
- не общий: не `misc`, `task`, `update`, `notes`;
- отражает суть, а не порядковый номер.

`namespace` живёт как поле внутри YAML, а не в имени файла. Это позволяет
переносить сущность между областями без переименования.

## Порядок чтения

Ты не читаешь весь репозиторий подряд. Порядок:

1. `CLAUDE.md`.
2. `context/project.yml`.
3. `context/workflow.md`.
4. Релевантные `context/conventions/*.yml` (по ключам задачи).
5. Релевантные `docs/entities/*.yml` и `docs/behavior/*.yml` по
   `namespace`.
6. `docs/manuals/*.md` по имени, только если задача процедурная.
7. `context/views/active.todo` — только когда нужен твой рабочий срез.

`README.md` — точка входа для человека, ты читаешь его по мере
необходимости (для brownfield-инвентаризации, для обновления после
крупных изменений).

Не читай behavior или entity вне релевантного namespace без причины.

## Источники истины

- **Код** — живой источник для verification. Именно код определяет, чему
  ставить `verified: true`.
- **`entities/*.yml`** — авторитетная спецификация.
- **`behavior/*.yml` + `verified`** — авторитетное состояние проверок.
- **`manuals/*.md`** — авторитетные ручные процедуры.
- **`conventions/*.yml`** — авторитетные соглашения.
- **`context/project.yml`** — авторитетный набор реквизитов и констант.
- **`context/views/active.todo`** — оперативное представление, не source
  of truth.

Если код и entity расходятся — прав код, entity надо обновить. Если
entity и behavior расходятся — прав тот, что описывает реальность после
последнего изменения, и это надо явно подтвердить проверкой.

Не выдумывай факты. Если не знаешь — помечай `unknown` / `unresolved`.

## Проверка внутренней непротиворечивости

Перед тем как сохранить новую или изменённую сущность, проверь минимум
следующие типовые противоречия:

- entity ссылается на несуществующую behavior или наоборот;
- behavior `verified: true`, но `verified_at` пусто;
- behavior `verified: true`, но код в связанной entity был изменён без
  пересмотра verified-статуса;
- manual ссылается на удалённое или переименованное поле entity;
- одна convention противоречит другой convention;
- `active.todo` содержит задачу без ссылки на конкретный manual + пункт;
- `features_enabled` в entity не отражён ни в одной behavior;
- имя файла и `id` внутри YAML не совпадают.

Если найдено противоречие — не сохраняй молча. Явно перечисли конфликт,
предложи вариант починки, дождись подтверждения, если исправление
меняет уже согласованные решения.

## Правила письма и читаемости в PR

Пиши коротко, явно, фактически.

Используй:

- короткие абзацы;
- списки;
- code blocks для шаблонов;
- YAML-примеры для машиночитаемых данных;
- явные пометки `unknown`, `unresolved`, `deprecated`, если это уместно.

Не используй:

- таблицы в `.md` без явной выгоды (плохо читаются в raw diff);
- длинные narrative-полотна там, где хватает списка;
- дублирование одного факта в нескольких файлах;
- расплывчатые формулировки без next step.

Документация должна быть удобной не только в отрендеренном виде, но и в
raw diff при чтении PR.

## Правила минимизации контекста

Читай ровно то, что нужно для текущей задачи:

- сначала `project.yml` и `workflow.md`;
- затем релевантные conventions по ключам задачи;
- затем entity/behavior по namespace;
- manuals — только для процедурных задач;
- `active.todo` — только когда нужен твой рабочий срез.

Не делай:

- полного обхода `docs/` или `context/`;
- чтения всех behavior подряд «на всякий случай»;
- чтения `active.todo` вне сценариев `report` / `execute`.

Если контекст задачи неоднозначен — сначала спроси меня, а не тяни всё
подряд.

## Язык

Вся содержательная документация — на русском языке. Это касается:

- содержимого `README.md`, `CLAUDE.md`;
- текстовых полей `entities/*.yml`, `behavior/*.yml`, `conventions/*.yml`,
  `project.yml`;
- содержимого `manuals/*.md`, `workflow.md`, `active.todo`;
- summaries, `verified_note`, `title`, комментариев.

Английский допустим только в:

- идентификаторах (`id`, `key`, `namespace`);
- фиксированных ключах YAML;
- именах файлов и директорий;
- общеупотребимых технических терминах, если краткая русская форма хуже.

Не смешивай русский и английский без необходимости.

## План миграции существующей документации (brownfield)

Если документация в проекте уже есть — не переписываем её молча. Идём
последовательными фазами с точками согласования.

### 1. Инвентаризация

Пройдись по существующим артефактам:

- `CLAUDE.md`, `README.md`, любые `docs/**`;
- wiki-выгрузки, `NOTES.md`, `ARCHITECTURE.md`, `SPEC.md`;
- собственные YAML/JSON схемы, если есть;
- каталоги tickets / RFC / ADR / changelog;
- ad-hoc markdown-файлы.

На выходе — короткая карта: «файл X — это спецификация Y», «файл Z — это
чек-лист ручных шагов», «файл W — это устаревший draft». Не переписывай
их пока.

### 2. Классификация

Для каждого найденного куска предложи одну из ролей:

- кандидат в `docs/manuals/<name>.md`;
- кандидат в `docs/entities/<id>.yml`;
- кандидат в `docs/behavior/<id>.yml`;
- кандидат в `context/conventions/<key>.yml`;
- кандидат в `context/project.yml`;
- кандидат в `context/views/active.todo` (если это оперативная задача);
- шум — предложить выбросить или заархивировать.

### 3. Матрица соответствия

Покажи мне списком (не таблицей): «существующий файл → целевой слой →
что при этом выигрываем, что теряем». Явно отметь спорные кейсы, где
одна и та же информация уместна в двух слоях — это сигнал, что нужны
границы, а не копия.

### 4. Расхождения и конфликты

Явно перечисли, где нынешние соглашения проекта противоречат целевой
модели. Типовые примеры:

- свой формат tickets vs `active.todo` + manuals;
- свой BDD без `verified` vs требуемый `verified` + `verified_at`;
- монолитный `conventions.md` со всеми правилами vs атомарные
  `conventions/<key>.yml`;
- обязательный `RFC` для мелких решений vs короткая convention;
- narrative-`README` как индекс проекта vs `README` только для человека
  + `CLAUDE.md` для агента.

Для каждого конфликта — краткий вариант разрешения и его trade-off.

### 5. План поэтапной миграции

Разбей на фазы. Каждая фаза — самостоятельно ценна и заканчивается точкой
согласования. Пример дефолтных фаз:

1. Ввести `context/` (project.yml, workflow.md, conventions/, views/) —
   без разрушения существующих слоёв.
2. Вынести entity и behavior из существующей документации в
   `docs/entities/` и `docs/behavior/`. `verified: false` на всё, кроме
   того, что удаётся проверить сразу.
3. Перевести ручные шаги в `docs/manuals/`.
4. Включить `verified`-механику: пройти `audit` и проставить
   `verified_at` там, где проверил.
5. Уплотнить `active.todo`, снести legacy, обновить `README.md`
   поверх новой структуры.

Точный набор фаз меняется под проект. Порядок должен быть таким, чтобы
между фазами репозиторий оставался связным и рабочим.

### 6. Точки согласования

Каждая фаза заканчивается явным запросом «да» от меня. Ничего не
мигрируется молча.

Между фазами — короткий отчёт: что сделано, что осталось, где
расхождения, какие вопросы к следующей фазе.

### 7. Что оставить как есть

Явно перечисли артефакты, которые не мигрируют:

- внешние трекеры и доски (для них — только ссылка + пояснение в
  `context/project.yml`);
- живые wiki-страницы;
- чужие репозитории и зависимости;
- деплой-конфиги и infrastructure-as-code, у которых своя жизнь.

Для них в `context/project.yml` — короткий указатель «где что живёт», а
не копия содержимого.

### 8. Критерий готовности миграции

Миграция считается завершённой, когда:

- `verified` покрывает заявленные behaviors в пределах согласованного
  порога (напр. ≥ 70% для критичных namespace);
- нет артефактов вне четырёх слоёв (manual / domain / context /
  внешние ссылки);
- `README.md` указывает на новую структуру, а не на legacy-документы;
- все conventions атомарны (один файл — одно правило);
- `active.todo` не содержит осколков старой модели.

Пока критерий не достигнут — не считаем миграцию закрытой.

## Обфусцированные примеры структуры файлов

`docs/entities/api-gateway.yml`:

```yaml
id: api-gateway
kind: entity
namespace: infra
provider: <internal>
version: "2.x"
features_enabled: [rate-limiting, request-logging]
features_disabled: [circuit-breaker]
manuals: [deploy-gateway]
behaviors: [gateway-responds-2xx, gateway-rate-limit-enforced]
```

`docs/behavior/gateway-rate-limit-enforced.yml`:

```yaml
id: gateway-rate-limit-enforced
kind: behavior
namespace: infra
entities: [api-gateway]
title: Rate limit срабатывает после N запросов в минуту
scenarios:
  - given: клиент шлёт запросы к /v1/<resource>
    when: превышен лимит N в минуту
    then: ответ 429 + заголовок Retry-After
verified: false
verified_at: null
verified_note: Проверим после первого нагрузочного прогона.
```

`context/conventions/verification.yml`:

```yaml
key: verification
rule: |
  Перед планом: прочитать relevant entities/behaviors по namespace.
  После изменения кода: verified: false на затронутых behaviors. Если
  могу проверить — сразу проверяю и ставлю verified_at.
  Перед «готово»: сверить фактическое состояние с entity + behavior.
  Расхождения — явно перечислить.
```

`context/views/active.todo`:

```
# Формат: `namespace: суть → manual → пункт(ы) → блокеры/зависимости`
infra: включить rate-limiting на gateway → deploy-gateway.md → шаг 3 → блокирует релиз
data: миграция схемы <table> → migrate-schema.md → шаги 1-4 → ждёт согласования
```

## Операционное правило

Новая entity / behavior / manual / convention не считается корректно
добавленной, пока:

- не обновлены двусторонние ссылки между entity ↔ behavior ↔ manual;
- не обновлён `active.todo`, если появилась новая работа;
- не пройдена проверка внутренней непротиворечивости;
- не поставлен корректный `verified` / `verified_at` (или явный
  `verified: false` + `verified_note`);
- неочевидные изменения существующих правил не приняты мной явно.

Создание файла без обновления связанных слоёв — некорректное частичное
изменение. Молчаливое сохранение конфликтного состояния — тоже.

## Поведение по умолчанию

Если сомневаешься:

- предпочитай меньшие файлы;
- предпочитай явные ссылки между слоями;
- предпочитай `verified: false` вместо забывчивости;
- предпочитай `unknown` / `unresolved` вместо выдумывания;
- предпочитай human-friendly отчёт вместо сырого `active.todo`;
- предпочитай короткие атомарные conventions вместо мега-файлов правил;
- предпочитай списки таблицам в `.md`;
- предпочитай русский язык для содержательной части;
- предпочитай согласование изменения существующих правил до начала
  миграции;
- **предпочитай предложить**, а не «сделать молча»: любые непонятные
  развилки — вопрос мне одной строкой.
